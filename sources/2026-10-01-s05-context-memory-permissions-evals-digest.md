## 2. One-paragraph summary

Every practitioner source says the same thing about evals from a different angle: **an eval is applied data science on your own application, not a test suite you buy** — "what good means for your product is living in your head, it's not in the traces" (Shankar) — so the first step is a human reading traces and writing one note per trace (*open coding*), clustering the notes into failure modes (*axial coding*), counting, and only then deciding which failure modes deserve a grader (Husain and Shankar 2025-09; Yan 2025-04; Nova Escola 2026-07). Graders are **binary, one per failure mode**, code where code can decide and an LLM judge otherwise; a judge is a classifier **calibrated against human labels with true-positive and true-negative rates, never raw agreement**, its model and prompt pinned (Husain; Lucas; Yan's bias survey). Anthropic's 2026 agents guide adds the vocabulary and harness rules — task, trial, grader, transcript, outcome; 20–50 tasks from real failures; isolated trials; grade the outcome, not the path; **pass^k** for consistency (0.75 per trial is 42 % over three); read the transcripts — and the production teams add the loop: judges gate every PR and grade a stable production sample daily (Nova Escola), or close the loop without a human once a golden set exists (Uber). **Memory** is the least settled bullet: the sources agree on a taxonomy (thread state vs cross-session namespaces; semantic, episodic, procedural), on a write path that **extracts facts and consolidates them** (add / update / forget / noop by a reasoning model — Mem0), on doing that **off the response path** (LangChain's "background", Letta's "sleep-time compute") and on **forgetting as a status, not a delete** (Alake), while disagreeing on whether memory is a retrieval pipeline (Mem0), state the model edits with tools (Letta; Anthropic's client-side memory tool) or "a form of context" (Tricot). **External context** is now largely a provider feature — Anthropic's Files API (never accept a `file_id` from a user; one workspace per tenant) and server-side web search with domain lists and code-side filtering before results reach the window — and **permissions** have no talk of their own: zero-trust vocabulary (just-in-time, least privilege, an identity per agent), authorisation **before or after retrieval** with embeddings inheriting the source's permissions (Pinecone/AuthZed), an **allow-list of reviewed MCP servers** and destructive-tool annotations that force an approval (Block), and the SDK shape of an approval — an interruption with resumable state, validation "next to the tool that creates the side effect", fail closed on timeout (OpenAI). The survey confirms the gap: evals are the number-one stack challenge for the third year, 89 % of agent builders give agents write access, and the control layer is "the same toolkit you'd use to manage an intern".

## 3. Detailed digest

### 3.1 Testing and evaluation — the lifecycle, and error analysis first

**What an eval is.** Husain (Lenny's, 2025-09): "a way to systematically measure and improve an AI application… at its core data analytics on your LLM application". Shankar widens it on purpose: unit tests are "a very small part of that very big puzzle"; evals include looking at data to find new user cohorts, product metrics, online monitoring and A/B tests. Yan (2025-04): "building product evals is simply the scientific method in disguise" — observe, annotate a balanced set, hypothesise, experiment with a control, measure — and **eval-driven development**: "first, write some evals; then, build systems that pass those evals". Anthropic (2026-01) gives the mechanical definition and a vocabulary this KB lacked: a **task** (inputs and success criteria), a **trial** (one attempt; run several), a **grader** (logic scoring one aspect; several per task), a **transcript** (the full record, tool calls included), the **outcome** (the final environment state — "whether a reservation exists in the environment's SQL database", not that the agent said "booked"), the **eval harness** (runs, records, grades, aggregates) as distinct from the agent harness, and a **suite**.

**Error analysis before any grader.** Husain's live walk-through uses Nurture Boss, an apartment-leasing assistant with chat, text, voice, tools and retrieval: open a trace in any observability tool ("we don't have a favorite tool"), read it "with your product hat on", write one short note — the **most upstream error only**, specific enough to categorise later ("did not confirm call transfer with user", never "janky"). This is **open coding**, a social-science term the LLM also knows. "At least a hundred" is a mental unblock; the real stop is **theoretical saturation**, when new traces stop producing new kinds of note. One **benevolent dictator** reads — the person with domain taste ("for legal… a law person… oftentimes it is the product manager") — because committees make it "so expensive that you can't do it". Then **axial coding**: hand the notes to an LLM using the words "open codes" and "axial codes", rename the generic categories ("capability limitations… that's not actionable"), map every note with a spreadsheet prompt that includes **"none of the above"** so an incomplete taxonomy announces itself, and **count** with a pivot table — "basic counting is the most powerful analytical technique in data science"; a rare failure may still come first. Shankar (2026-07) names the lifecycle **analyze → measure → improve** and the Pareto shape ("80 % of issues… caused by 20 % of failure modes"); a trace read twice yields failures the first pass missed ("the word *matters*… I only actually found very deep into my error analysis"), so loop over the data and have the agent apply each new label back to reviewed traces.

**Not every failure needs an eval.** "If it's obvious, do it… just fix your application" (Husain); "between four and seven" judges per product, only for "the pesky ones that you've described your ideal behavior in your agent prompt, but it's still failing" (Shankar). Lucas's first attempt at Nova Escola (a Brazilian lesson-plan generator; six people in technology) labelled against a full pedagogical rubric and "spent a lot of time labeling data that we didn't need" — fixes that took one prompt change; and two annotators "disagreed more than if I was flipping a coin", "a sign that the rubric wasn't clear", at "a month of work, sometimes two" per relabelling round.

**Criteria drift.** Shankar's *Who validates the validators* (2024): "it is impossible to completely determine evaluation criteria prior to human judging of LLM outputs"; a participant asked to "enforce that we look at at least 20 examples first". Yan flipped his workflow — the human reads "at least 20 or even 50" input–output pairs before writing criteria, which otherwise come "from an ivory tower" — and has watched traces labelled "good" turn "bad" the moment the labels were to stand in for the labeller. Lenny's "evals are the new PRDs" is accepted with the correction that the judge prompt is derived from the data; the PRD keeps changing.

**The 2026 production loop (Lucas).** Langfuse for traces and as the store for test sets and prompts ("I'm using it as a database"); Claude Code with Husain's skills (`write judge prompt`, `validate evaluator`, `create annotator review interface`) over the Langfuse MCP; four judges calibrated to production; judges run **as a CI gate on every PR** and **on a daily batch sample of production** — 2 % gave "very erratic" numbers, so he raised the rate until the series stabilised, "around 80 % in my case". Calibrated with one strong model, "every time we run again the judge, we use exactly the same model, so we can say that the TPR and TNR still applies". His tool complaint is a finding: the observability tool "assume[s] your judge is calibrated, so they go straight to give you a score. And I don't want a score."

### 3.2 Graders and judges — binary, calibrated, pinned

**Three kinds of grader** (Anthropic 2026-01): **code-based** (string and regex matches, fail-to-pass tests, static analysis, state checks, tool-call verification, transcript metrics — fast, objective, "brittle to valid variations"), **model-based** (rubrics, assertions, pairwise, reference-based, multi-judge — "requires calibration with human graders"), **human** (SME review, spot checks, inter-annotator agreement — gold standard, expensive): "deterministic graders where possible, LLM graders where necessary… human graders judiciously". Husain's three levels (2024) are the same ladder by cadence: level-1 assertions in pytest on every change (Rechat has "hundreds"; a pass rate "is a product decision"), level-2 human and model eval on a cadence, level-3 A/B. Shankar: code for a format, a length, a JSON shape; a judge when "we don't know how to evaluate in an automated way".

**One failure mode, one judge, binary.** Husain: a 1–5 scale "in most cases… is a weasel way of not making a decision… no one knows what 3.2 versus 3.7 means"; Shankar: "you should be anti-Likert-scale LLM judge". The judge is narrow — "evaluate one failure mode… pass or fail" — which is why it is easier than the product. Yan from the literature: "simplifying to binary actually leads to better performance"; for *subjective* criteria **pairwise comparison** is more reliable, while objective ones (faithfulness, policy) need direct scoring because "the better option from a pair might still be a defect". Anthropic's agents guide converges: "grade each dimension with an isolated LLM-as-judge" and "give the LLM a way out… return 'Unknown'". The dissent is Anthropic's own docs page, with 1–5 Likert and ordinal graders in its examples (§5).

**Chain of thought in the judge, then discard.** Yan: without reasoning the judge was "just not usable"; with it, "going from not usable to usable" — Liu's number is "12 % improvement in classification accuracy", at a latency cost from "two or three tokens" to "10 to 15 seconds", acceptable offline. Anthropic: "reason first… and then discard the reasoning". Husain's 2024 spreadsheet already carried a *critique* column beside the binary outcome, because the critique is what lets you fix the judge prompt.

**Calibration: measure the judge like a classifier.** Husain: once the prompt exists "a lot of people stop there… if the judge says it's wrong it's wrong. Don't do that". Measure it against the labels from axial coding and **never report raw agreement**: "if you only have the error 10 % of the time, then you can easily have 90 % agreement by just having a judge say it passes all the time". Look at the two off-diagonal cells of the confusion matrix and iterate until both are small; "it agrees 75 % of the time" without that matrix is "a bad smell". His blog: measure precision and recall; agreement was acceptable in his case only because the set was ~50 % failures. Yan: Cohen's κ corrects for chance (80 % agreement was κ 0.62; human–human κ on TriviaQA grading 0.97 against the best judge's 0.84); correlation metrics are "a fairly bad smell" because they do not translate to production recall. Lucas adds the hygiene the course teaches: a training split for prompt iteration and a held-out split for the number ("we were using training data inside this split"), no unbalanced sets. Husain's 2024 rules stand — the most powerful model you can afford for the critique, "a mini-evaluation system to track its quality", periodic re-checks — and Anthropic agrees: "closely calibrated with human experts… once the system is robust… human review only occasionally".

**Known judge biases (Yan's survey, papers 2023–24).** *Position bias* in pairwise comparison (one model preferred the first position 70 % of the time); *verbosity bias* (padded answers preferred "more than 90 % of the time"); *self-enhancement bias* (own answers win 10–25 % more); strong models "over-reasoning" on reference matching until told "don't overthink". Fine-tuned judge models "essentially functioned as task-specific classifiers" with "a catastrophic performance drop" on a different scoring scheme; a **panel of three smaller judges** beat one large judge "at one-seventh the cost". Judges catch obvious hallucinations and miss partial ones. Results on models two generations old: the biases are durable, the numbers are history.

**Evaluator or guardrail.** Yan's decision tree: as an *evaluator* on a few hundred samples, an LLM API with chain of thought and n-shot examples; as a *guardrail* in production, "invest in finetuning a classifier or reward model, bootstrapping it on… labels you've collected during internal evals" — `practices/structured-outputs/guardrail-tiers.md` from the eval side, and why calibration labels are an asset. Huyen (2024-12): a RAG hallucination is a **factual inconsistency with the retrieved context**, a natural-language-inference question, so an NLI classifier is the right grader (Galileo says its Luna models build on this — vendor claim).

**Own your judge prompts.** Huyen: the "number one mistake" is undefined criteria used as exact — "coherence, relevancy… very highly dependent on the model you use, the prompt for the judge"; metric maintainers and users differ; judge prompts in popular open-source tools "almost every single one have a little typo", and fixing one silently changes every score; and a correct answer is not a good one ("no, you're a terrible fit"). With Lucas's pinned model, the rule: a judge prompt is a versioned artifact with a calibration record attached — the eval-side twin of `principles/10-llm-api-fundamentals.md` §3.3.

### 3.3 Suites, harnesses and numbers — Anthropic's roadmap and pass^k

**From zero to a suite** (Anthropic 2026-01, first-person): **start early** — "20–50 simple tasks drawn from real failures is a great start"; "evals get harder to build the longer you wait… you're reverse-engineering success criteria from a live system"; **start with what you already test manually**, the bug tracker and the support queue; **write unambiguous tasks with a reference solution** — "two domain experts would independently reach the same pass/fail verdict", and "a 0 % pass rate across many trials is most often a signal of a broken task"; **balance the set** — the web-search eval needed both should-search and should-answer queries to stop over- and under-triggering; **isolate each trial** (shared state causes correlated failures; a model once peeked at "the git history from previous trials"); **grade what the agent produced, not the path** — exact tool sequences give "overly brittle tests" (the Opus 4.5 τ²-bench loophole that was better for the user and failed the eval); **partial credit**; **hack-resistant graders**; **read the transcripts** — "we do not take eval scores at face value until someone… reads some transcripts" (CORE-Bench: 42 % became 95 % after rigid grading of "96.12" vs "96.124991…" and ambiguous specs were fixed); **watch for saturation** — a suite at 100 % "provides no signal for improvement". Two suite kinds: **capability evals** that "should start at a low pass rate" and **regression evals** near 100 %; a capability eval graduates once reliably passed.

**pass@k and pass^k.** *pass@k* — at least one success in k trials — rises with k; *pass^k* — **all** k succeed — falls: "if your agent has a 75 % per-trial success rate and you run 3 trials, the probability of passing all three is (0.75)³ ≈ 42 %", the metric "for customer-facing agents where users expect reliable behavior every time". This is Klein's criterion (reused, 2026-04): "for how many of these scenarios will I get it right every time, 100 times in a row… if one in 10 customers you tell them you booked their flight but you didn't, that's a showstopper". Uber's pass@K for its retry loop is the other reading — one success in K iterations suffices because deterministic gates follow.

**The holistic table and the docs page.** Anthropic lists automated evals (CI), production monitoring (drift), A/B (slow), user feedback (sparse), manual transcript review (weekly) and systematic human studies (judge calibration) as Swiss-cheese layers, with the cadence "triage feedback constantly, sample transcripts to read weekly" — matching Shankar's online judges ("sample a thousand traces every day") and the s3 rule that offline evals are unit tests and online evals are monitoring. The older docs page asks for specific, measurable, multidimensional criteria, shows exact-match, cosine, ROUGE-L, Likert, binary-PHI and ordinal graders, and says "prioritize volume over quality: more questions with slightly lower signal automated grading is better than fewer… human hand-graded evals" — the opposite emphasis from Husain's "look at your data" (§5).

### 3.4 Automating evals, and closing the loop in production

**What AI can and cannot do (Shankar 2026-07).** The argument is epistemic: "if a tool could fully build and fix your product for you, it could do the same for… all of your competitors… your judgment is the only differentiating factor". AI is weak at *analyze*, useful at *measure* and *improve*. Three mistakes: (1) "check out my traces, evaluate the app" to a coding agent — it "will miss all of the taste-specific issues… anything that lives in your head that's not externalized", "fabricates what they think is the highest priority", and leaves **no reusable intermediate** — failure-mode definitions must be persisted; (2) reviewing each trace once; (3) "a uniform accuracy bar for all of your AI applications" — set the bar by reasoning about **worst-case scenarios** from the user's shoes ("sabotaging the citation… leaking… private" information). What she automates with an open-source skill: the agent reads a sample, builds a review app (trace viewer, cluster map, progress view), samples per cluster, then **monitors her in-situ annotations, maintains the taxonomy and proposes instances of a known failure mode in other traces** — "I don't tell the agent to find me entirely new examples of failure modes… I don't love the experience of just trying to validate the agent's taste". Husain, in the Nova Escola video: the skills "are meant to be customized… ultimately it's somebody else's prompt"; their unpublished benchmark reportedly found coding agents "more exhaustive" than dedicated discovery platforms because a vendor's tool "is like someone's prompt" (§4).

**Remove the friction from looking at data.** Husain (2024): "build my own data viewing & labeling tool so I can gather all the information I need onto one screen" (Gradio, Streamlit, Shiny, "in less than a day"); Nurture Boss "created this within a few hours". DoorDash (2026-08): UI-first for non-engineers, then **API-first** ("stable table APIs" for traces, scores, datasets), then workflow-first — "we were actually able to enable our strat-ops teams to use something like Codex or Claude Code and vibe-code their own annotation UIs"; its loop is tracing → sampling → annotation → review → golden datasets → judge calibration (a self-serve UI showing the original and the optimised judge prompt side by side "so that they are also able to gain that trust") → monitoring, with GEPA for prompt optimisation. *Paired error analysis* (2026-04) shows a developer and a domain expert building the annotation app together from a raw JSONL export, with Husain's commentary as the method: "when you explore the data, you come up with some hypotheses", "this is a product problem… that wouldn't be something you need an eval for". Ownership is cross-functional at DoorDash (ops set the bar, product writes rubrics, ops annotate, engineering provides APIs and judges) and at Anthropic ("dedicated evals teams… own the core infrastructure, while domain experts and product teams contribute most eval tasks"; PMs "can use Claude Code to contribute an eval task as a PR — let them").

**Closing the loop without a human (Uber 2026-07).** The food-photo enhancement pipeline is the module's one fully closed loop. Logging first — one flat JSON per orchestration, "if you don't start with it, you have nothing to optimize for". The **router** (describe → structured output → rubric → enhance or skip) is evaluated as a classifier with a confusion matrix; its guardrail metric is **recall** ("we don't want any bad image to slip through"). **Human labels are the golden source of truth**, on a representative cut with "a very objective guideline". Drift: sample production, send to the same labelers, compare; on mismatch a "diagnosis agent" localises the failing agent and triggers **auto-tuning** — a *reflect* sub-agent denoises mismatches, a *synthesize* sub-agent rewrites the config — **benchmarked against the golden set and registered only if it passes**, "completely config driven and doesn't require human in the loop… quick rollback built in". The enhancement loop is generate → multi-dimensional QA gate → regenerate-with-feedback, measured as pass@K, then a second "publish-ready" QA ("a Swiss cheese model"), with named failures: added shrimp (faithfulness), removed sauce (completeness), an overly conservative plate after feedback ("an example of a reward hacking"), an *unsure* verdict that rejects. Safe because every automated change is measured against a human-labelled set and deterministic gates follow the model.

**The market's numbers (Amplify 2026-07; 1,048 respondents).** "Evals" is the top stack challenge "every single year", "by a very thin margin"; "the vibe review is number one"; 95 % use agents and 89 % of those agents can write data (52 % before), so write-enabled agents tripled; the top controls are "human-in-the-loop approvals and gating permissions… the same toolkit you'd use to manage an intern" — "nobody has settled the control layer"; two-thirds name hallucination or "losing context mid task" as the top frustration. Self-selected; useful as self-report.

### 3.5 Tooling — promptfoo, DeepEval, and what a tool assumes

**promptfoo** (read 2026-10-01): "an open-source CLI and library for evaluating and red-teaming LLM apps" — declarative test cases, matrix views across prompts and inputs, caching, CI/CD, any provider, "runs completely locally", a red-teaming mode; "test-driven LLM development, not trial-and-error" in five steps (define cases from failure modes → configure → run → analyze → expand from feedback). **DeepEval** (quickstart, v4.2.7 as shown): a pytest plugin (`deepeval test run`) whose first example is `GEval` — a criteria string scored 0–1 with `threshold=0.5` deciding pass/fail — and whose second is `JevEval`: typed questions (`Noul(…, weight=2)`, `Score(levels=["Almost none","Some","Most","All of it"])`) answered by the Jev decision model with "no LLM key needed" — the s4 system-one model already shipping as a grader; agents are evaluated by tracing (`@observe`, `TaskCompletionMetric` over "the complete ordered trace") with span-level evals; online evals need the vendor's Confident AI. Anthropic's appendix lists Harbor, Braintrust, LangSmith, Langfuse and Phoenix: frameworks "are only as good as the eval tasks you run through them". The KB's reading, with Lucas's complaint and Huyen's typos beside DeepEval's defaults: **a tool's default score and threshold are someone else's judge prompt and cut-off; a 0–1 score at 0.5 is a Likert scale in disguise until calibrated** — use the tool as runner and datastore, write your own binary graders, keep the calibration record outside it.

### 3.6 Conversational memory — taxonomy, write path, forgetting, substrate

**Taxonomy.** LangChain (read 2026-10-01): **short-term memory** is thread-scoped — the message history and per-conversation state, persisted by a checkpointer — and its problem is the one principle 11 covers; **long-term memory** is cross-thread, saved under **namespaces** (user, organisation, context) as JSON documents searchable by filter and similarity. Three types via the CoALA paper: **semantic** (facts about a user), **episodic** (past actions — "often implemented through few-shot example prompting"), **procedural** (the agent's instructions — "more common… to modify their own prompts" by reflection than weights or code). Alake's four map to runtime parts: working memory → the window or a scratchpad; semantic → the knowledge base; episodic → anything timestamped; procedural → "skills… we have skill MDs now". Semantic memory is a **profile** (one JSON document regenerated or patched — error-prone as it grows; "strict decoding" keeps the schema valid) or a **collection** of small documents (higher recall, but "the model must now delete or update existing items… some models may default to over-inserting and others… to over-updating"). **When to write**: "in the hot path" (immediate, transparent, but latency and one more tool — ChatGPT's `save_memories`) or "in the background" (no latency, but a trigger policy). Tricot's refusal to separate is the null hypothesis: "memory is a form of context… data that is going to land somewhere in your agent and you have a way to query it, update it".

**The write path: extract, then consolidate (Mem0).** Chhikara (2025-06) on the 2025-04 paper: on each exchange the **extraction** call sees a running summary (generated asynchronously), the last *m* = 10 messages and the new pair, and emits candidate memories; the **update** call retrieves the *s* = 5 most similar existing memories per candidate and asks the model to choose **ADD / UPDATE / DELETE / NOOP**. Three model calls per turn, one off the critical path; `add` can be asynchronous, `search` cannot. The graph variant extracts triplets, merges duplicate nodes ("SF and San Francisco") and redundant edges ("likes" and "loves"). Two engineering findings matter more than the benchmark: the update step "requires reasoning between the existing and the new memories" — a small *reasoning* model instead of a small chat model gave "a huge performance improvement"; and extraction prompts are use-case specific (the platform asks for a use case, a memory style and **include/exclude** lists so order ids are kept and SSNs are not). The graph "we do not recommend… to all of our users" — only where social relations matter — and roughly doubles tokens against the "100 milliseconds" customers want; bulk import uses `infer=false`. The abstract's numbers (LOCOMO: 26 % relative judge improvement over OpenAI's memory, graph +2 %, p95 latency 91 % lower, >90 % fewer tokens than full context) are the vendor's on ten companion-style conversations; the mechanism is what the KB keeps.

**Stateful agents and sleep-time compute (Letta 2025-07).** Packer: agents "don't really have the capability to learn", so they are run once and thrown away; a stateful agent "persist[s] indefinitely". MemGPT's mechanism — the model edits its own memory with tools — is what every chatbot's memory feature now does; the next step is **consolidation**: atomic facts rewritten into one sentence, because "memories are more than a sum of their parts" and ChatGPT's raw memory is "the most random stuff". It runs **at sleep time** — "test time compute taken to its limits" — a background agent, "the subconscious brain of the main agent", that rewrites memory, reads uploaded documents proactively and indexes a codebase while the user is away, removing the synchronous "hold on, I'm going to write to my memory" latency. Kept as opinion with a kernel the KB accepts: OpenAI's agent definition (model, instructions, tools, runtime) "doesn't have state"; and "the lifetime of the agents are much longer than the lifetime of the models", so state lives in storage you own. Bilt's "over a million agents" is a vendor figure.

**The provider's version: Anthropic's memory tool (read 2026-10-01).** A **client-side** tool: `{"type": "memory_20250818", "name": "memory"}` is the whole configuration; Claude issues `view`, `create`, `str_replace`, `insert`, `delete`, `rename` under `/memories` and **your application executes them against storage you control**. The API adds the instruction automatically — "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE… ASSUME INTERRUPTION: your context window might be reset at any moment". Security is the handler's job: reject paths outside `/memories` (canonicalise; refuse `../` and URL-encoded traversal), strip sensitive data before writing ("Claude usually refuses… for stronger guarantees, add validation"), cap file sizes and `view` output, expire unused files. Its relation to s2 is stated: pair it with **compaction** — "compaction keeps the active context small without client-side bookkeeping, and memory preserves the information that must survive summarization" — and for multi-session software work an initializer session writes a progress log and a feature checklist, each session reads them first and updates them last, a feature is complete "only after end-to-end verification" — the provider-side form of `practices/session-state/`. SDK helpers for Python, TypeScript, C#, Java; Go and Ruby run the loop by hand; PHP wraps a handler in the generic runnable-tool helper.

**Forgetting, audit and substrate (Alake 2026-04).** **Think memory first**: "every piece of information [is] something to be remembered or forgotten", so every **memory unit** carries attributes that make it recallable and forgettable, evaluated against "LongMemEval, LoCoMo or MemBench". And **"you don't delete information in memory engineering. You forget"** — human-like, and it serves audit in finance. His one concrete mechanism is the Stanford *Generative Agents* (2023) score — **recency** × **relevance** × **importance** (how many units depend on it) — so unreferenced memories decay out of retrieval without being destroyed. His boundary is the one the KB adopts: storage side — retrieval strategy, indexing, data model, "the forget logic" — is **memory engineering**; inside the window — budgeting, just-in-time retrieval, composition — is **context engineering**; a summary put back in the window is context engineering, the original moved to a store with an id and a description for later fetch is memory engineering (Manus's compaction-vs-summarisation split restated). **Memory-aware agents** segment the window by type, each prefixed with its purpose, including a **workflow memory** of the steps taken. On substrate he argues against "files are all you need": a proof of concept may use files, production needs "scalability… ACID transactions… auditability". The KB's own sources point the other way (Claude Code's files, Manus's sandbox, Anthropic's file-shaped tool over any store); §5 resolves it as interface vs substrate. Manus's explicit memory (reused) is the user-confirmed variant — "here's what I learned… would you like to accept it or reject it?".

### 3.7 External context — files, web, MCP

**Files API (read 2026-10-01).** Upload once, get a `file_id`, reference it in `document` (PDF, text), `image` or `container_upload` (datasets for code execution) blocks. The security paragraph is the finding: **"Uploaded files are accessible to your entire workspace, not scoped to an end user, conversation, or session… Never accept `file_id` values from end users… create a separate workspace for each tenant. The workspace is the isolation boundary"** (100 workspaces per organisation). Limits: 500 MB per file, 1 TB per organisation, ~500 requests/minute, optional `expires_in_seconds` (1 hour to 90 days, set once; expiry "is a lifecycle feature, not a guaranteed-deletion control"); uploads cannot be downloaded, only files produced by skills or code execution; operations are free, content is billed as input tokens; uploads, downloads and deletes appear in the Compliance API feed.

**Web search tool (read 2026-10-01).** Server-side, three versions (`web_search_20250305`; `_20260209` adds **dynamic filtering**; `_20260318` adds `response_inclusion`). The model decides when to search and answers directly for stable knowledge; triggering is steerable by prompt and capped by `max_uses` ("simple factual queries typically use 1–3 searches; comparative… 10 or more"). Controls: `allowed_domains` *or* `blocked_domains` (400 if both), `user_location`, an organisation-level switch. Dynamic filtering is the s2 *reduce* operation done by the provider: "Claude instead writes and runs code that filters the results first, so only relevant content reaches the context window", inside code execution by default on newer versions; `response_inclusion: "excluded"` drops consumed result blocks. Client duties: results carry `encrypted_content` that **must be sent back unchanged on later turns** (400 otherwise); citations "must be included" when shown to end users; errors arrive inside a 200 (`max_uses_exceeded`, `too_many_requests`, `query_too_long`, `request_too_large`, `unavailable`); a long turn may return `stop_reason: "pause_turn"` to be resumed by resending. Price: US$10 per 1,000 searches plus tokens; results count as input on every later turn. Anthropic's agents post supplies the eval: a balanced should-search / should-not set.

**MCP as the external-context transport (Block 2026-01).** Jones's answer to "fancy function calling": MCP's value is cross-system workflows "that couldn't have happened on your closed machine" — an incident report that pages a human while a GitHub-connected agent opens a PR; an agent in Slack that reads a thread, proposes three fixes and implements the chosen one; tickets assigned to the agent in Jira. This does not contradict Notion's s12 position (CLIs for coding agents, MCP for narrow permissioned agents): her examples are all narrow, hosted and permissioned. The Council of Mind demo uses MCP **sampling** — the server borrows the user's model for nine persona calls — the primitive `principles/21-agent-design-and-tools.md` §3.5 lists.

### 3.8 Permission-adaptive systems — zero trust, retrieval-time authorisation, the tool boundary

**Zero trust restated for agents (IBM 2026-02).** Kept because the bullet has nothing better and the vocabulary is standard: **verify, then trust**; **just-in-time, not just-in-case** ("only when they're needed, and not for longer than they're needed"); **pervasive controls**, not "the hard crunchy outside and the soft, chewy center"; **assume breach**. For agents: every agent and every sub-agent it spawns gets its own **non-human identity** (NHI) with "the same level of control and visibility that we had for the human users… maybe even more"; **no static credentials** — a vault issuing dynamic, short-lived ones; a **tool registry** of vetted APIs, data sources and tools; an **AI gateway or firewall** inspecting inputs for injection and outputs for leakage; **immutable logs**; model scanning; and a human with a **kill switch**, **throttles** ("it doesn't just suddenly decide… to buy a thousand of these in a minute") and **canary deployments**.

**What a regulated company did (Block 2026-01).** Goose, Block's open-source MCP client, reached all 12,000 employees in about eight weeks; the controls: an **allow-list of MCP servers** — "if it's not on that allow list… the agent will say nope, can't install it" — admitted only after a security review, most built in-house, "only a handful" from vendors; **tool annotations** marking a tool *destructive* and a toggle so the agent runs non-destructive tools freely and "if you run into one that is, you need to ask my permission first, like give me some insight into what this is"; **OAuth against the company identity provider** instead of API keys and scopes; a red team that found **invisible characters** hidden in shareable "recipes" (bundled instructions, prompt and servers), and detection of malicious servers built into the client.

**Approvals in the SDK (OpenAI, read 2026-10-01).** The decision table: block disallowed requests → **input guardrails**; validate or redact the final output → **output guardrails**; check arguments or results around a function → **tool guardrails**; "pause before side effects like cancellations, edits, shell commands, or sensitive MCP actions" → **approvals**. An approval is a tool declared `needs_approval=True`; the run "records an approval interruption instead of executing the tool", returns the interruptions plus a **resumable state**, the application approves or rejects, and the run resumes *from that state* — "if the review might take time, serialize state, store it, and resume later. That's still the same run"; it holds inside handoffs and nested agent-as-tool calls, and streaming "doesn't create a separate approval system". The boundary rule adopted verbatim: "don't rely only on agent-level input or output guardrails. **Put validation next to the tool that creates the side effect.**" The cybersecurity paragraph is the strictest check in the module: compare "the proposed target, action, tool arguments, calling identity, and engagement window against the approved scope", give the reviewer "only the context needed", pause ambiguous actions, and **"fail closed if review times out or becomes unavailable"** — the default `practices/verification/dry-run-and-approval.md` rule 2b already chose.

**Authorisation at retrieval (Pinecone/AuthZed 2026-01).** "If different users have different levels of access to data… your RAG pipeline must enforce those access boundaries"; the constraint is that "embeddings need to retain the permissions from where the data was originally sourced", hence the author's case for **relationship-based access control** (ReBAC, Google Zanzibar, SpiceDB). Two placements, worked with user Kim and two articles whose answer disappears when permission is revoked: **pre-filter** — `LookupResources` returns the ids the subject may view and the vector query carries `filter: {article_id: {$in: authorized}}`; **post-filter** — the store returns top-k and `CheckPermission` (or `CheckBulkPermissions`) runs per result before the context is built. Choice by hit rate: post-filter when most retrieved documents are authorised, pre-filter for a large corpus with a low authorised rate. The mechanism is product-independent; "OpenAI secures 37 billion documents" with it is AuthZed's marketing. The same filter applies to a memory store — a user's or tenant's memories are a namespace the query must carry — which is why the memory skeleton in §7 scopes every unit by owner and filters at query time.

**Why scope limits are scale limits (Zhang, reused).** "If your errors are going to be high stake and very hard to discover… you can have read only access, you can have more human in the loop, but this will also limit how well you're able to scale your agent." The survey shows the market moving the other way — write access tripled, controls "pretty primitive".

## 5. What is contested / trade-offs

- **Binary judges vs Likert scales.** Husain, Shankar, Yan: binary per failure mode (pairwise for subjective criteria); Anthropic's agents post: isolated judges per dimension with an "Unknown" out — compatible; Anthropic's docs page and DeepEval's defaults: 1–5 scales and 0–1 at 0.5. **Position:** binary per failure mode, the s4 allowance of at most five classes only for a graded decision, a calibration record either way; a tool's 0–1 score is uncalibrated until its threshold has been checked against labels.
- **LLM judge vs human.** Shankar: the human is irreplaceable at analysis, the judge a scaled stand-in on one failure mode; Yan: "it's usually the human that breaks" — the judge exposes criteria nobody could articulate; Huyen: human-in-the-loop "never going to go away… not the first line of defense". **Position:** humans label and own the rubric; judges scale the verdict; the calibration record is the contract and is re-checked on a cadence.
- **Automate vs look at the data.** Anthropic's docs: "prioritize volume over quality"; Husain: "you are doing it wrong if you aren't looking at lots of data"; Shankar: automate measure and improve, never analyze. Not a contradiction once the lifecycle is explicit — the docs page describes the measure step. **Position:** error analysis manual and first; graders automated and many; the agent builds the tools that make looking cheap.
- **Closed loop (Uber) vs human in the loop.** Uber's auto-tuner rewrites configs with no human, behind a human-labelled golden set, guardrail metrics and rollback. **Position:** close the loop only after a golden set exists and only for changes measured against it; the human moves to labelling and rollback; judges still never gate the publish alone.
- **Memory as a pipeline (Mem0) vs state the model edits (Letta, Anthropic's tool) vs "just context" (Tricot).** **Position:** the write path is extract → consolidate regardless of who triggers it; a tool-triggered write suits agents working across sessions on their own tasks; a background pass suits user-facing memory where latency and transparency matter; the application owns scoping, validation and forgetting in both. An opinion for Martin's shapes.
- **Files vs database as substrate.** Alake: production needs ACID, scale, audit; Claude Code, Manus, Anthropic's tool: a file interface. **Position:** the model's *interface* is files or file-like commands; the *substrate* for a multi-user product is a namespaced store with concurrency and audit; a single-user agent can keep real files. "One database for everything" is the vendor's preference.
- **"Don't delete, forget" vs the right to erasure.** **Position:** forgetting is a status with a trail by default; a documented erasure path where `personal_data` or `regulated` holds.
- **Permissions in the retriever vs at the tool boundary.** Pinecone/AuthZed around retrieval; OpenAI "next to the tool that creates the side effect"; IBM everywhere. Not alternatives: retrieval authorisation protects *reads*, tool guardrails and approvals protect *writes*. **Position:** both, with identity carried from the request through filter and tool call, and the trust register recording each tool's identity rung.
- **MCP everywhere vs CLIs.** Jones: hosted, cross-system, permissioned workflows; Notion (s12): CLIs for coding agents. Compatible once the agent's shape is named; Block's allow-list and annotations become the permission model for the MCP branch.
- **Who benefits.** Mem0, Letta and Oracle sell memory substrates; Galileo sells judges and sponsors the podcasts; DoorDash and Uber describe their own platforms; IBM sells security; AuthZed wrote the Pinecone post; Confident AI upsells from DeepEval; Husain and Shankar sell the course; Amplify invests in what it surveys; Anthropic documents its own tools. Mechanisms kept with a second source; numbers and rankings not.

### 7.4 New principle — `principles/14-evals-and-error-analysis.md` (draft until 2026-11-12; ≤ 28 KB)

### 7.8 Glossary entries to add (`principles/00-glossary.md`)

- **Eval** (rewrite). Systematic measurement of an LLM application's quality on its own tasks — code assertions and judges in CI, graded production samples, A/B tests — preceded by error analysis. Husain and Shankar (2025-09); Yan (2025-04); Anthropic (2026-01).
- **Error analysis (open coding, axial coding).** One specific note per trace about the most upstream error, then clustering notes into named failure modes and counting. Husain and Shankar (2025-09).
- **Theoretical saturation.** When more traces produce no new kind of note. Shankar (2025-09).
- **Benevolent dictator.** The one domain expert whose taste decides labels and rubrics. Husain (2025-09).
- **Criteria drift.** Criteria cannot be fixed before looking at outputs; rubrics and earlier grades change as more is seen. Shankar et al. (2024).
- **Judge calibration.** Measuring a judge as a classifier against human labels on a held-out set — TPR/TNR or Cohen's κ with the confusion matrix — never raw agreement; then pinning model and prompt. Husain (2024); Lucas (2026-07); Yan (2024-08).
- **Judge bias (position, verbosity, self-enhancement).** Preferring the first option, longer answers, and the judge's own outputs. Zheng et al. (2023) via Yan.
- **Task / trial / grader / transcript / outcome / eval harness / suite.** Anthropic's agent-eval vocabulary (2026-01).
- **Capability vs regression eval; pass@k vs pass^k.** Suites that start low vs suites held near 100 %; at least one success in k trials vs all k — (0.75)³ ≈ 42 %. Anthropic (2026-01); Klein (2026-04).
- **Memory (semantic / episodic / procedural; short-term / long-term).** Facts, events and instructions an agent keeps; thread-scoped state vs cross-session namespaced store. LangChain; CoALA; Alake (2026-04).
- **Extract → consolidate.** Candidate facts from an exchange, nearest memories retrieved, a reasoning model deciding add / update / forget / noop. Mem0 (2025-04).
- **Sleep-time compute.** A background agent that consolidates memory and pre-processes documents while the user is away. Letta (2025-07).
- **Forgetting (vs deleting).** Removing a memory from recall by status or a decayed recency × relevance × importance score while keeping its trail; a separate erasure path where law requires. Alake (2026-04); Generative Agents (2023).
- **Memory engineering vs context engineering.** The storage side (retrieval, indexing, forgetting) vs the window side (budget, just-in-time retrieval, composition). Alake (2026-04).
- **Non-human identity (NHI); just-in-time access.** An identity per agent and sub-agent with short-lived, vault-issued credentials granted only while needed. IBM (2026-02).
- **Pre-filter vs post-filter authorisation (RAG).** Constraining the query to authorised ids vs checking each result; chosen by hit rate. Pinecone/AuthZed (2026-01).
- **Approval (interruption with resumable state).** A tool call that pauses the run, returns serialisable state, resumes on a human decision; fails closed when review is unavailable. OpenAI Agents SDK (2026-10-01).
