## 2. One-paragraph summary

The market has renamed this whole module **context engineering** — "the delicate art and science of filling the context window with just the right information needed for the next step" (Karpathy's definition, quoted by every speaker) — and has converged on five operations and four failure modes. The operations: **offload/write** (put large tool results and notes in files or a store and keep a pointer), **reduce/compress** (reversible compaction first — drop payloads whose pointer survives — then structured summarisation of the oldest half, never the recent turns, never the system prompt), **retrieve/select** (bring back only what this step needs; for code and docs a curated manifest plus grep often beats a vector index), **isolate** (sub-agents with their own windows that return a self-contained digest; fan out only read-only work, converge for anything that must cohere), and **cache** (a stable, append-only prefix so the provider's KV cache hits; caching cuts cost and latency and does *nothing* for quality). The failure modes (Drew Breunig's, repeated by Google, LangChain and Martin): **poisoning** (a hallucination lodged in history is reused), **distraction** (the model fixates on a long history instead of planning afresh), **confusion** (irrelevant detail steers the answer), **clash** (two sources disagree and the wrong one wins). The one number everyone agrees on is that quality degrades long before the advertised window: practitioners trigger compaction at roughly 60–85 % of the window or at ~128–200k tokens on 1M-token models — "the less context window you use, the better outcomes you'll get, always" (Horthy). On the economics: agent workloads are input-heavy and re-send the whole transcript every turn, so the bill grows quadratically without caching and linearly with it; cache reads cost ~10 % of fresh input; a timestamp or a changing tool list at the top of the system prompt silently destroys the saving; compaction resets the cache and that is fine. On **CAG vs long context vs RAG**: CAG (pre-compute and persist the KV cache of a fixed corpus) is what prompt caching delivers "as a service"; long context wins for a bounded corpus queried once or needing whole-document reasoning (the "what was omitted?" question RAG cannot answer); retrieval remains necessary for unbounded or fast-changing data and to keep the haystack out of the window; and for code and documentation, agentic search (grep, a manifest with good descriptions) has displaced indexing in the leading coding agents. Finally, three things the vendors disagree on and the KB records as open: whether free-form summarisation is production-viable at all (AWS yes with a preserve-list, Arize no — head+tail truncation with retrievable middle), whether to leave tool errors in context (self-correction) or prune them (poisoning), and how much of this the harness should decide versus the model.

## 3. Detailed digest

### 3.1 Why the window is not the budget (Martin; Horthy; Ebbelaar; Google; IBM)

Every source states the same premise with different evidence: a bigger window is not a bigger budget. Chroma's *Context Rot* (18 models, 2025-07) and the needle-in-a-haystack literature Anthropic's post cites show accuracy falling as input grows, non-uniformly and on simple tasks; *Lost in the Middle* explains the shape (edges recalled, middle lost — IBM and Pocock in s1 repeat it). Practitioners give the operational version: Manus compacts at ~128–200k tokens on models sold as 1M; Horthy's "smart zone" is the first 100–200k depending on the model and he calls it intuition, not measurement; LangChain's middleware defaults to a trigger at 80 % of the model's window; AWS's demo at 85 %. Horthy adds a second budget most people miss: beside the *information* budget there is an *instruction* budget — he cites a 2025 study of instruction-following degrading past ~150–250 instructions (unverified by him, and "on old models") — and a *trajectory* effect: because the model is autoregressive, a history full of failed attempts and "you're absolutely right" corrections predicts more of the same; the fix is a fresh window, not another prompt. Claude's own short (2026-05) gives the coding-agent rule in one line: `/compact` to continue the same feature, `/clear` to start another, because "you don't want the previous conversation to present bias in anything new".

### 3.2 The five operations (Martin's taxonomy; Manus; AWS; Chase; Arize)

**Offload / write.** Every tool result whose content is already persisted somewhere addressable — a file path, a URL, a search query — can be dropped from the transcript and re-read on demand: "no information is truly lost, it's just externalized" (Manus). Chase (LangChain Deep Agents) makes the file system — real or "virtual", backed by Postgres — a first-class agent capability for exactly this; AWS shows the concrete shape (results above ~2,500 tokens go to S3 with a 500-token preview and a retrieval tool). Design consequence, stated by Manus and by nobody in the s12 digest: **tools should return an identifier alongside or instead of the payload**, because that is what makes later compaction lossless.

**Reduce / compress.** Manus draws the line the others blur: *compaction* is reversible (strip the `content` field, keep the `path`), *summarisation* is lossy, and you escalate to the second only when the first stops freeing enough. Rules that recur across Manus, AWS and LangChain: compact the oldest ~50 % and keep the recent turns verbatim (the model imitates the format of recent tool calls — compact them all and it starts emitting malformed calls); summarise from the *full* record, never from already-compacted history; splice the last N raw exchanges *after* the summary; prompt the summary as a **schema** (goal, files touched, decisions, where I left off, open questions) rather than "please summarise", because structured output is stable and iterable; use a cheaper model for the summariser (LangChain's demo uses the small tier); never reset the system prompt. Arize's counter-experience is the important dissent: their free-form summariser was "too inconsistent — no control over what got dropped", head-only truncation broke follow-ups, and what has held for months is **head + tail preservation with the middle stored and retrievable**, plus deduplication of repeated tool results. The KB reads the disagreement as: unconstrained summarisation fails; constrained (schema, preserve-list, recency window) or reversible compaction holds.

**Retrieve / select.** Google's phrasing — "selection, not hoarding" — and two concrete data points. Lance Martin's own three-way test on ~3M tokens of LangGraph docs: a curated `llms.txt` (file list with LLM-written one-line descriptions) plus a plain fetch tool beat both a vector store and context-stuffing when driven by a coding agent, and description quality was the dominant variable. And the coding agents that work (Claude Code, Cline, per Boris Cherny as relayed by Martin) do **no indexing** — agentic grep/glob only — while Windsurf keeps a chunk-embed-rerank-graph pipeline; Manus's answer to the same question is "it depends on scale: no index for a task, an index for an enterprise knowledge base". Ebbelaar's RAG rule of thumb (retrieve ~50, rerank to ~8) and Airbyte's point that retrieval fails for lack of *metadata at ingestion* (the attendee's name on a call transcript), not for lack of a better embedding, are parked for the RAG sessions. AWS adds **progressive disclosure of instructions** (skills loaded on demand instead of one monolithic system prompt), the same mechanism the KB already has for tools.

**Isolate.** Sub-agents with their own windows, returning a digest. Three refinements the s12 digest did not have. (1) Chase: the commonest sub-agent bug is that *only the final message crosses the boundary* — a sub-agent told to "refer to the work above" leaves the orchestrator blind; require a self-contained final message. (2) Manus: two patterns — *communicate* (short brief in, structured result out; Claude Code's Task tool) and *share memory* (the sub-agent inherits the whole history) — and the second forfeits the cache entirely because the sub-agent's system prompt and tool set differ from the parent's: "you have to pay the full price". Default to *communicate*. (3) Martin, reconciling Cognition ("don't build multi-agent; inter-agent compression is lossy, decisions conflict") with Anthropic's multi-agent researcher: fan out only **read-only, independent gathering**; do every step that must cohere — the final report, code that must integrate — in one agent. His own bug (sections written independently inside sub-agents produced a disjoint report) is the first-hand confirmation. Manus additionally refuses role-based agents (no "designer agent", "manager agent"): a general executor, a planner and a memory agent, because every extra agent multiplies communication.

**Cache.** Treated in §3.3.

### 3.3 Prompt caching, the KV cache and the economics (Hugging Face; IBM; Manus; Martin; AWS)

**What it is.** Not output caching. The provider stores the transformer's key/value tensors for a **prefix** of the request and, on the next request, matches token by token from the start until the first difference; everything after that is recomputed (IBM; Hugging Face). Hence the single design rule, stated by all five: **static first, dynamic last, append-only**. What breaks it, per Hugging Face's list: a timestamp or current directory in the system prompt, a tool list that changes between turns, edits to earlier messages, and — legitimately — compaction, which rewrites history and therefore restarts the cache ("that's exactly how compaction is supposed to work; just consider that it resets your cache"). Manus's version of the same rule is architectural: they never load tools dynamically because swapping tool schemas invalidates the cache and leaves the model remembering tools that no longer exist; instead a fixed set of ~10–20 atomic functions ("under 30") plus two escape hatches — sandboxed shell utilities discoverable with `--help`, and Python packages for heavy computation — so capability grows without the schema changing. That is the "mask, don't remove" rule from Manus's July 2025 post, restated live.

**What it buys.** Agents re-send the whole transcript every turn, so a 50k-token session costs 50k + 51k + 54k + 55k… — quadratic without caching, roughly linear with it (Hugging Face's chart). Cache reads are ~10 % of fresh input on the two most expensive providers (Hugging Face; IBM says "something like 90 % off"); Anthropic's docs (written canon) price cache writes at 1.25×/2× and reads at 0.1×. Hugging Face's own coding-agent session: 10.9M tokens exchanged, 126k window, six cents on a cheap open model routed to one provider — extreme, but the shape (cost dominated by cache hits) is the point. Manus draws the strategic conclusion: at their input-heavy/output-light ratio "flagship models can sometimes be even cheaper than open-source models" once hit rate is counted, and they use only frontier hosted models because distributed KV-cache infrastructure is hard to replicate. **Choose a model on cached-input price and cache infrastructure, not sticker price** — a new row for the provider checklist.

**What it does not buy.** Quality. "Caching doesn't solve the long context problem… it absolutely helps you with latency and cost" (Martin, with Anthropic's confirmation that context rot applies whether or not tokens are cached). AWS: prompt caching "isn't really a context engineering technique because we're not changing what goes into the context window". A high hit rate is not a licence to keep stuffing.

**Operational details worth keeping.** Minimum cacheable prefix ~1,024 tokens (IBM; OpenAI docs); TTLs from five minutes (Anthropic default) to one hour (OpenAI; Anthropic extended) — Hugging Face's session graph shows the cache expiring over lunch and being rewritten at full price; some providers cache automatically on a stable prefix (OpenAI Responses), others need explicit breakpoints (Anthropic), Gemini has an explicit cache object — the speakers themselves were unsure of the current state (Martin: "I'm actually not sure that's the case"), so the KB points at the docs and not at the talk. Measure it: a harness must show cache hit rate per request and per session (Hugging Face's Tau/Pi examples); a multi-turn feature with zero cached tokens has its prompt in the wrong order (already the rule in `principles/10-llm-api-fundamentals.md` §3.4).

### 3.4 CAG, long context and RAG (IBM ×3; Martin; Manus; Airbyte; Liu)

**CAG** (Chan et al., 2024-12) is: prepare a bounded corpus → pre-compute its KV cache once → persist it → answer every query by loading the cache and appending the question. IBM reports the paper's 10×–40× speed-ups over re-processing and states the limits: the corpus must fit the window and must be stable, because any change recomputes the whole cache. IBM's key sentence: **prompt caching is "CAG as a service"** — the provider manages the KV cache for a long, stable prefix — which is why the research idea became usable without infrastructure. The practitioner term "CAG" has not caught on: the scan's "cache augmented generation" query returned only tiny re-explanations of one paper; everyone who builds calls it prompt caching.

**Long context vs RAG — the decision.** IBM's "Is RAG still needed?" gives the cleanest statement of both cases. For long context: collapse the infrastructure (no chunking, embeddings, vector store, reranker, sync); no *retrieval lottery* ("silent failure": the answer existed and retrieval never returned it); and the **whole-book problem** — "which security requirements were omitted from the release?" needs both documents in full; retrieval returns snippets of each and can never retrieve the gap between them. For RAG: the re-reading tax (a 250k-token manual processed on every query, only partly offset by caching and not at all for changing data); the haystack (attention dilutes; top-k retrieval removes the haystack and hands over the needles); and the unbounded set (enterprise data in terabytes will never fit). Verdict shared by IBM, Manus and Airbyte: bounded, stable corpus with global reasoning → long context (+ caching); unbounded or fast-changing → retrieval; and "RAG is not dead, just the way we're doing it" (Tricot) — the failure is thin retrieval without metadata, not retrieval. Jerry Liu's framing that "RAG in 2026" has decomposed into *agent harness + document context layer* (the agent writes its own retrieval queries; parsing PDFs faithfully — tables drawn as line segments, reading order not guaranteed — is the hard, unsolved part) is recorded for the RAG sessions along with his ParseBench numbers, which are his company's.

### 3.5 Conversational architecture and the harness (Chase; Horthy; Arize; Ebbelaar; Google)

**Trace, or you cannot debug.** Chase's line is the reason: "you don't actually know what the context at step 14 will be, because there's 13 steps before that that could pull arbitrary things in." Ebbelaar: bugs invisible in a five-turn dev test appear at turn 10–20 in production and are "almost always" obvious in a full trace. This confirms `principles/21-agent-design-and-tools.md` §3.3 and adds the multi-turn reason.

**Long-session evals.** Arize's fix for failures that only users reported: load ten turns, test the eleventh — a reproducible eval for context management. New to the KB; it goes into the practice's Verify section and is parked as a pattern for the evals sessions.

**Prompt hygiene that is really context hygiene.** Ebbelaar (from Anthropic's post): the system prompt at the "right altitude" — not vague, not a growing if/else list of exceptions — and *positive examples over negative rules*, because prompts accumulate "don't do X" patches from user complaints until they are brittle and bloated; when one prompt covers many workflows, route to sub-prompts or swap system-prompt segments by conversation phase (a state machine) instead of pruning linearly. Google's seven-part "context stack" (instructions, user input, retrieved facts, tools, short-term notes, long-term memory, output format) and its four failure names are the vocabulary the KB adopts.

**Harness decisions, not model decisions.** Chase: compaction strategy is still mostly decided by the harness author; a few labs let the model decide when to compact, not yet common. Deep Agents bakes planning, compaction and file access into the harness. Manus: the harness has been rebuilt five times since March 2025 and the direction is *less* scaffolding as models improve — "build less and understand more" — the same "expect to rebuild the abstraction" the s12 digest recorded from Notion.

**Horthy on plans and docs.** Three things that touch existing principles. (1) *Intentional, frequent compaction* as a working method: turn a noisy 100k-token research session into a ~10k-token verified markdown artifact and start a fresh window with only that — research → plan → implement, each phase a small human-checkable file and a clean context. (2) Those task docs are **throw-away**: his team abandoned keeping research/plan docs in sync with code after two or three months ("tokens are cheap, stale docs cost more than regenerating them"; he knows no one who has made spec–code parity sustainable). (3) Plans should be *vertically sliced* (mock endpoint → real data → error handling, each testable) rather than layer-by-layer, and a plan that lists every diff doubles review time without adding leverage. (2) sits against `principles/04-spec-driven-development.md` — see §5. Also first-person and worth its own line: his fully autonomous "lights-off software factory" ran July–November 2025 and was shut down when a primary-key type bug took three weeks to root-cause in code nobody had read; "slow loops" (a nightly job that fixes one lint class and opens one small, reviewed PR) replaced it.

### 3.6 Context quality and the data layer (Airbyte; Google; Martin)

Airbyte's episode is a product pitch for a synced, indexed "context store" that agents query instead of raw SaaS APIs; the demo numbers (~30,000 fewer tokens and one minute instead of three for a user-filtered Gong query, because Gong's API cannot filter by user and the agent paginated everything) are the vendor's, against a strawman it built. The mechanism is nonetheless real and generalises: **when an upstream API cannot filter the way the question needs, the agent pages the whole set through its window** — pre-index or pre-filter outside the model. Google names the failure this produces (*confusion*) and Breunig's *poisoning* is the one nobody has a rule for: Manus and Martin prefer to leave tool errors in context so the model self-corrects; Breunig documents the Gemini 2.5 Pokémon report where a lodged hallucination derailed the run. Recorded as contested.

## 5. What is contested / trade-offs

- **Summarisation: viable or not?** AWS and LangChain ship it (with a preserve-list, a recency window and a cheap model); Arize tried it and replaced it with head+tail truncation and a retrievable middle; Manus does reversible compaction first and summarises only from the full record with a schema. Resolution recorded: unconstrained free-form summarisation is not production-viable; reversible compaction is always safe; summarisation is acceptable when schema-constrained, recency-exempt and fed the full record.
- **Leave errors in or prune them?** Self-correction (Manus, Martin) vs poisoning (Breunig). No consensus; test both for the specific agent.
- **Living docs vs throw-away docs.** Horthy: task research/plan docs are regenerated per task and discarded; spec–code parity is unsustainable. `principles/01-context-engineering.md` and `04-spec-driven-development.md` keep *standards and conventions* documents alive. These reconcile by kind of document: durable *how-we-work* docs (conventions, architecture, definition of done) stay alive and short; per-task *research and plan* docs are ephemeral compaction artifacts. `04` gets a change-log line saying so; nothing is superseded.
- **Harness decides vs model decides.** Compaction triggers and strategy are still harness-author decisions (Chase); the trend is toward the model deciding and toward less scaffolding (Manus). The KB states the current rule and dates it.
- **Multi-agent.** Cognition's "don't" and Anthropic's "works" reconcile by task shape (read-only fan-out yes; coherent writing no). Recorded in `21` and `06`.
- **Vendor interest.** Every long talk except Horthy's and Ebbelaar's positions a product; the KB keeps mechanisms confirmed by at least two independent sources and marks every number as the vendor's.
