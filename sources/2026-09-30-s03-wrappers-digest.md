## 2. One-paragraph summary

Everything a product puts between its code and the model providers — the market calls it an **LLM gateway** or a **wrapper layer** — exists to manage one trade-off that cannot be maximised on all sides at once: **availability, latency, guardrails and cost** (Twilio). The settled practices: route to the *next deployment* on failure rather than retrying the same endpoint, because LLM calls are slow and expensive and retries burn the latency budget; keep **one owner of retries** — ManyChat found router retries × agent-framework retries = 16 attempts per call, synchronised in waves that delayed recovery; put failing providers in **cooldown** (LiteLLM's `allowed_fails` / `cooldown_time`, Writer's five-minute latch) instead of a classic circuit breaker; set **timeouts per model class and route**, because "a reasoning model's normal is a chat model's outage" and a missing timeout is the top cause of silent outages; **provision and test the fallback** at primary volume, since fallbacks are not transparent — tool-calling formats, token limits and stop reasons differ across "OpenAI-compatible" providers, a different *model* needs its own evals, and "available is not approved" (a fallback must be pre-decided against data sensitivity and capability, never chosen mid-incident); design **tiered capacity** (ManyChat: reserved 80 % + pay-as-you-go 20 % + direct providers at weight 0, 300 RPS sustained at ~1.5× baseline cost); **bound queues and shed load**, because provider quota is rented, not owned — "we don't scale it, we route it with what we have". **Streaming** forecloses most of those levers: once tokens reach the client you cannot switch provider, so the safe fallback point is *before the first token* (Writer waits for the first token to classify error vs response), SSE is the default edge transport (stateless, auto-reconnect; gRPC stays internal; WebSockets only for client→server streams), and a stream is a pipeline of stages — timeout, token counting, guardrail buffering, SSE decode, `finish_reason` check — with the `[DONE]` sentinel distinguishing a finished stream from a dropped connection. **Traceability** is distributed tracing: an LLM call is a span (`gen_ai.operation.name`, `gen_ai.request.model`, `gen_ai.provider.name`, `gen_ai.usage.input_tokens` / `output_tokens` / `cache_read.input_tokens`, `gen_ai.response.finish_reasons`; prompt and completion content opt-in), a pipeline is a trace, and the dev loop is trace → replay in a playground → edit → re-run; start with traces and add evals, keep LLM-judge scores out of pager alerting, pseudonymise user ids, redact secrets that decorators capture by default, and expect the OTel conventions to keep moving (status *Development*). **Semantic caching** sits above provider prompt caching, returns someone else's answer to a similar question, and is therefore safe only for stateless, non-personal, slow-changing content behind a conservative threshold (90–95 %), a TTL and tenant/domain/model-version filters — the demo's 85 % threshold and "aim for 80 % hit rate" are the vendor's. Two architectural tensions stay open: *central* gateway (one place for credentials, caching, accounting; TensorZero, OpenRouter) versus *centralised governance with decentralised traffic* (Twilio: a central gateway is a single point of failure), and whether the gateway is also the place to make every LLM call a *typed, optimisable function* (TensorZero's thesis, unbenchmarked). And a quiet lesson from the smallest case: a retired model hardcoded in 22 places broke a production button although the retirement had been announced — "information is not control" — so a **model registry with a daily availability check** is part of the layer.

## 3. Detailed digest

### 3.1 What the layer is for (Twilio; TensorZero; 12-Factor; OpenRouter)

TensorZero's definition is the cleanest: a gateway is a server (or a library) between application code and model providers that handles the provider-interface mismatch, retries, fallbacks, load balancing, credentials, caching, accounting and observability — "one endpoint instead of five SDKs". Twilio's framing is the trade-off: availability, latency, guardrails and cost pull against each other and, during a degradation, you choose which to sacrifice. 12-Factor Agents gives the layer's *design stance*: own your prompts (eventually "you're going to end up writing every single token by hand"), own your context window, own your control flow; tools are "just JSON and code" dispatched by a deterministic switch; the agent is a stateless reducer over a serialisable state you own; small focused agents (3–10 steps) inside mostly deterministic code. This is the same thin-wrapper stance `principles/10-llm-api-fundamentals.md` §3.5 took for the client module — the gateway is that module grown to serve several services and several providers, no more. OpenRouter's episode adds the market view: a gateway's value is reaching every model with one integration on launch day, and provider competition on the *same* open-weight model (prices fell ~80 % after Mixtral) — the "swing": frontier launch → usage surge → invoices 30 days later → cheaper open-weight option ~3 months later — so model choice is re-evaluated quarterly and never hardcoded into product logic.

Two tensions, recorded rather than resolved. **Central vs decentralised**: TensorZero and OpenRouter describe one central place (credentials, provider caching opt-ins, accounting, data-policy enforcement); Twilio argues that most teams want *centralised governance, not centralised traffic* — a company-wide gateway is a single point of failure, so run the gateway as a library or per-team deployment with plugins that centralise cost tracking and rate-limit management. Both are compatible with "one team owns it; many instances run it". **Gateway as optimisation platform**: TensorZero's thesis is that every LLM call should be a typed function (input/output schemas, variables stored structured rather than as rendered prompt strings) so that prompt/model *variants* can be A/B-tested, fine-tuned and optimised later; stated as a hypothesis by its CTO, with no benchmark, and admitted to be "the hardest to use". The KB keeps the *storage* half (store the structured inputs and the prompt version, not only the rendered string — it is what makes replay and later fine-tuning possible) and parks the optimisation half.

### 3.2 Fallback, retries, cooldown, timeouts (Twilio; ManyChat; LiteLLM docs; Writer; API World)

- **Fallback over retry.** For an LLM call, retrying the same endpoint consumes the latency budget and multiplies cost and tail latency; try provider A then B. Parallel fan-out (same request to two providers) doubles cost and is for the "highly obsessed with latency" (Twilio). ManyChat: "increasing retries doesn't work in this use case".
- **One owner of retries.** ManyChat configured 3 retries + the first try at the LiteLLM router *and* retries in the agent framework: up to 16 attempts per call, synchronised waves that delayed recovery. Rule: audit every layer (SDK, framework, router, gateway) and keep one retry owner; add jitter; cap retries as a percentage of normal flow; 429 waits longer (`retry_after`), 400 never retries.
- **Cooldown, not circuit breaker.** A deployment that crosses `allowed_fails` in a minute is taken out of the pool for `cooldown_time` seconds and then re-tried (LiteLLM; Twilio; ManyChat's healthy → cooldown → timeout → healthy; Writer's ~5-minute latch). Where the failure counters live is a design choice: per-instance counters shift the failover threshold silently under autoscaling; shared counters (Redis in LiteLLM) fail over faster at the price of shared infrastructure.
- **Timeouts per model class and route.** Without one "your gateway thinks your request is being happily served while it is not". Chat ~3 s, embeddings < 1 s, reasoning 2–60 s on the same prompt; p99 jumped to 60 s "for no good reason" — so pin the reasoning-effort parameter per route and treat auto-select models as latency risk; hedging (a second request once the first has used p90 of its budget) is Twilio's untested idea.
- **Fallbacks are not transparent.** Tool-calling schemas, token limits, stop reasons, JSON-mode support differ (TGI has none; TensorZero fakes it with a forced tool call); Anthropic rejecting two consecutive user messages surfaced through LiteLLM as an opaque 400. So: log the raw provider request/response and error body at the gateway, and run the same eval through every fallback target. ManyChat's fallbacks are the *same model* via other capacity; a different model "needs an evaluation system" — the tier they discussed and did not build. API World: "available is not approved" — a fallback is pre-decided against data sensitivity, consequence, capability and cost, never chosen mid-incident; changing the model changes the product (behavioural drift).
- **Provision the fallback at primary volume.** Teams test the primary and neglect the last line of defence; check its quota and rate limits at peak (Twilio).
- **Tiered capacity** (ManyChat, concrete and cost-efficient): reserved Azure capacity sized slightly above baseline at 80 % weight; Azure pay-as-you-go at 20 % (kept warm so the path is known to work); direct OpenAI and Anthropic at weight 0, used only on 429 or failure. Result: a 10× viral spike (≈30 → 300 RPS) sustained at ~1.5× baseline cost and no pages. LiteLLM's `routing_strategy` options (simple-shuffle default, weighted, rate-limit-aware, latency-based, least-busy) and `max_parallel_requests` derived from rpm/tpm are the knobs.
- **Route, don't scale; bound the queue; shed load.** Provider quota is rented; pods do nothing against 429s. Excess has three destinations: queue, raise the cap (cost), or drop by priority. ManyChat used an unbounded queue plus an in-flight semaphore and admitted it "wouldn't work for sustained overloads" and had no way to cancel abandoned requests — bound the queue and attach a deadline (Twilio).
- **Keys per route and per tenant** so one noisy tenant cannot exhaust everyone's quota (Twilio); per-key spend caps and anomaly alerts because "if you're making a gateway you are a target for fraud" and runaway agents hit the bill the same way (OpenRouter).
- **Model lifecycle.** A model hardcoded in ~22 places, a retirement that Anthropic had announced, no alert, a broken production button. Fix: one source of truth for model ids, a daily scan of the provider's model list against the models in use, an alert on mismatch *and* on failure of the check itself; re-audit older systems (the new portal was fixed, the old one broke) (API World).

### 3.3 Streaming through the layer (Writer; CNCF panel; OpenAI Build Hour reused; Twilio)

SSE is the stated default for token streaming to browsers — text over HTTP, unidirectional, auto-reconnect, stateless so a reconnect lands on any server; WebSockets need stateful scaling and are for client→server streams (voice, collaboration); gRPC bidirectional streaming stays *internal* (service ↔ vector DB ↔ model) because browsers cannot read trailers and gRPC-Web needs a proxy; Protobuf for service contracts, JSON wherever a model must read the payload (CNCF). Parse SSE correctly: `data: <json>` lines can be split across network chunks, so buffer and reassemble; `[DONE]` distinguishes a finished stream from a dropped connection (Writer). The gateway's stream is a pipeline of stages — timeout, token counting and metrics, **buffering for guardrails** (token-level filtering is meaningless, and buffering delays first visible output: a per-route decision), SSE decode, `finish_reason` check (Writer). Build clients on typed events, not regex over text deltas (OpenAI, s1). **Fallback inside a stream**: wait for the first token to classify error vs response, then commit; after tokens were shown, restarting on another provider needs a product decision (discard or splice) that nobody has a clean answer for — Twilio: this is why "something went wrong, please try again" exists. Guardrails that run *in parallel* with generation do not combine with streaming; pre-hooks add serial latency; post-hooks suit auditing — placement is a per-route attribute (Twilio). Streams are opaque to WAFs, so injection checks belong in the application layer (CNCF). HTTP/3 and WebTransport are coming but enterprise firewalls drop UDP; the pragmatic choice stays SSE over HTTP/2 through the CDN.

### 3.4 Traceability (Langfuse; Mastra panel; PyCon DE; OTel spec; Ebbelaar reused)

"LLM observability isn't a different problem from distributed tracing — it's a special case of it" (Langfuse). An LLM call is a span; a pipeline is a trace; propagate `traceparent`. The OTel GenAI conventions (read from the spec, status **Development** — expect names to move): span name `{gen_ai.operation.name} {gen_ai.request.model}`; required `gen_ai.operation.name`, `gen_ai.provider.name`; `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.response.id`, `gen_ai.response.finish_reasons`, `gen_ai.conversation.id`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.usage.cache_read.input_tokens`, `gen_ai.usage.cache_write.input_tokens`, `gen_ai.usage.reasoning.output_tokens`, `gen_ai.request.reasoning.level`, `gen_ai.prompt.version`, `gen_ai.tool.*`; content attributes `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, `gen_ai.tool.definitions` are **Opt-In**. Practice from the founders' panel and the PyCon demo: start with traces, then evals; offline evals are unit tests, online evals are monitoring, and production cases feed the offline set; the P0 workflow is trace → replay in a playground with the full prompt, tool definitions and inputs → edit → re-run, so the trace store must capture all of it; sampling is rare, retention is the cost lever ("you need to be really big to sample"); page on deterministic expectations (a checkout that must happen) with ordinary alerting, never on LLM-judge scores; filter infrastructure spans; put a session id and a *pseudonymous* user id on the root span; a gateway can trace only its own segment unless callers forward `traceparent`; multi-agent tracing is distributed tracing. One concrete hazard from the demo: `@observe` records every function argument by default, so passing a client object leaks the API key into the trace store — audit what auto-instrumentation captures and redact. OTel does not make you vendor-agnostic by itself ("still a lot of monkey-patching"), but it lets you switch backends with a mapping layer.

### 3.5 Semantic caching (Percona/Valkey; Redis canon; Lance Martin reused)

Mechanics: embed the query (384–768 dims), vector-search stored queries, return the cached answer above a similarity threshold, else call the model and store; controls are threshold, TTL, metadata filters, the embedding model and the index. Demo numbers (laptop, vendor): miss ≈ 6.5 s, paraphrase hit ≈ 180 ms at 97 % similarity, another at 90 %; the demo threshold of 85 % would return "a different question's answer" on the speaker's own example (Python the language vs the snake), and a 95 % threshold would have missed the legitimate 90 % paraphrase — the useful band is narrow and per-domain. What the talk understates and the KB states: a semantic-cache hit is **someone else's answer** — unsafe for personalised, tenant-scoped, time-sensitive or tool-using responses, and a cross-user cache without tenant keys leaks one user's context into another's; safe for stateless FAQ-style content with tenant, domain, language and model/prompt-version in the filter and a short TTL for anything that changes. It sits *above* provider prompt caching (`principles/11-runtime-context-management.md` §3.3), which caches the prefix of *your* request and never returns another request's answer. ManyChat built its own response cache and uses cached responses in test pipelines because live LLM tests are flaky — the one caching use nobody argues with.

### 3.6 The conversational-interface bullet (written canon only)

No video was selected for Streamlit; the Streamlit chat docs (`st.chat_message`, `st.chat_input`, session state, streaming) and Gradio's `gr.ChatInterface` are the canon and the DeepLearning.AI course the tutorial. The one rule the module adds: the UI holds **no model logic** — it renders typed events from the layer and keeps session state; swapping Streamlit for a web front end must not touch a prompt.

## 5. What is contested / trade-offs

- **Central gateway vs centralised governance.** TensorZero/OpenRouter: one place. Twilio: single point of failure; centralise governance (cost, limits, keys) through plugins, decentralise traffic (library or per-team deployment). The KB records both; for Martin's shapes (one person, a handful of products) the library-in-each-service form with one shared config repo is the fit, and the practice says so as an opinion.
- **Same-model vs cross-model fallback.** Same model via other capacity is transparent (ManyChat); a different model needs evals (ManyChat, API World, TensorZero, Twilio all say it, differently). Rule: cross-model fallback is a *pre-approved, pre-evaluated* route, never an automatic one.
- **Retries at all?** All four gateway speakers say blind retries hurt; ManyChat still keeps a small router retry with jitter. Rule: one owner, small cap, jitter, class-aware (429 ≠ 400).
- **Gateway as ML platform.** TensorZero's typed-function thesis is kept as storage discipline and parked as optimisation.
- **Semantic cache.** The vendor says "a few lines of Python"; the same talk's examples show why the threshold is a product decision. Recorded as narrow-scope.
- **"OTel-native".** Langfuse's own video says it; the founders' panel and the PyCon talk say it came late and the conventions are immature. Recorded as: use OTel, pin versions, expect a mapping layer.
- **Vendor interest.** Every number from a vendor is marked; mechanisms are kept only with a second source.
