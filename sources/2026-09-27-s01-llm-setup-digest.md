## 2. One-paragraph summary

Everything in this module rests on one mechanical picture that Karpathy gives best: a model is a next-token predictor with a *fixed amount of computation per token*, whose knowledge is a *lossy compression* of its training text ("a vague recollection") and whose only reliable memory is the *context window* ("the working memory"). Almost every practical rule follows. Put the document in the context instead of asking the model to remember it. Make the model spend tokens before answering anything multi-step — as explicit "show your work" on ordinary models, or through the native thinking/reasoning budget on reasoning models, which are trained by reinforcement learning on *verifiable* answers and therefore help most where an answer can be checked (code, maths, schema-bound extraction) and least on open-ended writing. Route character-level tasks, arithmetic and fresh facts to tools, because tokenization hides characters and parameters hide nothing reliably. Treat fluency as no evidence of truth: LLMs are "plausibility engines" (Klein), prompting is "not a control surface with precise semantics", and stacking one model to check another does *not* compound reliability because their failures are correlated — guarantees belong in code, schemas and deterministic checks, and reliability is measured as "100 out of 100 runs on this scenario", not as an aggregate pass rate. On the API itself, both large vendors have converged on the same shape — an *agentic loop* where you send a list of typed items (messages, tool calls, tool results, reasoning) and receive typed items back — with state kept either by resending the list or by a server-side handle, hosted tools and remote MCP servers callable from the request, reasoning carried across turns, versioned prompt objects, and *prompt caching* that only works if the stable part of the prompt comes first. Prompting is an engineering activity: a fixed structure (task context → tone → background → rules → examples → history → immediate task → thinking → output format), written as clear communication to "a competent temp with no context", iterated against real inputs and edge cases, tested for sycophancy with neutral framing, and versioned like code. Provider choice, finally, is less about which lab is smartest this quarter than about API shape, caching, structured outputs, tool support, data-retention options and a thin client wrapper of your own so that switching is a config change and not a rewrite.

## 3. Detailed digest

### 3.1 What a model is, and what follows for an engineer (Karpathy 2023-11, 2025-02; Klein 2026-04)

**Two files.** A model is a parameters file and a few hundred lines of inference code; producing the parameters costs months and millions, running them is cheap. Nobody building a product retrains a frontier model; the only costs to architect around are inference cost and latency (Karpathy, intro talk).

**Compression, not a database.** Pretraining compresses internet text roughly a hundredfold into weights. What comes out is a "gestalt", not exact facts, and the model cannot tell from the inside whether it is recalling or confabulating. Knowledge is also one-directional (the "reversal curse": knows who Tom Cruise's mother is, cannot answer the inverse). Consequence: any fact, identifier, date or number that matters must be *in the context* (retrieved, pasted, returned by a tool) or verified by a tool — never taken from parametric recall. Karpathy demonstrates the difference with *Pride and Prejudice*: summarising chapter 1 from memory versus with the chapter pasted into the prompt gives a materially better result the second time, even for a text the model has certainly "read". His phrasing is the one to keep: *knowledge in the parameters is a vague recollection; knowledge in the tokens of the context window is the working memory.*

**Tokens, not characters.** Byte-pair encoding with a ~100k-symbol vocabulary means the model never sees letters, only opaque multi-character chunks. This single fact predicts a whole class of failures — counting letters, exact substring manipulation, precise spelling — which Karpathy demonstrates live ("how many Rs in strawberry", counting dots). The fix is not a cleverer prompt but a code-execution tool, which resolves the same tasks reliably.

**Fixed compute per token — "models need tokens to think".** Each output token gets the same, bounded amount of computation. Asked for the answer to a moderately hard arithmetic problem "in one token", the model is wrong; asked to show intermediate steps, it is right, because the calculation is distributed over many tokens. This is the mechanical reason chain-of-thought works and the reason never to ask for a bare final answer on a multi-step problem when reliability matters more than latency. (How this reconciles with Andrew Ng's "think step by step is obsolete" is in §5.)

**Swiss cheese.** Capability is not monotonic in difficulty: a model that solves graduate-level problems can insist that 9.11 > 9.9. Test the cases that matter empirically; never infer "easier, so surely fine".

**Three training stages, and what "reasoning model" means.** Pretraining (document completer) → supervised fine-tuning on labelled conversations (assistant behaviour, imitation of human labellers) → reinforcement learning. Karpathy's key distinction: RL on *verifiable* rewards (maths, code with tests — the DeepSeek-R1 recipe) produces the long, self-correcting "wait, let me re-check" chains that define a *reasoning/thinking model*; RLHF on a learned reward model approximating human preference is "not RL in the sense that it lacks magic" — the reward model is gameable, so RLHF is run for a bounded number of steps. Product consequences: (a) reasoning models cost more tokens and latency and pay off where the answer is checkable; (b) any pipeline that optimises against an LLM-as-judge signal will be reward-hacked if pushed, so prefer ground-truth checks (tests, exact match, calculators) wherever the task allows; (c) closed vendors show only a *summary* of the chain of thought, so do not build a product on reading the model's literal reasoning. Karpathy's own routing: a fast non-reasoning model for 80–90 % of everyday queries, a thinking model for hard maths/code/logic.

**Base models and identity.** A raw base model continues documents, it does not answer; it needs instruction tuning or a transcript-shaped few-shot scaffold. And "what model are you?" is itself a hallucination unless the answer is put in training data or the system prompt — a product that needs the model to state its version, cutoff or capabilities must inject them.

**Hallucination mitigation as recipe.** Meta's approach (interrogate the model several times per fact, judge against ground truth, add "I don't know" training examples where it is confirmed not to know) is described concretely; the API-side equivalent is retrieval or a search tool that refreshes the working memory instead of guessing, plus "give the model an out" in the prompt (also Anthropic's roundtable, §3.3).

**Plausibility, not truth (Klein).** "We have built not truth engines, not reliability engines, we've built plausibility engines." Three structural claims worth keeping. (1) *Prompting has no semantics*: there is no compiler-like guarantee that a wording produces a behaviour, unlike a function contract, so where a guarantee is needed — money, irreversible actions, policy-bound answers — enforce it outside the model with schema validation, business rules and tool restrictions. (2) *Failures are correlated*: putting a second model to check the first does not multiply reliabilities as if independent ("80 % checking 80 %" lands near 82 %, not 96 %), and multi-turn conversations compound per-turn error; an LLM judge is a useful signal, never the only guard. (3) *Measure consistency, not pass rate*: what ships is "for how many of these scenarios will I get it right every time, 100 times in a row", so run each test case N times and look at the worst case. He also names the "iceberg": detected hallucinations are the fluent-enough-to-notice tail; "looks right and is right are not the same". The second half of the episode is a pitch for his company's action-based model and is sponsored by an evals vendor; none of it is used here.

### 3.2 The structure of a call (OpenAI Build Hour 2025-10; Anthropic MCP + Claude API 2025-10; Witteveen 2026-01)

**Two vendors, one shape.** OpenAI's Responses API and Anthropic's Messages API have converged on an *agentic loop as the unit of the API*: the request carries a list of typed **items** — user and assistant messages, tool calls, tool results, reasoning — and the response is a list of typed items back (OpenAI calls them items and output items; Anthropic calls them content blocks). Chat Completions' "one string in, one string out" is legacy. A developer's mental model of a call should therefore be: *system instructions + a list of items + tool definitions → a list of output items, some of which are tool calls I must execute and append before calling again.*

**State: three options (OpenAI).** Keep the whole item list yourself and resend it (stateless, portable, what Anthropic requires); or pass `previous_response_id` and let the server chain (stateful, less to ship, vendor lock); or use a server-side *conversation object*. For stateless or zero-data-retention deployments, OpenAI returns **encrypted reasoning items** so the model's reasoning can still be carried across turns without the server storing it.

**Reasoning persists across turns.** Passing reasoning items back into the next call is reported to raise tool-use accuracy (+5 % on an internal ToolBench-style eval per the Build Hour) and cut latency (~20 %) because the model does not re-derive its plan. Vendor numbers, unverified; the *pattern* — keep the model's own reasoning in the loop — is what to keep, and it is the same lesson as `principles/21-agent-design-and-tools.md` §3.3 "think like your agent".

**Hosted tools and remote MCP in the request.** Web search, file search, code interpreter and computer use are hosted tools the vendor runs server-side; remote MCP servers can be attached to a request with `allowed_tools` (restrict) and `require_approval` (human gate per tool). Anthropic's session shows the equivalent MCP connector in the Claude API. Both confirm the KB's tool rules: the tool list *is* prompt ("tools are prompts" — Anthropic), servers should expose few, well-described tools, and stuffing many servers into one request pollutes the context (`principles/21-agent-design-and-tools.md` §3.4–3.5, `practices/token-savings/mcp-audit.md`).

**Streaming is typed events.** Not a text delta stream but semantic events (item added, text delta, tool call arguments delta, item done). Build clients on the event types, not on regex over deltas.

**Prompts as versioned objects.** OpenAI's dashboard prompt objects (id + version + variables) let a prompt be edited, versioned and referenced from code by id. Whatever the vendor, the durable rule is: prompts are versioned artifacts with a changelog, not string literals scattered in the codebase.

**Prompt caching is prefix caching.** Caching applies to a stable, *append-only prefix*; anything variable placed early breaks the cache for everything after it. Order the prompt static-first (system instructions, tool definitions, reference material, few-shot examples) and dynamic-last (conversation, the current user input). Cursor's short explainer states the billing side: input tokens, output tokens and *cached* input tokens are priced differently, output tokens costing several times input, cached tokens a fraction of input.

**Few-shot still works** under the new API shape; nothing in the loop model removes examples as a lever (OpenAI).

**Standards (Witteveen).** Open Responses is an attempt to make the Responses shape an open standard for open-weight model servers; Witteveen's observation is that each lab now owns its API shape, and that the Claude Messages API had become a de facto compatibility target for third-party servers by early 2026. For a developer this is a *provider-selection criterion* (which shapes does my client have to speak?) and an argument for a thin in-house wrapper rather than a heavyweight abstraction framework.

### 3.3 Prompting as an engineering activity (Anthropic Prompting 101 2025-05; Anthropic roundtable 2024-09; JetBrains 2026-02; Andrew Ng 2026-05)

**The fixed structure (Prompting 101).** Anthropic's recommended order for a production prompt, each part a labelled section, XML tags where it helps: (1) task context / role, (2) tone, (3) background data and documents, (4) detailed rules and instructions, (5) examples, (6) conversation history, (7) the immediate task or request, (8) thinking instructions ("think step by step before answering" or extended thinking as a scratchpad), (9) output format, (10) prefilled start of the answer. Ordered steps beat prose paragraphs; put reminders of the most important rules near the end; ask for the output format explicitly.

**Prompt engineering is clear communication plus iteration (roundtable — Zack Witten, Amanda Askell, David Hershey, Alex Albert).** The durable advice: *read the outputs* — many people never look at what the model actually returned; iterate hundreds of times on a prompt; test on *real* inputs and *edge cases* (typos, empty input, off-topic), not on the ideal case; write for a "competent temp-agency person with no context about your company" rather than role-playing an identity the model does not need ("you are a teacher" adds little when the task is stated plainly); *give the model an out* ("if none of these apply, say so") so it does not force an answer; give it the actual paper or spec rather than a paraphrase; distinguish *illustrative* examples (show the shape) from *concrete* examples the model will copy too literally; enterprise prompts must cover the *range* of inputs, not the median; ask the model to critique the prompt or to rewrite it, and use its own words back. Askell's line — prompting is "externalising your brain" — is the reason a prompt should read as a complete, explicit briefing.

**JetBrains** repeats the developer version in four minutes: give context, state constraints, show an example, iterate. Confirmation only.

**Andrew Ng's course** adds, at the level of a general-audience course but with concrete demonstrations: (a) **sycophancy** is trained in (preference optimisation rewards agreement; he cites a study of ~10× more agreement than disagreement) and is suppressed by neutral framing and factual criteria instead of "don't you think…?" — testable by A/B-ing leading versus neutral phrasings of the same question; (b) **rubric-based grading** with explicit, near-binary criteria scored independently gives lower and more discriminating scores than "score this out of 100" (his demo: 100/100 vs 75/100 for the same text), because a holistic score is decided first and rationalised after; (c) **cross-model review** gives a small, real boost over self-critique, no more — modest, not load-bearing; (d) **staged generation** (outline → critique → expand) and **piecewise editing** beat whole-document rewrites, because an outline edit is high-leverage and a full rewrite is unreviewable; (e) irrelevant leftover context degrades answers and is hard to detect afterwards — start a new thread on a topic change; (f) "think step by step" belongs to 2022–2023 and reasoning models respond better to "think hard"/thinking mode — see §5 for how this squares with Karpathy; (g) web-search grounding cites what is *most available* (Reddit, Wikipedia, forums) unless steered to authoritative sources, and the answering model reads a second model's *summary* of pages, not the pages — citations are unverified until checked; (h) "deep research" is a multi-round search → judge relevance → search again loop, not one retrieval call; (i) fine-grained vision (equipment IDs, meter readings, handwriting) needs a verification step; (j) image and video generation are orders of magnitude costlier and slower than text, so "generate five options" does not transfer to them. Items (g) and (h) belong to the RAG sessions and are parked; (i) and (j) are outside this module and skipped.

### 3.4 Tokens and the context window (Cursor 2025-09; Pocock 2025-10; Ng; Karpathy)

A token is roughly three quarters of an English word; pricing is per million tokens, separately for input, output and cached input (Cursor). The context window is a hard per-model limit, and everything competes for it: system prompt, tool definitions, conversation history, attached files, tool results (Ng, Pocock). Quality degrades before the limit is reached — "lost in the middle": material in the middle of a long context is recalled worse than the start or the end (Pocock, citing the paper). In coding agents, Pocock's practical rules are: know the window of the model you use, `/clear` between unrelated tasks rather than letting `/compact` summarise away what mattered, and audit MCP servers because their schemas load on every turn. Ng's independent version of the same rule for chat products: switch threads on a topic change. Karpathy's "RAM" analogy (context = working memory, finite and precious) is the frame all of them share, and it is already the frame of `principles/01-context-engineering.md` and `07-token-economy.md`.

### 3.5 Providers, stacks and architectures (IBM 2025-11; Witteveen; Build Hour; Karpathy)

IBM's "AI stack" is a five-layer taxonomy — infrastructure, model, data, orchestration, application — useful vocabulary for a conversation, not a decision aid; it adds no rule and is not adopted. Karpathy's provider guidance (hosted labs for frontier models; leaderboards such as LM Arena with the caveat that they were "somewhat gamed" by early 2025 — his opinion; LM Studio and similar for local open-weight models) is dated by nature. What the scan *did* yield as durable selection criteria, assembled from the vendor sessions and Witteveen, is a checklist an engineer can actually apply: which API shape(s) the provider speaks; model tiers and whether a reasoning tier exists; prompt caching and its rules; structured outputs / JSON schema enforcement; tool calling and hosted tools; MCP support; state options and zero-data-retention / encrypted reasoning; rate limits and regions; price per million tokens by class; and how much of your code would change if you swapped — which is the argument for the thin wrapper. Consumer "$20 plan" comparisons, of which the search returned nine, answer none of these questions.

## 5. What is contested / trade-offs

- **Chain of thought: obsolete or essential?** Ng says explicit "think step by step" is 2022-era advice replaced by "think hard" on reasoning models; Karpathy shows mechanically that a model *must* spend tokens to compute a multi-step answer. Both are right at different layers. On a reasoning model, use the native thinking/effort parameter and do not hand-scaffold steps; on a non-reasoning model, ask for the work to be shown before the answer; on either, never require a bare final token for a multi-step problem when reliability matters. Klein adds the third axis: extra reasoning pays where the answer is *verifiable*, and is "totally unnecessary" on open-ended tasks.
- **Stateful or stateless API?** Server-side state (`previous_response_id`, conversation objects) is less code and enables cross-turn reasoning without shipping it; resending the item list is portable across vendors and satisfies zero-data-retention. OpenAI's encrypted reasoning items exist precisely to soften this trade-off. The KB's stance: default to owning the item list (portability, auditability), adopt server state deliberately and per feature.
- **Multi-model review.** Ng: small real gain from a different-family grader; Klein: correlated failures mean stacking models barely helps and multi-turn compounds error. The KB records the skeptical reading: an LLM judge is a signal to combine with deterministic checks, never the sole gate for anything irreversible.
- **Vendor interest.** Both platform sessions steer toward the vendor's hosted tools, hosted state and dashboard prompts; the roundtable steers toward long, careful prompts for Claude. All of it is used as *what the vendor recommends for its own product*, with the portable pattern extracted.
