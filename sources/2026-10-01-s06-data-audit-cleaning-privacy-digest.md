## 2. One-paragraph summary

Every parsing source says the same thing from its own seat: **the inputs are now the bottleneck** — "the risk of bad inputs becomes really, really pervasive in your pipeline" once agents chain decisions (Abraham), "better document parsing always gives you better downstream task accuracy" (Reducto), "the real challenge in RAG or agentic AI isn't building the agent, but curating the knowledge and the context behind it" (IBM). A PDF is "a bunch of machine instructions that help… print characters for display purposes" (Liu), so reading one is a layout problem first; the 2026 pipeline is **layout detection by small models → the right model per region → an element-typed document with provenance (page, bounding box) → a format per consumer** (Markdown for text, HTML for complex tables, a natural-language rendering for the embedding model), with the frontier VLM a tool on hard regions, never the parser of a million pages (Reducto; Liu; Docling). The audit bullet is assembled from Ng's doctrine (consistent labels, representative inputs, cleaning as iteration), Gambill's control plane (data contracts, gates, "gold data is not automatically AI approved data", lineage, deletion proof) and the vendors' one rule — benchmark parsers on **thousands of your own documents**, never "five documents" (Reducto). Privacy is carried by the written canon: **PII filtering before anything is embedded, indexed, cached or copied** (Gambill; Huyen), masking with a reversible placeholder dictionary (Huyen), Presidio as a detector that gives "no guarantee" of finding everything, the EDPB's three-criteria anonymity test, and **Row Level Security in the database rather than a `WHERE` clause**, because "RLS is always applied even as new queries and application logic is introduced" (Supabase) — the data-layer form of "no side door access" (Gambill).

## 3. Detailed digest

### 3.1 The framing — why data is the problem the module is about

Abraham (Reducto, 2026-09): the shift "from just like information synthesis products to actual agents doing work" changes the cost of a bad input — a chatbot answers one question wrong, an agent "making multiple decisions that compound over the course of a source of files" propagates it. Enterprise data "is unstructured, it is scattered, and it is multimodal", and "you don't necessarily know what is in your corpus of information" — the sentence this digest takes as the definition of the audit problem. Liu (2026-05): "the core kind of alpha of like any AI agent system these days is basically the context that you feed it". Barnett et al. (abstract, 2024-01) supply the engineering lesson the vendors agree with: "validation of a RAG system is only feasible during operation, and… the robustness of a RAG system evolves rather than designed in at the start" — the pipeline is measured in production, `14-evals-and-error-analysis.md`'s production sample applied to ingestion. Liu (2024): "rag is really only as good as your data… garbage in, garbage out"; ingestion is "a new type of ETL… on top of your unstructured data".

### 3.2 Auditing and cleaning — Ng's doctrine, Gambill's gates, the vendors' one rule

**Data-centric AI (Ng, 2022-07; supervised CV, carried as doctrine).** "Data centric AI is the discipline of systematically engineering the data used to build an AI system" (captions write "entering"); hold the model fixed, iterate on the data. A good dataset has "consistent and accurate labels", inputs "representative of the data distribution and… high quality", and reflects "post deployment changes". Three mechanisms transfer to an LLM corpus: (1) inconsistent labels mean "I didn't write clear enough labeling instructions" — the team-edited **label book** has "some of the highest ROI" of anything a team does (the s5 coin-flip-agreement finding, from the other direction); (2) **agreement-based labeling** — several labelers on the same items "for the purpose of surfacing where exactly are the disagreements", then **slice** to the problem subset; (3) cleaning is "a core part of the iterative process", not "a core pre-processing step that you do once" — collect "a lot more pictures of scratches", not more of everything. For ingestion: re-run the audit after every parser or source change; let trace errors decide what is re-parsed.

**The control plane (Gambill, 2026-06).** "The data plane executes work. The control plane decides what work is actually allowed to happen." Five control-plane jobs — execution authority, data trust, security and compliance, cost and reliability, **AI usage policy** — and the line between "land the data first, we'll clean it later" and "some data should not be allowed to pollute downstream layers in the first place". A **data contract** "is not just the column exists… a real contract includes shape, meaning, ownership, freshness, compatibility rules, and what happens when the contract breaks". **Lineage** answers "where did the data come from? What changed it?… if the data is wrong, what else is now contaminated?" — otherwise "debugging a production data incident becomes archaeology with Slack messages". Four gates in the data plane (source contract, schema and meaning, quality, publish) and a fifth, the **AI approval gate**: "gold data is not automatically AI approved data… can this data set be embedded? Can it be retrieved by a model? Can an agent act on it? Does it contain PII? How fresh does it need to be? What lineage do we need into the AI output?" The reason: "bad data in a dashboard can mislead a human. Bad data in a RAG system can become a confident answer to a customer. Bad data in an agent workflow can trigger an action." The landing-zone minimum — "can we identify the source?… detect obvious schema breakage?… quarantine records that are malformed?… tag sensitivity and region?" — is the field list of this digest's audit report and envelope (§7.5). Two more rules kept: ask first "which sources are authoritative for which business concepts" ("computers are very good at making bad decisions repeatable"); set freshness per use case by "what business decision gets worse if the data is 5 minutes old?".

**The corpus audit in the vendors' practice.** Reducto's **classify and split** — "a very underappreciated way to have an LLM do its best work": paper-mail packets "can be hundreds of pages long. You don't necessarily know what is going to be contained within it", so route each document or interleaved section to its pipeline before extraction, because over-stuffed context shows "erosion… in quality outside of just the token economics". Reducto's evaluation rule: "people will kind of benchmark like say five documents… a very high variance estimate"; the alternative is an automated run over "thousands of examples" from "the whole rich heterogeneity of documents that your applications are going to be experiencing" (their internal "autoeval"). Abraham: "eval should underpin all of your decisions", including "real-time production monitoring because your production data is going to differ from whatever else you have in your contrived set", and **at every stage** — "even perfect parsing with a horrible retrieval pipeline is not going to help". Ebbelaar's pipeline (2025-02) is the minimal shape in five files — extract, chunk, embed, search, chat — with Docling's `DocumentConverter` taking "PDF, PowerPoint, docx or websites" into one `DoclingDocument`, a `sitemap.xml` walk for whole sites, and a metadata envelope of **filename, page numbers and title** beside every chunk.

### 3.3 Why PDFs are hard, and the pipeline that reads them

**The format.** Liu (2026-05): a PDF "is a bunch of machine instructions that help like print characters for display purposes on a page… random numbers representing coordinates plus like glyph symbols"; a table "is basically drawn as a set of like lines, borders, and then also values with coordinate positions" with no association; reading order in a multi-column page "could be totally arbitrary". Abraham: humans "encode so much context visually" — merged cells, line charts, handwriting. Word and PowerPoint are "a little bit more structured… but in… this custom bespoke XML format" with "a ton of fluff" (Liu, s2). The Reducto researcher's cases: circled options instead of checkboxes, handwriting crossing a divider, a dense table where a frontier model "got some extra data points… and… missing some data points", a watermarked table no model parsed; "you cannot write custom prompts for everything".

**Three generations of parser** (Liu; Abraham). Heuristic pipelines (PyPDF, PyMuPDF, pdftotext, Tesseract) cluster characters by spacing — "the moment the document format deviates from what the heuristic is able to handle, it's going to break"; Liu's 2024 slide shows PyPDF collapsing a missing value into one row, and "the more… information chaos and loss there is in the data, the higher… the likelihood of some sort of hallucination" downstream. Trained document models (Donut) one-shot a distribution. VLMs read "the way that a human would have" and handle the long tail but are "not a one-size-fits-all solution" (§3.4).

**The 2026 pipeline shape (Reducto's "blended approach… divide and conquer"; Docling's architecture).** (1) **Layout first**: "sub-hundred-million-parameter models" (as captioned) detect regions and "can actually run on CPU"; Docling's report names **DocLayNet** for layout and **TableFormer** for table structure, "on commodity hardware in a small resource budget" (abstract). (2) **Route by region**: "a lot of smaller steps… OCR with our OCR model… layout with layout model, then table extraction model… key value parsing model", decided "based on the complexity of the tags, based on the length, based on the size"; the expensive autoregressive models "are only needed for the most challenging cases". (3) **Grounding is the product**: "we basically have a pixel map for every single element"; extraction returns citations with confidences, and "for the information that we wanted to extract but was missing from the document, we were able to cite in the document that it was missing". Liu: "you typically want some sort of at least like region-level or line-level citations", which "doesn't come out of the box if you just call the VLM API". Docling: "every element includes provenance, page and bounding box information". (4) **Agentic verification — "agentic OCR"**: a correction layer making *token-level* edits ("a period versus a comma, a zero versus an O"), explicitly not "sending OCR to Gemini… asking it nicely to not deviate too much", because a rewriting model "will see the word total and if the human made a mistake in that table models will actually sometimes go through and add up the values in the table themselves" — faithfulness to the page, not to arithmetic. (5) **Use the metadata when it is good**: Reducto's "hybrid extraction mode… will look at the metadata and say like is this actually good"; government forms carry field descriptions "as a starting point" (Alvin). (6) **Output per consumer** (§3.5).

**Benchmarks.** OmniDocBench "is starting to become a little bit saturated… too rigid for what agents care about"; olmOCR-bench is "academic papers… binary pass fail" (Liu). LlamaIndex's ParseBench ("2000 human verified pages") and Reducto's RD-TableBench are vendor leaderboards. Rule drawn here (opinion): a public benchmark shortlists, your own thousand pages decide.

### 3.4 Frontier VLMs as parsers — the failure modes and the cost line

Four findings from two vendors who compete with the models they describe. **Silent drops**: frontier models are precise on what they keep but "silently drop a lot of the contents… recall really really struggles", while dedicated services are "behind… from a precision perspective, but close that gap on a recall perspective" (Abraham, citing a benchmark the captions call "micro one"). **Repetition at low temperature**: Gemini 2.5 Flash on a row of dots "will basically give you dot dot dot dot dot until the end of the context window"; raising temperature "from 0.1 to probably 0.5 or 0.7 the issues mostly go away. But then… the models are more likely to make up some stuff" — a sampling trade-off no prompt fixes (2025 model; mechanism carried). **Thinking does not help vision**: "increased thinking in the frontier models… generally does not correlate to increased visual understanding accuracy" because post-training is "on coding and reasoning and kind of math" (Liu, 2026-05). **Cost**: "Gemini Pro is… 8 cents plus per page… super expensive"; "if you're trying to run and parse like a million PDFs at scale, this is not going to work" (Liu). For long documents, Reducto's rule: "always parse them and then work with the parsed text" — text input lets an extraction model take "100 plus pages… one shot… maybe a 100 different fields", whereas "if your input is like a 100 images… hallucinations are everywhere".

**Where the VLM belongs — in the loop, on demand.** Liu describes the assistant loop as the model makers built it: "it does some sort of like free and open source text parsing first on the documents. Once it identifies a page, it'll screenshot the page and then feed it into itself" — fine for assistive work, not for a million PDFs. LightParse (free, "doesn't use any of the LLMs at all", Rust-based, "one-click installable as an agent skill", keeps bounding boxes so the harness "reconstruct[s] it into word-level citations") is the fast first pass; "then… equip a VLM-based parser… as a tool". Abraham's customers "create effectively a file system for their agent to go through and navigate… a content field which the agent can read as it needs to… [and] all the metadata… bounding boxes" — the s2 file-system context (Manus; Martin's "glob and grep") with parsed documents as the files. Reducto's chart pipeline is the extreme: an agent "with its own code interpreter… iteratively… until it's able to get to the final output" — mechanism noted, no numbers.

### 3.5 Architecture by data type — one intermediate representation, then a format per consumer

**One document model for every input.** Docling's `DoclingDocument` is "a rich hierarchical Docling document with element types, headings, and per-element metadata" (IBM), exported as Markdown, HTML, DocTags or "lossless JSON" (README); Ebbelaar adopts it because "it doesn't really matter if you throw a PDF or a web page at it". Unstructured's **partitioning** is the same idea: "distinct document elements that encapsulate paragraphs, tables, images, code snippets" with per-element metadata (`filetype`, `page_number`, `filename`), a `Table` element that "is not combined with other elements" and carries `text_as_html`, and `orig_elements` for traceability. LlamaIndex's `Document` → `Node`s, *Readers* (including a `DatabaseReader` that "returns every row of the results as a Document") and `IngestionPipeline` name the three stages every source agrees on: **load → transform → index/store**.

**By type.** *PDFs and scans*: §3.3; "page level chunking… is honestly a pretty strong baseline… stop worrying about tuning your chunk size of like 512 or 1024" (Liu, 2024; chunking itself is s7). *Tables*: "when you have a simple table, great, we can approximate that data in markdown. When you have a more complex table, you may want to use something like HTML" because merged cells "encode a lot of meaning" and the model reasons "through like an HTML structure" well but "you're also wasting a lot of tokens"; and a **second rendering for the embedding model** — "embedding models really struggle to correlate that natural language human prompt with this messy blob of HTML tags and numbers", so build "a representation that's more so designed for the embedding model itself… a natural language representation of that table", embed that and pass the HTML to the reasoning model (Abraham; Liu's 2024 "embed… an extracted summary, or embed the caption… and basically link all of them to the same underlying data" is the same move). In 2026-01 Reducto did "not do any of that auto routing… it's a user controlled thing"; by 2026-09 Abraham calls it "a dynamic problem" — dated. *Spreadsheets*: supported by LlamaParse and Docling; no source says more. *HTML and websites*: Docling "essentially just looks at the HTML and parses it"; whole sites via the sitemap (Ebbelaar). *Images and charts*: Docling can "enrich figures with text descriptions so that they're retrievable alongside text" and converts bar, pie and line charts "into tables or code" (README). *Databases*: Huyen's "Text-to-SQL… SQL execution… Generation", with "an intermediate step to predict what tables to use" when schemas do not fit, versus rows-as-documents (`context-store-decision.md` q7). *Audio and video*: Docling parses them with ASR — noted, not digested.

**Chunks or the tree (IBM, 2026-08).** "The author already organized the information for you. Chunking takes that tree and flattens it… and then spend a lot more effort trying to recover the relationships that were sitting right there the whole time." Alternative: keep the tree, give the agent an outline "where each section comes with a short summary", let it open one section, follow a footnote, hold its place — "this is still retrieval. It just keeps the document whole". Costs, from the same video: "you need a good tree before any of it works and parsing real world documents into clean structure is a hard problem. That's most of the engineering"; "more latency and more calls"; and "if you've got millions of documents and a fuzzy find me anything about X kind of question, similarity search is hard to beat". Its resolution — "similarity search to find the right document, structure to navigate inside of it" — becomes a row in `context-store-decision.md` (§7).

### 3.6 Privacy and compliance — PII before the index, reversible redaction, anonymity tests, deletion proof

**Where the PII check goes.** Gambill: "PII filtering must happen before sensitive data gets embedded, indexed, cached, copied, or scattered like glitter… Once sensitive data is downstream, AI artifacts are going to suck it up and use it. And cleanup gets really ugly." Huyen (2024-07): a reply contains sensitive data because "your model was trained on sensitive data and regurgitates it back" or "your system retrieves sensitive information from your internal database… and then it passes this sensitive information on to the response" — "prevented by not training your model on sensitive data and not allowing it to retrieve sensitive data in the first place". Her **input guardrail** is the mechanism the KB lacked: detect classes "specified by you" (ids, phone numbers, bank accounts, faces, IP keywords), then "block the entire query or remove the sensitive information from it… mask a user's phone number with the placeholder [PHONE NUMBER]. If the generated response contains this placeholder, use a PII reversible dictionary… so that you can unmask it"; run "a routing component… and a PII removal component… at the same time". Jarmul explains why retrieval-time filtering alone is late: "any documents that are available to the model is also something that we can… exploit the model to extract" — an early ChatGPT app, asked for "the file for download", returned "the file with everybody's salaries". **Three placements** (§5): scrub at ingestion what must never enter the index; filter at retrieval what some identities may see (§3.7); redact at output as the last net (G3).

**The detector.** Presidio (README; now at `data-privacy-stack/presidio`, MIT): "predefined or custom PII recognizers leveraging Named Entity Recognition, regular expressions, rule based logic and checksum with relevant context in multiple languages", analyzer and anonymizer modules, an image redactor, a structured-data module — and the sentence for every policy doc: "because it is using automated detection mechanisms, there is no guarantee that Presidio will find all sensitive information. Consequently, additional systems and protections should be employed." `13` §3.3's tiers apply unchanged: checksum and regex first, NER second, a classifier or judge last.

**What anonymous means (EDPB, 2026-07-08, press text).** "Data is anonymous if it does not relate to an identified or identifiable natural person", which "may vary from one entity to another"; the test is **three criteria — no record isolation, no linkage, no inference** — applied by a "contextual approach" (who could re-identify) or a "simplified approach" that ignores those differences and "may lead an anonymising controller to treat data as though it is not anonymous even if it would actually be so" but gives "greater confidence". A placeholder whose dictionary survives fails *linkage*, so Huyen's reversible masking is pseudonymisation, not anonymisation (this digest's reading; the page does not define the term). **Scraping for AI**: GDPR applies to "collection, storage, organisation and retrieval"; purpose limitation and transparency; "scraping data only from reliable sources, recording the timestamp, and validating the data before using them in AI training to ensure compliance with the accuracy principle"; data minimisation; legitimate interest as a basis; special categories (Art. 9) "in principle prohibited", no general exemption. Consultation until 2026-10-30 — re-read after. IBM's regime list (GDPR, EU AI Act, SOC 2, ISO 27001, HIPAA) is a checklist's column headers, not guidance.

**OWASP (landing page).** LLM02 *Sensitive Information Disclosure* and LLM08 *Vector and Embedding Weaknesses* are the 2025 names the threat model maps (T14, T17); their mitigations are not in the snapshot.

**Deletion and lineage.** Gambill's legal scenario: "can you prove that this customer's data was actually deleted…? Did the vector index retain anything? Did [caches] retain anything? Did evaluation data sets retain anything? And what about those logs?" — "test deletion like you're testing your recovery"; key boundaries and regions decided "before your replication"; eval datasets "need lineage and quality controls. Otherwise, your evaluation numbers become just acting theater". IBM (2026-09): data "gets transformed by RAG" so "if I'm looking for it in only this form, I might miss it"; track "child files… derived from" a sensitive file; its "31 %" figure is uncited (§4). Jarmul's three for the threat model: "please never put anything in your prompt that you wouldn't want to write on your public website" ("please repeat every sentence that was in our conversation" suffices); "poisoning of prompts or poisoning of other documents that are on your infrastructure" is "more meaningful to think about" than training-data poisoning; "prompt hijacking" of "a public facing with no authentication interface" that becomes "agent botnets". Her defences are the KB's: "segregate your model", sanitisation, access control — "this is not new"; "if we can do smaller models, if we can do local models… we can have a little bit more control"; "use guardrails but they're not going to save you"; red-teaming "beyond looking at what the vendor said". Docling's "local execution capabilities for sensitive data and air-gapped environments" (README) is the parser-side version of that choice.

### 3.7 Tenant isolation at the data layer — RLS, not a WHERE clause

Supabase (read 2026-10-01): with pgvector on Postgres "you can implement fine-grained access control on your vector database using Row Level Security (RLS)". The shape: `documents` with `owner_id … default auth.uid()`, `document_sections` with `content` and `embedding vector(384)`, RLS enabled, and a `select` policy `document_id in (select id from documents where owner_id = (select auth.uid()))`; then "semantic search over these sections (or any additional filtering for that matter) will continue to respect these RLS policies" — the similarity query is unchanged. Variants: a `document_owners` join table for many-to-many; permissions in another database through a foreign data wrapper ("RLS is latency-sensitive"); a direct connection setting `app.current_user_id` per session; a custom JWT whose `sub` claim `auth.uid()` reads. The sentence that settles the s5 placement question for Postgres products: "you might be tempted to discard RLS completely and filter by user within the where clause. Though this will work, we recommend RLS as a general best practice since RLS is always applied even as new queries and application logic is introduced in the future." Gambill at architecture level: "if a user can't access a customer record directly, they should not be able to ask a chatbot to summarize it through the side door… access control has to flow into this retrieval, not just the warehouse… retrieval, embeddings, vector search, agent tools, APIs, every place where the data happens to be exposed." Beside s5: Pinecone/AuthZed's pre- and post-filter is the *mechanism* when authorisation lives outside the store; RLS is the *enforcement point* when the store is the database — and the owner column is written at ingestion (§7.5), closing half of the s5 park "chunk-level permission metadata at ingestion".

## 5. What is contested / trade-offs

- **Parse to Markdown vs structured elements vs "chunkless" navigation.** Markdown is "something that agents will effectively reason on" (Abraham) and every parser's export; element graphs (Docling, Unstructured, LlamaIndex nodes) keep types, tables and provenance; IBM's tree navigation keeps the whole document and pays in calls. **Position:** parse to an element-typed document with provenance and keep it; derive Markdown, HTML for a complex table, or an embedding-text rendering as *views*; chunk for similarity over a large corpus, navigate the tree for long organised documents — "similarity search to find the right document, structure to navigate inside of it". Chunking's parameters are s7.
- **Open-source parser vs vendor API.** Docling runs locally on CPU, MIT, air-gapped — the choice when `personal_data` or `regulated` holds; Reducto and LlamaParse sell long-tail accuracy, grounding and agentic correction, on benchmarks they top. **Position:** start local plus a frontier VLM as a tool on hard regions; buy a vendor when your own thousand-page audit shows the long tail is yours.
- **Frontier VLM as parser vs as tool.** Vendors say "not at a million pages"; the model makers' harnesses parse fast first and screenshot on demand. Compatible: both put the VLM in the loop.
- **PII scrub at ingestion vs at retrieval vs at output.** Gambill: before embedding; Supabase/Pinecone: at retrieval by identity; Huyen and G3: at output. Different questions (should it ever be indexed; who may see it; did it leak anyway). **Position:** all three; ingestion is the only one cheap to prove; the output net is calibrated against Presidio's own warning.
- **Anonymisation vs pseudonymisation.** A reversible placeholder keeps *linkage* and is pseudonymised under the EDPB's three criteria (digest's reading); anonymous means no isolation, no linkage, no inference. **Position:** name which one the product does; treat pseudonymised data as personal data.
- **RLS in the database vs filter in the application.** Supabase: RLS "is always applied even as new queries… are introduced"; the application filter works today and breaks on the next query; Pinecone/AuthZed's pre/post-filter is for stores without RLS. **Position:** RLS or the store's native partition as the enforcement point, an application filter only as defence in depth, a two-identity test either way (s5 Verify 3).
- **Who benefits.** Reducto, LlamaIndex and Unstructured sell parsing; IBM authors Docling and sells data-security products; Supabase sells Postgres; Ng's company sold data-centric tooling; Gambill a checklist and course. Mechanisms kept with a second source; superlatives, prices and leaderboard positions not.

1. ### 7.6 Glossary entries to add (`principles/00-glossary.md`)

- **Document parsing (document OCR).** Turning a file designed for display into a structured representation with reading order, tables and provenance. Liu (2026-05); Abraham (2026-09).
- **Layout detection / element-typed document (partitioning); provenance.** Small models find regions on a page; each is parsed into typed elements with page and bounding box (the provenance a citation needs) — Docling's `DoclingDocument`, Unstructured's elements, LlamaIndex's nodes. Docling report (2024); Unstructured docs (read 2026-10-01).
- **Agentic OCR.** Token-level verification of parser output, as opposed to an LLM rewriting a page and "correcting" totals. Abraham (2026-09).
- **Data-centric AI.** Holding the model fixed and engineering the data: consistent labels, representative inputs, iteration on slices. Ng (2022).
- **Data contract / control plane / AI approval gate.** Shape, meaning, ownership, freshness, compatibility, break behaviour; the plane deciding which data may be embedded, retrieved or acted on. Gambill (2026-06).
- **Chunkless RAG / structure navigation.** Retrieval that keeps the parsed tree and lets the agent navigate sections instead of matching flat chunks. IBM (2026-08).

- **Row Level Security (RLS).** A database policy filtering every query by the request's identity, so a similarity search returns only authorised rows. Supabase (read 2026-10-01).
