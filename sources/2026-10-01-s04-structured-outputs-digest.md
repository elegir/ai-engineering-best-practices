## 2. One-paragraph summary

The module's thesis, stated by every structured-output source from Liu (2023) to the Anthropic docs (read 2026-10-01), is that **software wants a value, not a paragraph**: a model's output should enter a program as a typed object, never as a string that code parses and prays over. There are three layers of mechanism and the KB should name them: **prompt-and-parse** (ask for JSON, extract it with tags, prefill or regex — Witten's 2024 craft, still the only option on models without the feature), **JSON mode** (the provider constrains output to valid JSON but not to your keys — Pokrass: "you don't want the model to kind of make up the keys"), and **native structured outputs** (constrained decoding against a JSON Schema, now on both major providers, also as `strict` tool schemas), which guarantee *schema conformance* and nothing else — not correctness, not calibration, not that a refusal or a truncation will not arrive instead of your object. Above that sit **validators in code** (Pydantic/Instructor, Guardrails AI): business invariants (totals add up, quotes exist in the source, URLs resolve) that a schema cannot express, with a bounded **re-ask** that feeds the validator's error message back as prompt — "validation error handling and re-asking… just separate systems in code" (Liu). **Guardrails** are the same idea applied to risk: a verification suite at named checkpoints (input, retrieval, tool call, output; NeMo's five rails, Bhardwaj's six zones) with an explicit on-fail action (re-ask, fix, filter, refrain, log, raise — Guardrails AI) and a fail-open/closed policy, implemented in tiers — rules and regex, then a **small discriminative classifier** (Rajpal: "you don't need a jackhammer to crack open a walnut"; Carpintero: a fine-tuned ModernBERT at 35–40 ms, ~85 % on a public injection benchmark, self-hosted, retrained in hours), then an LLM judge only where latency allows — because prompt-level defences and model alignment are "a probabilistic preference, not a hard constraint" (Carpintero). The 2026 signal is the **system-one model**: Jev (Type-Safe AI) answers typed questions (choice / score / yes-no) with calibrated probabilities in one forward pass, which is what every "rate this 1–10 in JSON" prompt was faking, and which Pokrass and Witten already recommended approximating with log-probabilities over a handful of options. For **non-conversational UX**, structured outputs are the mechanism of generative UI, and the market agrees on three tiers — static (tool call → a developer-built component), declarative (a JSON spec rendered through a component catalogue; A2UI, json-render, Netflix's server-driven UI) and open-ended (model-written HTML or code in an iframe or isolate) — trading coupling against consistency, cost and security; declarative is the stated balance, and model-written code is untrusted code with three questions (what can it access, what can it do while running, what comes back) answered by isolation, an outbound allow-list and a renderer that rejects unknown types (Agrawal). Prompt templates are confirmed, not changed: variables in placeholders, sections in tags, information before instructions, examples as the biggest lever, and "do it in code, not in the prompt" whenever code can (Witten).

## 3. Detailed digest

### 3.1 Structured data extraction — the three layers and what each guarantees

**Why it exists.** Liu's 2023 keynote (`yt-yj-wSRJwrrc…`) opens with the production reality: "90 % of the applications you build are just ones when you're asking a language model to output JSON… that you're parsing with a regular expression", because products must be "backwards compatible with the existing software". The failure modes he lists are the ones the KB's row-based tables already name — a key spelled `user` on one call and `username` on the next, "okay here you go, here's some JSON" preambles, missing keys, booleans parsed from strings — and his cure is to make the *schema* the unit of programming: a Pydantic model is "the prompt, the data and the behavior all in one", docstrings and field descriptions travel into the JSON Schema the model sees, nested and recursive models replace hand-written schemas, and the IDE type-checks the result. His 2024 follow-up (`yt-pZ4DIH2BVqg…`) reports that nothing changed in the idea while Instructor reached 1.0, six languages and "40 % growth month over month" (his figures); the API stays "one noun — the client — and three verbs — create, create with iterable, create with partial". Pokrass (`podcast-NjOfH9D8aJo…`) gives the provider's reason for building the feature natively: "if something is 95 % reliable but you're chaining together a bunch of calls… it makes your application not work… going from like 95 % to 100 %". Horthy's 12-Factor factor 1 (`yt-8kMaTybvDUw…`, reused) is the same claim from the agent side: "the most magical thing LLMs can do… is turning a sentence like this into JSON".

**Layer 1 — prompt and parse.** Witten's workshop (`yt-hkhDdcM5V94…`) is the most complete account of the pre-native craft, demonstrated live on Claude 3.5 Sonnet: the "here is the JSON" preamble is removed by an **assistant prefill** ("putting words in Claude's mouth" — put `Here is the JSON:` and even the opening `{` in the prefilled assistant turn, then add the bracket back before `json.loads`); outputs are wrapped in tags (`<json>…</json>`, `<summary>…</summary>`) and extracted with a regex; a closing tag in **`stop_sequences`** stops generation before any trailing explanation and saves the tokens; and the general rule is "it's cheaper and easier to do a little bit of work outside of a call to the LLM… don't put a bunch of stuff in the prompt about you must output JSON, just use the prefill and then parse it out". The Anthropic page read on 2026-10-01 now states that message prefilling is **incompatible** with JSON outputs — so prefill is the fallback for models without constrained decoding, not the default. Guardrails AI's README describes the same two-level fallback inside the library: function calling where the model supports it, "prompt optimisation" (schema appended to the prompt) where it does not.

**Layer 2 — JSON mode.** Pokrass: shipped at OpenAI's 2023 Dev Day; it "constrain[s] the output of the model to match the JSON language… you basically will always get something in a curly brace", but keys and types are the model's choice, and a purely engineering constraint without training produced a known pathology — "models output like whitespace for a really long time… it's legal per JSON". JSON mode remains useful only when "you want the model to be more creative and use it to come up with JSON schema that you don't even know you want"; "most developers are probably going to want to upgrade to structured outputs".

**Layer 3 — native structured outputs (constrained decoding).** Pokrass describes two halves: the engineering half masks "the available tokens that are produced every time to only fit the schema", and the research half trains the model to follow formats so that the constrained path is also the natural one; the first request with a new schema pays a one-time cost to "build this artifact for fast sampling", which is why schema pre-registration was considered and rejected. The two canon pages confirm the shape in 2026: OpenAI — "Structured Outputs ensure the model will always generate responses that adhere to your supplied JSON Schema… No need to validate or retry incorrectly formatted responses"; Anthropic — `output_config.format` with `type: "json_schema"` (the earlier `output_format` parameter and its beta header are deprecated), `client.messages.parse(output_format=Model)` in the SDK, "no retries needed for schema violations", and a grammar that "compiles" on first use and is "cached for 24 hours from last use". **Guaranteed is conformance, not correctness.** Pokrass states it unprompted: "the guarantees is that they fit the schema but the schema itself may be too broad… you might give me zero, give me 12" for a 1–11 range. Anthropic's page lists the cases where even conformance does not hold: a **refusal** (`stop_reason: "refusal"`, HTTP 200, billed), **truncation** at `max_tokens` ("retry with a higher `max_tokens`"), and **enum casing** ("don't guarantee the capitalization of string enum and const values — compare case-insensitively"). Pokrass explains the refusal design — a field rather than a 4xx/5xx because "there are things that are in between your fault and my fault, there's kind of like the model's fault, and there's no error code for that".

**Function calling versus response format.** Both sources insist the two are not synonyms although they share the mechanism. Pokrass: "you should use function calling when you actually have functions that you want the model to call… the new response format is a way of just getting the model to respond to the user but in a structured way"; the model is trained to treat the two differently, and hacking function calls to get a response shape loses "more of the model's verbosity". Anthropic: "JSON outputs control Claude's response format (what Claude says). Strict tool use validates tool parameters (how Claude calls your functions)" — both use constrained decoding, can be combined in one request, and `strict: true` is per tool. Pokrass also notes that constraining to the chat format removed a class of errors where "the model used to occasionally pick a recipient that was invalid" — a hallucinated tool name — which is the same guarantee Jev's authors call "cannot hallucinate" (§3.4). Horthy's factor 4 ("tool use is harmful" in quotes) is the conceptual bridge: a tool call *is* a structured output that deterministic code dispatches with a switch statement; "there's nothing special about tools, it's just JSON and code".

**The schema dialect, by design.** Pokrass's two decisions are the ones a schema author must know. `additionalProperties` defaults to `true` in JSON Schema — "the opposite of what developers want" — so the API *requires* `additionalProperties: false` rather than redefining the standard, "to play nice with the community"; every key in JSON Schema is optional by default — "you'd be very surprised if you passed in a bunch of keys and you didn't get some of them back" — so every key must be listed in `required`, and an optional value is expressed as a **union with `null`**. Parallel function calling was excluded at launch because the combined schema of a changing function list would re-incur the compile latency unpredictably. The Anthropic page adds the 2026 limits of its grammar: unsupported constraints (`minimum`, `maximum`, `minLength`, `maxLength`, `pattern`) are moved by the SDK into field *descriptions*; at most **20 strict tools** per request, **24 optional parameters** across all strict schemas, **16 union-typed parameters** (`anyOf` and `["string","null"]` are "especially expensive" — "each roughly doubles grammar state space"); a 180-second compile timeout; a `400 "Schema is too complex for compilation"` beyond that; required properties are emitted first, in schema order; citations are incompatible; **changing the output schema invalidates the prompt cache** for that thread; the compiled schema is cached for 24 h server-side, so "PHI must not be included in JSON schema definitions". These are vendor-specific facts dated 2026-10-01; the design rule they share is: *flat where possible, few optionals, no regex in the schema, business constraints in validators, not in the grammar.*

**The schema is a prompt.** Liu (2023): "when you have docstrings the docstrings are now a part of that JSON schema… your code quality, your prompt quality, your data quality are all in sync". Pokrass, asked where instructions go, gives three places with three jobs: the **system message** for *when* to call a function or produce a shape ("here's when you should call this function"), the **field or function description** for *how* ("do you want year-month-day or backwards"), and the **key name itself** for *what* ("name the key by what you want" — swyx's habit of naming a property `brainstorm_a_list_of_up_to_five_topics` is "the fun nature of this", not an official recommendation). The KB's tool-definition rules (`principles/21-agent-design-and-tools.md` §3.4: the description is part of the prompt) therefore extend unchanged to output schemas.

**Chain-of-thought as a field.** Liu puts an optional reasoning field inside reusable sub-models and switches it off in production ("disable that chain of thought field… in testing you add that to figure out what's the latency or performance trade-offs"); Pokrass's launch example is a `steps` array before the final answer ("a more structured way of extracting the final answer"); Witten's workshop ends with the same ordering rule for judges (§3.4). The rule the sources share: **the reasoning field comes before the answer field**, because generation is sequential and the model reads what it already wrote — the schema-level form of principle 10's "let the model spend tokens before answering".

**Streaming structured outputs.** Liu's 2024 API has two streaming verbs — *iterable* (a list of objects, each yielded complete as it finishes: "a search query for Y, a search query for X… two parallel search queries") and *partial* (one object whose fields fill in, validated at each step: "you can render that while streaming without having to write this very evil JSON stack code") — and he names generative UI as the use case. Anthropic's page: structured outputs stream "like normal responses". For the KB's streaming pipeline (`principles/12-llm-gateway-layer.md` §3.3) this means a structured route streams *typed partial objects*, not text deltas, and the renderer consumes fields, never substrings.

**Validation beyond the schema, and the re-ask.** This is the centre of Liu's two talks and of Instructor's front page (read 2026-10-01: `max_retries`, `field_validator`, `llm_validator`, "Automatic retries on validation failures"). The pattern: a Pydantic validator expresses an invariant the grammar cannot — `price × quantity` of the line items equals the receipt total; every quoted substring exists in the source chunk ("not by asking it to not hallucinate but actually trying to figure out… what the quotes were"); every URL in a RAG answer returns 200 ("if it's not real just throw it out next time, don't try too hard"); an owner is one of the meeting participants; a label is a `Literal["spam","not_spam"]`. On failure the **error message is appended to the conversation** and the model asked again — "it is the error message that is part of the prompt but conditionally added" — with a cap: "often one retry for models like OpenAI and Anthropic are basically enough and really all you care about is having good, well-written, informative error messages". Rajpal (`yt-9-vGxMoUM9Y…`) frames the same loop from the risk side as Guardrails' re-ask policy (§3.3) and quotes Alex Graveley's one-line design: "add a constraint checker to check for valid generation; on violation inject what was generated and the rule violation and regenerate". Pokrass's warning closes the loop from the other direction: library-side retries are *not* free — swyx reports ripping Instructor out for native structured outputs and cutting "55 % of API cost… because of we saved on the retries" (one person's measurement on one pipeline; §4), and Pokrass: "we are not retrying, we're doing it in one shot". Read together: **native constrained decoding for the shape, code validators with a bounded re-ask for the meaning**; never a library re-asking on top of a provider that already guarantees the shape.

**Escape hatches and the "Maybe" pattern.** Liu's 2023 example: instead of "return I DON'T KNOW in all caps, check if string contains it", model the output as `MaybeUser {result: User | None, error: bool, error_message: str}` — "I can kind of program with language models in a way that feels more like programming". This is the schema-level form of the KB's "give the model an out" (`practices/llm-api-calls/failure-modes-and-mitigations.md` row 7), and Pokrass's refusal field is the provider-level form of the same idea.

**Data structures as plans.** Both Liu talks end on the same application: the model emits a DAG (a query plan with ids and dependencies), a knowledge graph one-to-one with a visualisation API, or a list of typed search requests, and classical code executes it — "you can create the data that you want to send to Airflow rather than doing this for loop hoping it terminates". Horthy's micro-agents inside deterministic DAGs and Colvin's typed graphs (§3.4) are the same stance; the KB already holds it in `principles/21-agent-design-and-tools.md` and `12-Factor Agents` (glossary), and this module adds only that *the structured output is the hand-off format between the model and the executor*.

### 3.2 Structured prompts and dynamic templates

Nothing in this module contradicts `principles/10-llm-api-fundamentals.md` §3.3 or `practices/llm-api-calls/system-prompt-template.md`; Witten's 2024 workshop and the reused *Prompting 101* (2025-05) confirm them in detail and sharpen four points.

- **Templates and variables.** Witten asks for prompts "with spaces where the variables are going to go… denoted with these double brackets", the Anthropic console's `{{variable}}` convention; Instructor's front page offers Jinja templates with a `context` dict. The KB's template already separates static and dynamic parts for caching; the module confirms that the *placeholder syntax* is a tooling choice and the *static/dynamic boundary* is the rule.
- **Structure with tags; information before instructions.** "The most important thing is just clearly separating the different parts of the prompt… using it for semantics of what this section is"; XML works on Claude because it saw a lot of it in training, but the separation matters more than the syntax. "Instructions are more tightly followed the closer they are to the bottom of the prompt… particularly with long documents". Both are already in the template.
- **Examples are the biggest lever.** Witten: "most of the gains of writing a good prompt is literally just picking the perfect document… the perfect set of tweets… in some ways that's more important than everything else that I've said combined"; prefer **one excellent example over several truncated ones**, use **contrasting pairs** (a cringe tweet and an excellent tweet for the same document, each with a line of reasoning), and keep negative examples as "a tool in the toolbox", not a requirement. He has no evidence that a single examples block differs from examples as alternating messages. The OpenAI Build Hour (reused) gives the same answer to a structured-JSON hallucination question: "a few different varied examples". The KB's template has illustrative and edge examples; it gains the contrasting-pair form.
- **Light-touch negatives; role in the system prompt; small sentences; temperature 0 for extraction.** "If you tell the model don't talk about elephants… it might make it more likely"; the system prompt holds the role and little else, except where tool use was fine-tuned on system prompts; "simple small sentences is better"; temperature 0 "for knowledge work… marginally fewer hallucinations". Witten also routes **multi-persona** behaviour in code ("dynamically route the query… don't do it in a prompt if you don't have to"), which is the routing pattern of `principles/21-agent-design-and-tools.md`.
- **Do it in code.** The line that organises the whole workshop — "when you can offload stuff to code, especially if the code is really easy to write, just do that" — is the KB's "mechanism over prompts" (`principles/02-harness-engineering.md`) applied to the prompt itself: format checks in code, not model-graded; stop sequences, not "don't continue"; routing in code, not persona switching in a prompt.

### 3.3 Guardrails and response validation

**The paradigm.** Rajpal (2023) names it *trust, but verify*: "every output that you get back passes through a verification suite", and "only use large language model outputs if your verification suite passes; on failure… hook into… their ability to self-heal" within a latency, dollar or token budget. Her argument against the alternatives is the KB's own: prompting "doesn't act as a guarantee" (the same evaluator prompt at temperature 0 gave different benchmark numbers across five identical runs); training a classifier is expensive; commercial models change under you ("prompts that might have worked for you in the past will stop working"). Guardrails AI's README (read 2026-10-01) has kept the shape: a `Guard` composed of **validators** from a hub (regex match, competitor check, toxic language…), an `on_fail` action per validator — **`EXCEPTION`** in the README examples; Rajpal's talk enumerates **re-ask, filter, fix, fallback, refrain, noop-and-log** — input *and* output guards, structured generation through function calling or prompt optimisation, and a server mode that fronts an OpenAI-compatible endpoint. One dated fact: validators move to plain PyPI packages and hosted inference is discontinued, cut-off 2026-08-25 (README news item dated 2026-07-06).

**Where to check.** NeMo Guardrails (NVIDIA, read 2026-10-01) names **five rail types** — input, retrieval, dialog, execution (tool calls) and output — configured in YAML and Colang, with "LLM self-checking", NVIDIA safety models, community models (Llama Guard), third-party APIs and Guardrails AI validators pluggable at each; its agentic list is the KB's security baseline in four lines: "Isolate all authentication information from the LLM. Validate and sanitize all tool inputs. Apply execution rails to tool calls. Monitor agent behavior." Carpintero (`yt-YZHPEkfy2kc…`): "the minimum safety requirements here in production would be to check at least for the user inputs and the model responses; but ideally we should also add safety checks for all components interacting with our systems like retrieval augmentation, MCPs, and also within our context memory and agentic plans", and "the more complex and the more autonomy in our systems, the more checkpoints will be needed". Bhardwaj (`yt-v9wFSDSjb_c…`) lists **six zones** (input/sensory, retrieval, vector/memory, context assembly, model inference, tools/agents) with a control per zone — input schema validation and a regex-plus-classifier "prompt firewall"; tenant-scoped retrievers with ACLs and rate limits; signed documents against poisoning; a token budget and citation policy at context assembly; output schema validation (he says "OpenAPI 3.1") at inference; a **tool allow-list with per-agent, per-day, per-amount and per-tenant limits** at the action layer. Three vocabularies, one picture: checkpoints at the trust boundaries, each with its own check and failure policy — which is the extension of the gateway's placement table (`practices/llm-gateway/routing-policy.md` §Guardrails) that the s3 digest parked for this module.

**How to check — the tiers.** Rajpal's ordering, confirmed by Carpintero's whole talk: (1) **ground in an external system** when possible (a text-to-SQL output executed against a sandbox with the real schema "substantially improved the correctness"); (2) **rules and heuristics** (an interest rate ends with `%`; a regex for `ignore previous instructions`); (3) **small, high-precision classifiers** — "you don't need the full power of an LLM to solve really basic constraints… you don't need a jackhammer to crack open a walnut"; (4) **LLM self-reflection** last. Carpintero's contribution is the concrete recipe for tier 3 and why it fits: a safety check is "fairly regarded as a discrimination or a classification problem", an **encoder** sees the whole input in one pass with bidirectional attention and condenses it into a `[CLS]` token for a classification head; ModernBERT's architecture (alternating local 128-token / global attention every third layer, 8,192-token context, unpadding and sequence packing, rotary positions, flash attention) makes it fast and long enough for tool descriptions and agent plans; fine-tuned on **Inject Guard** (75k labelled prompts from 20 open sources), the base model (~150 M parameters) gives a baseline and the large one "almost six points" more; result "almost 85 % accuracy using only 35 milliseconds per classification" on unseen benchmarks, under a dollar of compute, **self-hosted** (no intermediate steps sent to a third party), **retrainable in hours** as attacks mutate. An LLM judge in the same position "can easily compound into… seconds of latency". The OpenAI Agents SDK page (read 2026-10-01) gives the economic framing from the vendor: "run a guardrail with a fast/cheap model… saving time and money".

**Placement and failure policy — the Agents SDK as the worked example.** The SDK page is precise where the talks are loose, and the s3 principle already holds the headline (parallel guardrails save latency, do not combine with streaming). Input guardrails run only on the **first** agent, output guardrails only on the agent that produces the **final** output, and **tool guardrails** run on every guarded tool invocation (before and after; also for a local MCP server's tools) — "if you need checks before and/or after each custom function-tool call… use tool guardrails". Two execution modes: **parallel** (default; best latency; "the agent may have already consumed tokens and executed tools before being cancelled") and **blocking** (`run_in_parallel=False`; "the agent never executes, preventing token consumption and tool execution… ideal… when you want to avoid potential side effects from tool calls"). A **tripwire** raises a typed exception and halts; a rejected final output is replaced in the session by a data-free placeholder ("Output withheld by an output guardrail.") so the rejected payload is not persisted or replayed. For the KB this settles the rule the s3 digest left as a table: *checks that guard side effects run blocking at the tool boundary; checks that guard the user-visible text may run parallel on non-streamed routes; every check names its action on failure.*

**Why prompt-level defences are a layer, not a guarantee.** Carpintero's attack survey (first half of his talk) is the module's threat model: **direct injection** (the Bing/Sydney system-prompt exfiltration, 2023, by natural language alone); **indirect injection** via content the model fetches (the Wikipedia-redirect proof of concept; and a documented 2026-03 case of websites embedding prompts to make AI ad-review systems approve non-compliant content — "the data that the AI is evaluating is able to overrule… the decision-making process"); **adversarial suffixes** found by gradient search on open weights that *transfer* to closed models because similar training yields "geometrically similar refusal boundaries"; **RAG poisoning** ("poisoning only five chunks" in an 8-million-document store, per the PoisonedRAG paper as he cites it); the **MCP tool-description asymmetry** (the user approves a one-line summary, the model reads a full description with hidden instructions — the "iceberg effect" for human reviewers); and **agentic** chains (an HTML page telling a computer-use agent to download and run a file; a malicious npm package installed because a GitHub issue title was interpolated into a coding agent's prompt). The structural reason is one sentence: "LLMs have no native separation of concerns between the system controls and the data". Hence "we cannot exclusively rely on model alignment" nor on human review. Bhardwaj's sandwich defence, random-sequence enclosure, post-prompting and XML tagging of user input are therefore recorded as the *cheapest first layer*, and the KB's existing rule holds — guarantees live outside the model (`principles/10-llm-api-fundamentals.md` §3.1; `failure-modes-and-mitigations.md` rows 10 and 14). The OWASP 2025 Top 10 names, read from the landing page: Prompt Injection, Sensitive Information Disclosure, Supply Chain, Data and Model Poisoning, Improper Output Handling, Excessive Agency, System Prompt Leakage, Vector and Embedding Weaknesses, Misinformation, Unbounded Consumption — a checklist the security baseline's threat model can map rows to.

**Prompts and policies as code.** Bhardwaj's one durable practice: the system prompt and the per-domain policy (a YAML of industry rules — "do not diagnose", "no guaranteed returns", blocked phrases) are **committed, code-reviewed and gated in CI** with "prompt linting", jailbreak and RAG retrieval tests before deployment ("shift left… lot of people don't even do this step"). It restates `principles/10-llm-api-fundamentals.md` §3.3 (prompts versioned like code) and `05` (sensors in CI); the module adds the explicit *policy file* and the injection fixture as a CI stage. His **confidence-gated human-in-the-loop** — "if you have a low confidence, have human in the loop… give them like one hour or two hours just to validate… if it is correct, agent will automatically send it out" — is a concrete shape for the approval rule in `practices/verification/dry-run-and-approval.md`: a confidence threshold decides which actions wait, and a time-boxed approval window decides for how long.

**Hallucination guardrails in particular.** Rajpal's *provenance* validator (every utterance traceable to the retrieved context, by embedding similarity, NLI classifiers and self-reflection) and Liu's substring-quote validator (a fact is kept only if its quote is literally in the source chunk) are two implementations of one rule the KB has as row 1 of the failure-modes table: *the answer must be anchored in the context, and the anchor is checked in code*. The module makes the check mechanical: cite with a verbatim quote, verify the quote exists.

### 3.4 Decisions versus generation — classifiers, calibration, system-one models

A thread runs through five sources that the KB has not yet named: **most decisions inside software are classifications, and a generative model is the wrong tool for them.** Pokrass, asked for a blessed rating scale: "we often recommend using log probs with classification tasks… rather than sampling two tokens for yellow you can just do ABCD and get the log probs… a non-calibrated model might always pick seven". Witten, on a 1–5 translation grader: "I don't think it's very well calibrated… limit the granularity to maybe five different classes", put the chain of thought *before* the grade, and note that log-probabilities after a chain of thought need both prefill and logprobs in one API, which few models offer. Rajpal and Carpintero reach for encoders for the same reason (§3.3).

**Jev** (Type-Safe AI, out of stealth 2026-09; founder Diogo Almeida, an InstructGPT author, per Witteveen `yt-X117w2Rark8…`) is the first product built on that observation. It takes text (no images or audio) plus **typed questions** of three kinds — **choice** (pick one of up to ~255 options, return a probability for each), **score** (a rubric from 0 to N, returned as the probability-weighted average with a confidence derived from the spread — Gupta reconstructs this from the website: "it's a sum"), and **nul** (a yes/no with a probability, a made-up word because `null` is taken) — and answers in **one forward pass**: "there's no text to parse… the number that you're getting back there is just generated text" when an LLM writes `0.9`, whereas here it is a probability. Witteveen's measurements: 70–500 ms round trip, US$0.042 per million input tokens and **free output tokens** ("they're literally only outputting one token, it's not worth billing for" — Gupta), 32k input limit, "just over 1/20th of a cent" for 20 chained classifications; it detects language, sentiment, routing, PII, spam, injection attempts and sarcasm in his demo, and is still stochastic ("slightly different each time"). What it cannot do: generate arguments for a tool ("it's just telling us which tool to use as opposed to getting the right arguments out"), reason or write; and "cannot hallucinate" means only that it cannot break the option set — it can still pick the wrong option. The design idiom the Boundary stream (`yt-35PSMmDDKP8…`) adds is the **smart if-statement**: decompose "rate this pitch" into small gut questions, run them in parallel (a triage class whose enum, score and boolean fields are four independent Jev calls), and gate on thresholds in code ("if the email feels urgent with confidence 80 % do this; 50–80 % maybe; otherwise normal"); Horthy's failed experiment — a coding agent as a finite state machine over Jev choices — shows the limit (255 options, no arguments, "an abuse of Jev"). Gupta's own caveat is the KB's: a small model is sometimes wrong, so "you're going to have to build code to deal with the fact that it might be completely wrong… the same stuff that we talked about agentic engineering, harness engineering". Both Boundary speakers expect every lab to ship such a model, and Horthy notes that inference engineers claim "you can do this with any model and get comparable results" with the right serving tricks. The KB records the **pattern** (decision tasks → a discriminative or probability-returning model with enumerated options, thresholds in code, generative models only where text or arguments are needed) as new, and the **product** as a parked trend to re-evaluate with an eval (Replicate's "90 % accuracy versus a 50 % LLM baseline, eight times faster" is a tweet relayed in the stream; §4).

### 3.5 Non-conversational interfaces and business-oriented UX

**The frame.** Casas (`yt-DLEPGhA4NJQ…`): LLMs are "a new computer" still at the terminal stage — "the GUI has not been invented" — and chat is "not the most efficient or the final form"; Agrawal (`yt-iymZjaNcwc8…`) found in production that a chat agent over an admin dashboard produced "text blurb" that became unreadable as conversations grew; Pokrass names "dynamic UI generation" as the first use case of recursive schemas ("every UI is a nested tree that has children"); Witteveen's reading of Jev's founder — "chat is the wrong interface for software; software doesn't want a paragraph, it wants a value" — is the same thesis at the API level.

**Three tiers of generative UI**, named almost identically by CopilotKit (`yt-Z4aSGCs_O5A…`) and Casas:

1. **Static** — the agent emits a tool call or structured state and the front end maps it to a **developer-built component** (CopilotKit's `useRenderToolCall`; AG-UI's registered components; Goose's visualiser). Pros: pixel-perfect control, "your designers really happy", simple mental model. Con: **coupling** — the tool's name and arguments are an API contract between back end and front end, and "the codebase is going to grow linearly with your use cases".
2. **Declarative** — the agent emits a **JSON description** that a renderer maps to a constrained component catalogue: Google's A2UI (launched 2025-12, pre-1.0 in 2026-01, Lit and Flutter renderers, a React renderer being written by CopilotKit), json-render, and the older precedent Casas cites — Netflix's server-driven, per-user personalised home page. "The structure of the content is non-deterministic but the actual rendering of it is deterministic"; "you fully control what each of these individual components look like… it's just the structure that changes". Casas: "probably the best balance… it provides the stability, you can keep your design system, your accessibility". Con: constrained by the spec (no arbitrary widgets; a calculator display is hard), and structure still varies run to run.
3. **Open-ended** — the model writes HTML or code rendered through `dangerouslySetInnerHTML` or an **iframe** (MCP Apps — the renamed MCP-UI, backed by Anthropic and OpenAI, launched the week of the CopilotKit talk; ChatGPT apps such as Zillow). Pros: lowest coupling, "render anything". Cons listed by both speakers: unpredictable (the same Rubik's-cube demo "looks slightly different every single time"), hard to style, **expensive** to regenerate every time, inconsistent with a design system unless you train on it, unfamiliar to users who "like to know where things are", and a **security** surface (XSS; iframes, double iframes and sandboxing are the protocol's answer).

Casas's closing opinion is that the more valuable near-term pattern is **collaboration on a shared artifact** (a canvas, an Excalidraw MCP app) rather than throw-away generated pages — the same "agent steering" and **bidirectional shared state** that CopilotKit demonstrates (AG-UI's state snapshots and deltas flow both ways; a human edit becomes agent context; human-in-the-loop interrupts as a first-class event). AG-UI itself is "a standardization layer of about 16 events" (run started, text message start/delta/end, tool call, state snapshot/delta, run finished) transported over SSE or WebSockets; it is a vendor-authored protocol with vendor-reported adoption figures (§4), and the KB keeps only the shape: *the UI consumes typed events and typed state, never free text; a tool call or a schema maps to a component*. This extends `principles/12-llm-gateway-layer.md` §3.6 ("the UI holds no model logic").

**Model-written code is untrusted code — Agrawal's production rules.** His Cloudflare certification-platform admin dashboard lets the model write a JavaScript function at request time that fetches data through a *typed tool* (the model never writes SQL), computes, and returns a **description of the UI** ("there is no React code written by the model, there is no JSX, there is no HTML"). Three questions decide the architecture: **what can the code access** (only the tools given; the data tool enforces its input schema and throws on anything outside it), **what can it do while running** (it runs *outside the app* in a Cloudflare dynamic worker — a V8 isolate, not a container, "spinning up a container is just futile" for a JavaScript function — with `globalOutbound` set to `null` or to an allow-list of URLs so a `fetch` to an attacker's domain fails, and CPU-time limits), and **what comes back** (schema validation on the server *and* in the browser; then a `switch` over known component types maps to React components, and an unknown type such as a smuggled `html` is simply not rendered — "the last defense point"). His summary: "whenever you have generated code by an LLM, treat it as an untrusted code… run the model-written code outside your app". These rules are the UI-side instance of the KB's sandbox and allow-list stance (`practices/security-baseline/`, `principles/21-agent-design-and-tools.md` §3.4 "bounded tools"); the depth of code sandboxing belongs to session 14.

### 3.6 Engineering quality around the libraries (Colvin, 2025-02)

Colvin's episode (`podcast-7wwWRph3Jls…`) is mostly about Pydantic AI and Logfire and is used here for three things that bear on this module. First, the **type-safe output as the unit of an agent**: an agent has "a system prompt, some tools and a structured return type", and even the graph library infers edges from return-type annotations so the workflow is type-checked rather than validated at runtime — the extension of structured outputs from one call to a whole workflow. Second, **testing discipline**: every documentation example runs in the test suite with its printed output checked (`pytest-examples`), live-model smoke tests run on every commit to `main` ("all of the models fail more often than you might expect"), and `TestModel` / `FunctionModel` let you unit-test an agent without calling a model — the mechanism behind the s3 rule "cached responses as test fixtures". Third, an **observability caveat specific to GenAI**: traditional observability scrubs parameters and keeps the SQL, but "with GenAI that distinction doesn't exist because it's all just messed up in the text", so prompt and completion data in traces is of "a different order of magnitude" of sensitivity and self-hosting demand follows — confirming the content-opt-in and redaction rules of `practices/llm-gateway/tracing-otel.md`. His view that "the more intelligent they are, the less we need to… constrain the routes in which they take" is recorded as opinion; his claim that one foundation-model company cut time-to-first-token 20 % by upgrading Pydantic v1→v2 is unverifiable (§4). The framework comparison (Pydantic AI vs LangChain vs LiteLLM as a model layer) is skipped: he refuses to rank them himself.

## 5. What is contested / trade-offs

- **Native structured outputs vs library-side validation.** The providers (Pokrass; OpenAI and Anthropic docs) say: no retries, one shot, schema guaranteed; swyx's cost anecdote supports them. Liu and Instructor say the library is still needed for *semantic* validation and the re-ask, and Liu's 2024 talk concedes the point ("whether or not we use something like constraint sampling… the benefits I get as a programmer is on a different level of abstraction"). Guardrails AI positions itself on the same layer. **Position taken:** the two are complementary and the order matters — native constrained decoding for the shape wherever the model supports it (and a `strict` tool schema for tool arguments), a thin validation layer in code for invariants, one bounded re-ask that carries the validator's message, and prompt-and-parse (tags, prefill, stop sequences) only for models without the feature. A library that re-asks for *schema* violations on a provider that guarantees the schema is paying twice.
- **Prompt-level guardrails vs classifier guardrails vs LLM-judge guardrails.** Bhardwaj teaches sandwich/XML/regex defences as if they were controls; Rajpal and Carpintero show why they are a first filter at best; the Agents SDK's own example *is* an LLM judge (a small agent returning `is_math_homework`), chosen for developer convenience; NeMo lists all three as pluggable. **Position taken:** tiers by cost and determinism — rules and grounding first, a small discriminative classifier (hosted or self-hosted) for the recurring risk classes, an LLM judge only where the content is "squishy" and the latency budget allows, and never a judge as the sole gate for anything irreversible (the KB's standing rule). The 2026 wrinkle is that a probability-returning model (Jev or a logprob read) blurs tiers 3 and 4; the KB treats it as a classifier with a threshold in code.
- **Who benefits.** Liu sells Instructor (and now consulting); Rajpal sells Guardrails AI; Colvin sells Logfire and promotes Pydantic AI; Pokrass sells a feature that makes Instructor's core less necessary (and says so politely); CopilotKit **authors AG-UI** and frames every protocol as transported by it; **Boundary sells BAML, not Jev** — its interest in Jev is that "it's very BAML coded" and it ships the client; Type-Safe AI, which sells Jev, has no paper and no architecture disclosure (Witteveen). Bhardwaj sells a framework name. Mechanisms from each were kept only with a second source; preferences were not.
- **Declarative vs open-ended generative UI.** CopilotKit presents all three tiers neutrally and transports all of them; Casas, who co-pioneered MCP Apps (the open-ended tier), still calls declarative "the best balance". Pokrass's recursive-schema example is declarative in spirit. **Position taken:** declarative by default for business UIs (design system kept, renderer is the allow-list), static for the two or three well-trodden paths, open-ended only inside a sandbox for consume-and-discard visualisations — stated as an opinion for Martin's shapes (admin tools, dashboards, back-office automation), not as a market consensus.
- **How much structure do smarter models need?** Colvin: less, over time ("if you're doing high-net-worth banking you just employ people who you think are going to be charming… and set them off"); Liu: "as models get smarter we're only going to have to do less and less… you're still fairly bulletproof"; Carpintero: attacks are escalating and alignment is probabilistic. Not contradictory — structure for *integration* (schemas) may shrink as instruction-following improves; structure for *safety* (checkpoints) does not.
- **Where the classifier runs.** Carpintero argues for self-hosting (privacy, cost, retrain cadence); Jev and Guardrails Hub are hosted; Guardrails AI is *discontinuing* hosted inference (README, 2026-07). For a solo operator the KB's opinion is: a hosted probability model or a hosted moderation endpoint first, self-hosted encoder when volume or data sensitivity demands it.

**Stack-sensitive points.** Native structured outputs are a provider feature, not a language feature — any stack gets the guarantee by sending the schema; what differs is the schema generator (Pydantic, Zod, hand-written JSON Schema in PHP) and the validation idiom (exceptions vs result objects). A streamed partial object needs an incremental JSON parser or the SDK's helper (Python/TS have it; PHP generally does not — fall back to iterable mode or non-streamed). A self-hosted classifier is a separate process in every stack; in a request-scoped runtime it is an HTTP sidecar, never in-process. Logprobs and prefill availability differ per provider and model; the decision file records which the chosen model supports.

**Verify (draft contract):**

1. Every model output that code consumes is produced through the provider's native schema-constrained mode where the chosen model supports it, and is parsed into a typed object before any other code reads it — observer: script — negative: a `json.loads`-style parse of free text, or a regex over the response, on a path that feeds a system — framework: beats
2. Every output schema is a closed object (no additional properties), lists every key as required with optionals expressed as nullable, and uses only features the provider's dialect accepts — observer: script — negative: a schema the provider rejects or that the SDK silently rewrites without a recorded reason
3. Every field carrying a business invariant (totals, ids, dates, quotes, URLs, membership) has a code validator, and a failure yields a message naming the field and the rule — observer: script — negative: a parsed object used while a known invariant is violated, or a bare "invalid"
4. Re-asks after a validation failure have one owner, carry the validator's message, are capped (default one) and are counted in the usage log; the library never re-asks for a schema violation the provider guarantees against — observer: script — negative: an unbounded re-ask loop, two layers re-asking, or a re-ask with no attempt count in the log — framework: beats
5. The three non-schema terminations — refusal, truncation at the output limit, provider error — reach the caller as typed results from named branches, never as a parse exception — observer: script — negative: a refusal or a truncated output that raises a JSON error
6. Where an output decides a branch (a label, a route, a gate, a score), the decision is an enumerated field with an explicit "none/unknown" option, any numeric score has at most five levels or is read as a probability, and the eval reports per-class consistency over at least five runs — observer: script — negative: a free-text label, a forced choice with no out, or a 1–10 score used as a probability
7. Every guardrail in the product has a row in the policy file with checkpoint, tier, on-fail action, fail-open/closed, time budget and placement, and guards on tools with side effects are placed blocking — observer: Martin — negative: a guardrail in code with no row, a row with no on-fail action, or a parallel guard on a send/pay/publish
8. (full) The known-bad fixture runs in CI against the input and output checkpoints and every item is caught by its stated action or recorded as a known gap — observer: script — negative: a fixture item that passes silently
9. Where the model drives the interface, it emits data (a schema or a declarative spec) that a renderer maps to components through an explicit allow-list which rejects unknown types, and any model-written code runs in an isolated runtime with outbound network denied by default — observer: agent — negative: model output inserted as HTML, an unknown component type rendered, or generated code with network access it was not granted
10. Each call logs the schema's version beside the prompt's version, and a schema change goes through the same header, eval and commit as a prompt change — observer: script — negative: a schema edited with no version bump or eval record

### 7.5 Glossary entries to add (`principles/00-glossary.md`)

- **Structured outputs / constrained decoding.** A provider feature that masks the model's next-token choices so the output must conform to a supplied JSON Schema (or a strict tool schema); guarantees the *shape*, not the correctness, calibration or absence of a refusal or truncation. Pokrass (2024-09); OpenAI and Anthropic docs (read 2026-10-01).
- **JSON mode.** The weaker predecessor: output constrained to valid JSON, keys and types left to the model. Pokrass (2024-09).
- **Strict tool use.** The same constrained decoding applied to a tool's argument schema, so tool names and arguments cannot be hallucinated or malformed; combinable with JSON outputs. Anthropic docs (2026-10-01); Pokrass.
- **Re-ask (validation loop).** Appending a validator's error message to the conversation and calling the model again, capped (usually once), owned by one layer; the mechanism behind Instructor and Guardrails AI. Liu (2023, 2024); Rajpal (2023).
- **Guardrail (runtime).** A check at a trust boundary of an LLM application — input, retrieval, tool call, output, memory, plan — with a tier (rule / classifier / LLM judge), an on-fail action (re-ask, fix, filter, refrain, log, raise), a fail-open/closed policy, a time budget and a placement (blocking or parallel). Rajpal; NeMo Guardrails; OpenAI Agents SDK (2026-10-01).
- **System-one model / decision model.** A model that answers typed questions (choice, score, yes/no) with calibrated probabilities in one forward pass instead of generating text; Jev (Type-Safe AI, 2026-09) is the first product; a fine-tuned encoder classifier or a logprob read over enumerated options is the older form. Witteveen; Boundary; Carpintero.
- **Generative UI.** A model deciding what interface to show: *static* (tool call → developer-built component), *declarative* (JSON spec → component catalogue; A2UI, json-render), *open-ended* (model-written HTML/code in an iframe or isolate; MCP Apps). Declarative is the stated balance; model-written code is untrusted code. CopilotKit (2026-01); Casas (2026-09); Agrawal (2026-09).
- **Prompt injection (direct / indirect).** Instructions that reach the model as data and are followed as commands — typed by the user (direct) or planted in content the model fetches or in a tool description (indirect); structurally possible because the model has no separation between instructions and data, so the control is a trust boundary in code, not a prompt. Carpintero (2026-04); OWASP LLM01:2025.
