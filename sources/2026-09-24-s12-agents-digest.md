# Digest — session 12: Introduction to AI agents

## 1. Context

This is the digest of the 15 transcripts selected in `sources/2026-09-24-market-scan-s12-intro-to-agents.md` (the log). Fourteen YouTube videos and one podcast episode, ≈7.5 hours, read in full on 2026-09-24. Sources span 2024-03 (Andrew Ng, Sequoia) to 2026-09 (IBM "Skills vs MCP vs RAG vs Memory"). The written canon for the same topic (Anthropic *Building Effective Agents*, OpenAI *Practical Guide*, Google *Agents* whitepaper, ReAct, MCP spec…) is catalogued separately and cited where a spoken claim needs checking against text.

Reading rule applied: primary sources (Anthropic ×3, Barry Zhang, Mahesh Murag, Google Cloud, Cursor, Claude) are treated as *what the vendor recommends* — with the vendor's interest noted; the Stanford lecture as *how the field explains it*; Notion (Latent Space) as *what a large production team learned the hard way*; IBM as *tidy taxonomies*, and Caleb Writes Code as *what the mainstream is now saying*, not as authority.

## 2. One-paragraph summary

The market has converged on one mental model: an **agent is a model calling tools in a loop inside an environment, steered by a system prompt** (Barry Zhang, Anthropic), as opposed to a **workflow**, where code fixes the sequence of LLM calls. Every serious source says the same three things: *do not build an agent for everything* (agents are for ambiguous, valuable tasks whose errors are cheap to discover), *keep it simple* (iterate only on tools, prompt and environment before adding orchestration), and *think from inside the model's context window* (read exactly what the model sees; most "agent bugs" are missing context or bad tool descriptions). Tool design is where the practical knowledge is: tools should map to what a *user* would see, not one-to-one to your API; they must be documented like functions handed to a new engineer; they should return human-readable errors, not exceptions; and models should be given formats they already know (markdown, SQL) rather than your internal schema. By 2026 the debate has moved to *how* to expose tools — MCP for narrow, tightly-permissioned agents; CLIs for coding agents because they are context-efficient and self-repairing; skills to package procedures — and to progressive disclosure, because a hundred tool schemas in context slow and dumb the model. Verification, not intelligence, is the limiting factor: an agent only converges if the loop injects a signal (tests, checkers, evals), and "99 % of the time it is a bug in a tool, not the model" (Notion).

## 3. Detailed digest

### 3.1 What an agent is, and when to build one

**Definitions (Anthropic, Feb 2025; Stanford, Nov 2025).** A *workflow* chains a fixed number of LLM calls through code (prompt A → prompt B → prompt C; each prompt narrow, e.g. classify into five categories). An *agent* is a prompt that is open-ended, gives the model tools, and lets the model decide how many steps to take until it reaches a resolution. The workshop-era intuition "everything is an agent" is explicitly rejected. Stanford's lecture 7 gives the same split in academic words: tool calling is one function call with three stages (model emits arguments → code executes → model reads the structured result and answers); an agent adds recurrence and reasoning over the results (the ReAct observe → plan → act loop).

**The three components (Barry Zhang, AI Engineer Summit, Mar 2025).** *Environment* (the system the agent operates in), *tools* (interface to act and get feedback), *system prompt* (goals, constraints, ideal behaviour); then "the model gets called in a loop, and that's agents". Three very different production agents at Anthropic "share almost exactly the same code"; the only two real design decisions are which tools and which prompt. Optimizations (caching the trajectory, parallelising tool calls, showing progress to earn trust) come *after* behaviour is right.

**When to build an agent — the checklist (Zhang).** (1) *Task complexity*: agents thrive in ambiguous spaces; if the decision tree can be drawn, build it explicitly as a workflow and optimise each node. (2) *Task value*: exploration costs tokens; a 10-cent budget per task buys ~30–50k tokens, so a high-volume support flow should be a workflow for the common cases. (3) *De-risk the critical capabilities* first (for a coding agent: write good code, debug, recover from errors); bottlenecks multiply cost and latency, so reduce scope and retry. (4) *Cost of error and of error discovery*: high-stakes, hard-to-detect errors mean limited autonomy (read-only tools, human in the loop), which also limits scale. Coding passes all four, which is why coding agents work: ambiguous, valuable, models already good at it, output verifiable by tests and CI.

**The 2025 → 2026 shift (Erik Schluntz, Anthropic, Oct 2025).** "Agents have taken over from workflows" for tasks where absolute quality matters, because models now respond to feedback and correct their own work; workflows remain right where low latency or a single best-shot answer is wanted. The new hybrid is *workflows of agents*: each step of a pipeline is itself a closed loop (write SQL → run it → see output → iterate → then hand off), instead of a single-shot prompt that silently passes a broken result downstream. Schluntz still insists on *start with the simplest thing* (single-shot, then a Claude Code SDK call, then layers) because observability gets harder with every layer. **Tension to note:** Zhang's March 2025 "don't build agents for everything" and Schluntz's October 2025 "agents dramatically outperform workflows" are both Anthropic; they reconcile as *the default moved toward agent loops for quality-critical work, but the four-question checklist still decides*. Both speakers have an interest in more agent usage; the checklist is the part to keep.

**Andrew Ng's four patterns (Sequoia, Mar 2024).** Reflection (have the model critique and revise its own output — "robust, just works"), tool use (robust), planning and multi-agent collaboration (emerging; "sometimes my mind is blown, sometimes it doesn't work"). Evidence he cites: on HumanEval, GPT-3.5 zero-shot 48 %, GPT-4 zero-shot 67 %, GPT-3.5 *with an agentic loop* above GPT-4 zero-shot. Two durable ideas: a critic can be the same model prompted differently (coder + reviewer), and fast token generation from a weaker model can beat slow tokens from a stronger one because the loop runs more times. Numbers are 2024 and model-specific; keep the pattern taxonomy, treat the figures as historical.

**Google ADK's three agent shapes (Google Cloud Tech, Jun 2026).** *Sequential* (assembly line, predictable, rigid), *reactive* (decide each step, flexible, no plan), *deliberate/planning* (sketch a plan, then execute; for multi-step goals with dependencies). The demo is a generator–checker loop: a planner LLM agent, a validator agent that answers only `OK` or `retry` + reasons, wrapped in a loop agent with max three iterations, outputs passed through shared state under an `output_key`, and each loop wrapped as a *tool* the root agent calls. That is Anthropic's evaluator-optimizer pattern implemented with a hard retry cap and a binary verdict — a good concrete shape.

### 3.2 Think like your agent

The single most repeated practical advice (Zhang ×2, Schluntz ×2, Stanford, Ebbelaar). An agent's whole knowledge of the world at each step is the 10–20k tokens in its context; "we see everything, the model only sees what we showed". Zhang's team spent a week staring at counter-intuitive computer-use trajectories until they *acted as the model*: close your eyes for a minute, blink at a screenshot, decide the next Python call in the dark. Then what the agent needed became obvious (screen resolution, recommended actions, limits). The mechanical version: (a) dump the raw context the model receives — system prompt, tool schemas, tool results — and read it as if you had nothing else; (b) ask the model itself to review it: "Is any instruction ambiguous? Can you follow this? Do you need more or fewer parameters on this tool?"; (c) paste a whole trajectory and ask "why did you decide this here, and what would have helped you decide better?" Schluntz's complementary observation: people write beautiful prompts and then hand the model tools whose parameters are named `a` and `b` with no docstring — "an engineer couldn't work with this either". Ebbelaar shows the same thing at code level: print every tool call's *parameters* (what the model chose to search for) and every *result* (what came back) before optimising anything.

### 3.3 Tool design

This is where the scan added the most that the KB did not yet have.

- **Tools ≈ UI, not API (Schluntz, Oct 2025).** The natural first instinct — one tool per endpoint — is wrong. If reading a Slack thread needs three endpoints (load conversation, user-id → name, channel-id → name), a model given those three tools must make three calls to understand anything; a user sees it rendered at once. Design the tool to return what a person would see, with the surrounding context, in one call. "The model is a user of these things."
- **Document tools as you would for a colleague (Schluntz; Ebbelaar).** The tool description and parameter docs are part of the prompt; they influence the rest of it. Ebbelaar: the docstring is where you also put domain hints ("search for X when the user asks Y").
- **Give the model what it already knows (Notion, Apr 2026).** Notion's first agents used a custom XML that mapped losslessly to their block model and a JSON query DSL that mirrored their internals; the model did not know either, and both had to be prompted in. They replaced them with a Notion-flavoured *markdown* (lossy, simple at the core) and exposed databases as *SQLite* queries — "the models are super good at that". Rule: cater to the model's environment, not to your data model, and expose no unnecessary internal complexity.
- **Return errors, do not raise them (Ebbelaar, May 2026).** A raised exception stops the loop; a returned human-readable error string lets the model read it and self-correct. Add request limits and maximum lines per read so an agent can neither loop forever nor blow its context by reading a huge file. Use `ripgrep` (fast, respects `.gitignore`, skips hidden files) — the same primitives all coding agents use.
- **Fewer, better tools; bucket the rest (Schluntz; Mahesh Murag).** Customers with 100–200 tools split them among subagents so each sees ~20 (Schluntz). Murag: models are fine up to ~50–100 tools, a few hundred for Claude; beyond that use a *tool to search tools* (RAG or keyword search over tool descriptions) or hierarchical groups (read-tools, write-tools) exposed progressively. Stanford cites the same idea as Google DeepMind's *tool selector/router* (two-stage: pick candidate tools by name + one line, then load only their full schemas). This is the same lesson as the Vercel "cut 80 % of tools" case already in the KB.
- **Progressive disclosure of tools is a quality issue, not only a token issue (Notion).** With 100+ tools, "saying hello was thousands of tokens", *and* any engineer adding a niche tool could "nerf the overall model" by making it call the tool too often. Notion rebuilt its harness to disclose tools progressively. A second effect: once tools were described by *goal* instead of few-shot examples, tool ownership could be distributed to product teams, each owning its tool definition and its evals, instead of five people guarding one system-prompt string. Notion also found by accident that two tools with the same name crashed one vendor's model and not another's — name collisions are real.
- **Few-shot examples went away (Notion).** Their agent moved from few-shot prompts to goal-driven tool definitions; "they just instruction-follow really well". Stanford gives the training-side reason: models are pre-trained on so much code that function calling mostly works from the API + a good explanation, and the explanation itself can be iterated by a reasoning model against an eval set of (query → expected tool call) pairs instead of hand-written.
- **Self-improving tool descriptions (Zhang; Murag).** Both foresee models iterating on their own tool ergonomics; Notion's custom agents already "set themselves up" and, on failure, are asked "why did you fail? update your instructions". Zhang's open question — budget-aware agents (time, money, tokens) — is still open in 2026 (Notion prices custom agents by usage and nudges users away from Opus for routine automations).

### 3.4 How to connect tools: MCP, CLI, skills, RAG, memory

**MCP as explained by its product lead (Murag, Mar 2025).** Motivation: the N×M problem between AI apps and tools, modelled on LSP. Three primitives, each with a different *controller*: **tools** are model-controlled (the model decides when to call), **resources** are application-controlled (the app decides what to attach; can be dynamic, subscribable), **prompts** are user-controlled (slash-command-like templates). *Sampling* lets a server ask the client for an LLM completion while the client keeps control of model, cost and privacy. *Composability*: a server can also be a client, so agents chain. Retry/auth logic belongs on the server side, which is closest to the end system and holds the OAuth token. Roadmap items in this talk — remote servers over SSE with OAuth, an official registry, `.well-known/mcp.json`, tool annotations (read vs write), namespacing, streaming, elicitation — have since landed in the spec (2026-07-28 revision, see written canon); treat the talk as rationale, the spec as fact. Murag was candid that observability, debugging and versioning best practices were "still emerging".

**Correction to a corporate explainer.** The Google Cloud Tech MCP video lists "tools, prompts, resources *and context*" as four primitives; the specification defines three (tools, resources, prompts). Keep the video for the API-vs-MCP framing ("APIs were designed for programs that know what they want; MCP for models that reason"), not for the taxonomy.

**MCP vs CLI vs skill — the 2026 debate (Notion; Claude video, May 2026).** Simon Last (Notion): CLIs are attractive for coding agents because they run in the terminal (pagination, cursors), give progressive disclosure for free (`--help`), and are *bootstrapped* — the agent can debug and fix its own tool in the same environment; when an MCP transport breaks, the agent has no browser. MCP is right for a *narrow, lightweight agent without a compute runtime* and when a *tight permission model* matters: "all you can do is call the tools", whereas a CLI raises real questions about token access and exfiltration. Sarah Sachs adds a cost argument: paying a language model to re-negotiate an integration on every call is wasteful when a deterministic CLI call would do; and a quality argument: Notion builds its own search over Slack/Linear/Jira instead of using their MCP servers because retrieval quality drives trajectories, and leaves MCP for the long tail. Claude's official video gives the operational rules: MCP tool definitions sit in context even unused; disable what you do not use (`/mcp`); prefer a CLI (`gh`, `aws`) where one exists; package CLI usage as a *skill* so it loads only when relevant; Claude Code switches to tool-search mode automatically when MCP tools exceed ~10 % of the context window. Notion reconciles the debate: keep an internal abstraction (`tool`, `agent`, `completion`, `integration`) so that MCP is *one integration type* among others and the framework can be swapped — they have rebuilt theirs five times.

**Skills vs MCP vs RAG vs memory (IBM, Sep 2026).** A tidy rule of thumb: knowledge someone *wrote down* → RAG; knowledge the agent *picked up from experience* → memory; a repeatable *procedure* (with judgment about when to stop and escalate) → skill; reaching *out into the world* → MCP. Notion's version of memory is deliberately primitive: no memory concept, "memory is just pages and databases" a human and the agent can both edit.

**Five patterns for connecting agents to tools securely (IBM, Aug 2026).** A ladder: (5) direct connection with the agent's own credentials (no user visibility); (4) OAuth so the tool knows the user — but the agent *impersonates* the user and tokens can live 90 days; (3) same plus MCP as the abstraction layer; (2) token exchange, the agent authenticates itself and acts *on behalf of* the user — both identities visible; (1) a vault holds the long-lived token and issues short-lived credentials to the MCP layer. Parked for session 14 (security) but the "tool auth ladder" belongs in the tool practice as a checklist item.

### 3.5 Agentic RAG

Ebbelaar's framework-free build: three tools over a folder of markdown — `list_files` (glob, relative paths to save tokens), `grep` (regex → file, line, text; production version shells out to `ripgrep`), `read_file` (path confined to the notes directory, max lines) — plus an agent loop (Pydantic AI in the demo, "any framework or your own loop") and a structured output with citations (`file`, `quote`, `line`). Semantic RAG is "not dead": it wins on latency and cost; agentic RAG wins on quality because the loop can self-correct when the first search misses. The LangGraph docs' agentic-RAG graph (retrieve → grade documents → rewrite query or generate) is the framework-side equivalent and is in the written canon. Stanford's lecture frames the two as complementary answers to the knowledge-cutoff problem: RAG injects unstructured documents; tools inject structured, real-time or actionable data.

### 3.6 Verification, evals, and where failures really are

Schluntz (Feb 2025): coding agents work because tests inject signal each loop; "if you don't have some mechanism to get feedback as you're iterating, you're not injecting any more signal, you're just going to have noise"; his "slightly controversial take": the next limiting factor is *verification*, because real code rarely has perfect tests. His advice to developers: have a way to measure results before building; many build in a vacuum and never learn that something simpler would have done. Notion (Apr 2026), at scale: three eval tiers — CI regression tests that must pass within a stochastic error rate, launch *report cards* per user journey (80–90 % to ship), and *frontier headroom* evals deliberately held at ~30 % pass rate ("Notion's last exam") to know where the next model helps; every product team owns its evals, the platform team owns the framework, evals run nightly and a custom agent triages failures. Their Friday ritual: read the P99 most-token-hungry custom-agent transcript and cut tasks. Simon Last: "99 % of the time it's a bug in one of the tools — just fix the bug"; training a model is an implementation detail; the outer loop (velocity and robustness in making tools, harness, verification) is what matters; fine-tuning on your own tools is a bet against frontier capability that has not paid off because tools change daily. Stanford's closing advice: start small, start with the most capable model to learn the headroom, optimise later, read the reasoning chains; "generating code is cheap, judging whether it is correct is the hard part".

### 3.7 Multi-agent and the harness (parked, but relevant)

Schluntz (Oct 2025): *workflows of agents* (sequential closed loops) ≠ *multi-agent* (a parent delegating to sub-agents that run in parallel — Anthropic's research product; Claude Code's subagents that protect the main context from a 10k-token search whose answer is one line). To the model a subagent is a tool that takes a prompt. Claude "makes the mistakes of first-time managers": incomplete instructions to sub-agents; training made it more verbose with them. Failure mode: overbuilt systems that spend their time talking to each other. Zhang (Feb 2025): "in production we haven't even seen a lot of successful single agents" — a useful calibration against 2026 multi-agent enthusiasm. Notion's practical multi-agent: 30 custom GTM agents generated 70 notifications a day; a *manager agent* that can invoke the others and reads an issues database they file into cut it to five — composition through the system of record (databases, webhooks), not a new protocol. Caleb Writes Code's "harness in 8 minutes" (579k views) describes the mainstream 2026 narrative: context summarisation is the failure mode of long tasks (the agent summarises, assumes work is done, and stops), so harnesses run the agent in a *loop with fresh context per task* from a requirements document with strict start/finish rules (the "Ralph" pattern, Anthropic's long-running-agents post). This is consistent with `principles/02-harness-engineering.md` and `practices/session-state/` (progress file, startup routine); the video's claim that the term was coined "in early 2026" conflicts with its use at the LIDR workshop and elsewhere — a trend signal, not a source of dates. The video is sponsored by Cursor.

## 5. What is contested / trade-offs

- **Agent vs workflow default.** Anthropic's own messaging moved between March and October 2025. Practical resolution: workflow when the decision tree is drawable, latency matters or the budget per task is cents; agent loop when the task is ambiguous, valuable, verifiable, and errors are cheap to discover.
- **MCP vs CLI.** Notion (and the Claude video) favour CLIs for coding agents and MCP for narrow, permissioned agents; Anthropic's MCP team naturally favours MCP everywhere. Both agree MCP tool definitions must not sit in context unused. Vendor interest on both sides; the permission-model argument for MCP and the self-repair argument for CLIs are the durable parts.
- **Multi-agent readiness.** Anthropic researchers are bullish (parallel research, tool bucketing); the same people say production single agents were rare in early 2025 and that overbuilt multi-agent systems waste effort. Notion got value from one manager agent over a flat set of workers, coordinated through data, not messaging.
- **Frameworks.** ADK, Pydantic AI, LangGraph, the Claude Code SDK and Notion's in-house abstraction all appear; every source that has shipped at scale says the same: keep the loop simple, own an abstraction over "tool / agent / completion", expect to rebuild it.
