# Structured outputs and guardrails

## 1. The question this answers

When a product needs a model's output to enter code, a decision or a screen — not a person's eyes — how do we get a typed value instead of a paragraph, what does the provider guarantee about that value and what do we still have to verify ourselves, how do we guard inputs, tool calls and outputs at the right checkpoint with the right tier of check, and how does a model drive an interface that is not a chat?

## 2. Short answer

Treat every model output that software consumes as a **typed object produced under a contract**, never as a string that code parses and hopes about. Three layers exist: *prompt-and-parse* (tags, prefill, regex — for models without the feature), *JSON mode* (valid JSON, keys left to the model) and *native structured outputs* — constrained decoding against your JSON Schema, also as `strict` tool schemas — which guarantee **conformance and nothing else**: not correctness, not calibration, and not that an object arrives at all. Design the schema **closed, every key required, optionals nullable, flat, business constraints in validators**, with a **reasoning field before the answer**, an **out** on every enum and a **Maybe shape** instead of a sentinel string. Put the invariants a grammar cannot express into **code validators** with informative messages and allow **one bounded re-ask** carrying the message — one owner, counted in the log. **Decisions are classifications**: a label, route, gate or score is an enumerated field read as a probability (classifier, moderation endpoint, logprobs, or a "system-one" model) with the threshold in code. **Guardrails** are a verification suite at named **checkpoints** (input and output at minimum; retrieval, tool call, memory, plan as autonomy grows), in **tiers** (rules and grounding → small classifier → LLM judge), each with an **on-fail action**, a **fail-open/closed** policy, a **time budget** and a **placement** — side-effect guards **blocking**; prompt-level defences are the cheapest first layer, never the control. For **non-conversational interfaces** the model emits **data a renderer maps to components** through an **allow-list that rejects unknown types**; model-written code is **untrusted code** run isolated. Prompt templates are confirmed, not changed.

## 3. Long explanation

### 3.1 The three layers, and what each one guarantees

**Why the layer exists.** Jason Liu's 2023 keynote (`yt-yj-wSRJwrrc…`, AI Engineer, 2023-11): most applications "are just ones when you're asking a language model to output JSON… that you're parsing with a regular expression". Michelle Pokrass (OpenAI; Latent Space, 2024-09, `podcast-NjOfH9D8aJo…`), the provider's reason: "if something is 95 % reliable but you're chaining together a bunch of calls… it makes your application not work".

**Layer 1 — prompt and parse.** Zack Witten's workshop (Anthropic, AI Engineer World's Fair, 2024-06, `yt-hkhDdcM5V94…`): an **assistant prefill** ("putting words in Claude's mouth" — the opening `{`), tags extracted with a regex, the closing tag in **`stop_sequences`**. Still correct for models without constrained decoding; Anthropic's structured-outputs page (read 2026-10-01) states prefill is **incompatible** with JSON outputs, so prefill is the fallback, not the default.

**Layer 2 — JSON mode.** OpenAI's 2023 Dev Day feature (Pokrass): "you basically will always get something in a curly brace", but keys and types remain the model's choice — "you don't want the model to kind of make up the keys". Useful only when you *want* the model to invent a schema.

**Layer 3 — native structured outputs (constrained decoding).** The engineering half masks "the available tokens that are produced every time to only fit the schema"; the research half trains the model so the constrained path is also the natural one; the first request with a new schema pays a one-time compile (Pokrass). Both canon pages say the same in 2026 — "No need to validate or retry incorrectly formatted responses" (OpenAI), "no retries needed for schema violations" (Anthropic; both read 2026-10-01, the OpenAI fetch summarised — digest §1, §4); parameter names and the SDK call are in `practices/structured-outputs/schema-design-rules.md` and `structured_call.py`.

**Guaranteed is conformance, not correctness — and there are cases where even conformance does not hold or no object arrives.** Pokrass: "the guarantees is that they fit the schema but the schema itself may be too broad… you might give me zero, give me 12" for a 1–11 range. Anthropic's page: a **refusal** (`stop_reason: "refusal"` — HTTP 200, billed, no object), **truncation** at `max_tokens` (no complete object), and **enum casing** not guaranteed (an object arrives; compare case-insensitively). A client therefore has five branches — `ok`, `refusal`, `truncated`, `invalid` (a validator failed after the one re-ask) and `error` (transport) — and none is a JSON parse exception (`practices/structured-outputs/structured_call.py`).

**Function calling versus response format.** Same mechanism, different training and purpose: "use function calling when you actually have functions that you want the model to call" (Pokrass); "JSON outputs control Claude's response format (what Claude says). Strict tool use validates tool parameters (how Claude calls your functions)" (Anthropic) — combinable in one request, `strict: true` per tool, and constraining removed hallucinated tool names (Pokrass). Horthy's 12-Factor Agents (`yt-8kMaTybvDUw…`, reused from s3) is the bridge to `21-agent-design-and-tools.md`: a tool call *is* a structured output that code dispatches; "it's just JSON and code".

**The schema dialect, by design.** Strict schemas are a deliberately small dialect of JSON Schema — closed objects, every key required, optionals as a union with `null`, numeric and length constraints in validators, hard limits on tools, optional and union parameters, a 24-hour grammar cache that forbids PHI in schema definitions, and a cache break on every schema change (Pokrass; Anthropic page read 2026-10-01) — so the stack-neutral rule is *flat, few optionals, business constraints in validators*; the dated limits are in `practices/structured-outputs/schema-design-rules.md`.

**The schema is a prompt.** "When you have docstrings the docstrings are now a part of that JSON schema" (Liu 2023). Pokrass's official places for instructions are the **system message** (*when* to produce a shape) and the **field or function description** (*how*: "do you want year-month-day or backwards"); naming a key by what you want (`brainstorm_a_list_of_up_to_five_topics`) is swyx's habit, which Pokrass calls "the fun nature of this", not an official recommendation. The KB's tool-description rule (`21-agent-design-and-tools.md` §3.4) extends unchanged to output schemas.

**Chain-of-thought as a field; streaming; plans.** The **reasoning field comes before the answer field** (Liu's switchable sub-model field; Pokrass's `steps` before the final answer; Witten's judges) — the schema-level form of `10-llm-api-fundamentals.md` rule 2. Liu's 2024 API (`yt-pZ4DIH2BVqg…`) streams *iterable* or *partial* objects; a structured route therefore streams **typed partial objects, not text deltas** (`12-llm-gateway-layer.md` §3.3). Both Liu talks end on the model emitting a DAG or a list of typed requests that classical code executes; Samuel Colvin (Pydantic; Latent Space, 2025-02, `podcast-7wwWRph3Jls…`) defines an agent as "a system prompt, some tools and a structured return type": *the structured output is the hand-off format between the model and the executor*.

### 3.2 Validation beyond the schema, and the bounded re-ask

A grammar cannot express an **invariant**: line items sum to the total; every quoted substring exists in the source chunk ("not by asking it to not hallucinate but actually trying to figure out… what the quotes were"); every URL returns 200; an owner is one of the participants (Liu 2023, 2024; Instructor front page read 2026-10-01). These live in **code validators** on the parsed object. On failure the **error message is appended to the conversation** and the model is asked again — "it is the error message that is part of the prompt but conditionally added" — capped: "often one retry… basically enough and really all you care about is having good, well-written, informative error messages" (Liu).

Two rules on the *order* of layers. **Native constrained decoding for the shape, code validators for the meaning**: a library that re-asks for schema violations on a provider that guarantees the schema pays twice — swyx reports "55 % of API cost… because of we saved on the retries" after replacing Instructor with native outputs (one pipeline; the figure stays in the digest's §4), and Pokrass: "we are not retrying, we're doing it in one shot". **One owner of re-asks**, as `12-llm-gateway-layer.md` §3.2 has one owner of retries: cap of one, counted in the usage log, and on failure a typed `invalid` result carrying the message — never a third attempt, never an exception from a handler (`practices/structured-outputs/validation-and-reask.md`).

**The "Maybe" pattern** (Liu 2023): `MaybeUser {result: User | None, error: bool, error_message: str}` instead of "return I DON'T KNOW in all caps" — the schema-level form of "give the model an out" (`failure-modes-and-mitigations.md` row 7); the provider's refusal field is the same idea one level down. Rajpal's *provenance* validator (AI Engineer, 2023-11, `yt-9-vGxMoUM9Y…`) and Liu's substring-quote validator implement row 1 of the failure-modes table — *the anchor is checked in code*. Since s6 the anchor can be a page and a bounding box: layout-first parsers supply both per element (Docling, `yt-zSA7ylHP6AY…`; Reducto, `yt-ybzR4LBY0Lo…`), so a provenance validator may check that a cited region exists (`16-data-for-ai-products.md` §3.3).

### 3.3 Guardrails — checkpoints, tiers, on-fail actions, placement

**The paradigm.** Rajpal's *trust, but verify*: "every output that you get back passes through a verification suite… only use large language model outputs if your verification suite passes; on failure… hook into… their ability to self-heal" within a latency, dollar or token budget; prompting "doesn't act as a guarantee". The Guardrails AI README (read 2026-10-01) keeps the shape: **validators** with an `on_fail` action each (Rajpal enumerates **re-ask, filter, fix, fallback, refrain, noop-and-log**), input *and* output guards.

**Where to check — the checkpoints.** NeMo Guardrails (read 2026-10-01): **five rail types** — input, retrieval, dialog, execution (tool calls), output — plus an agentic list (isolate credentials from the LLM, sanitise tool inputs, rail tool calls, monitor behaviour). Diego Carpintero (AI Engineer, 2026-04, `yt-YZHPEkfy2kc…`): "check at least for the user inputs and the model responses; but ideally… retrieval augmentation, MCPs, and also within our context memory and agentic plans". Rohit Bhardwaj (Developer Summit, 2026-06, `yt-v9wFSDSjb_c…`) adds the **tool allow-list with per-agent, per-day, per-amount and per-tenant limits**. One picture: *checkpoints at the trust boundaries — input, retrieval, tool-in, tool-out, output, memory, plan — each with its own check and failure policy* (`practices/structured-outputs/guardrail-policy.md`, closing the s3 park on `practices/llm-gateway/routing-policy.md` §Guardrails). The s6 sources add a checkpoint *before* the runtime ones: **ingestion** — "PII filtering must happen before sensitive data gets embedded, indexed, cached, copied" (Gambill, 2026-06, `yt-tkFr-4r906Q…`), with masked values kept in "a PII reversible dictionary… so that you can unmask it" in the reply (Huyen, 2024-07-25, `huyen-genai-platform.md`). Row G0 of the policy; detector tiers and the "no guarantee" warning: `16-data-for-ai-products.md` §3.6.

**How to check — the tiers.** Rajpal's ordering, confirmed by Carpintero: (1) **ground in an external system** (text-to-SQL executed against a sandbox "substantially improved the correctness"); (2) **rules and heuristics**; (3) **small, high-precision classifiers** — "you don't need a jackhammer to crack open a walnut"; (4) **LLM self-reflection** last. Carpintero's tier-3 recipe is a fine-tuned small encoder, self-hosted and retrainable in hours, against a judge that "can easily compound into… seconds of latency"; his numbers, the model name and the solo-operator opinion are in `practices/structured-outputs/guardrail-tiers.md`. The eval side confirms the split (s5): Yan's decision tree runs an LLM with reasoning as an *evaluator* offline on a few hundred samples and fine-tunes a classifier bootstrapped on those labels as the *guardrail* online (`eugeneyan-llm-evaluators.md`, 2024-08; `14` §3.2).

**Placement and failure policy.** The OpenAI Agents SDK page (read 2026-10-01) is the worked example — input guardrails on the first agent, output guardrails on the last, tool guardrails around each guarded invocation, a parallel-or-blocking choice for input guards, a tripwire that halts, a rejected output excluded from the session and a rejected tool output replaced by a data-free placeholder; the column definitions and the placeholder text are in `practices/structured-outputs/guardrail-policy.md` (Placement, On-fail, rules 4–5). The rule: *checks that guard side effects run blocking at the tool boundary; text guards may run parallel on non-streamed routes (Twilio, s3); every check names its action on failure.*

**Why prompt-level defences are a layer, not a guarantee.** Carpintero's survey of the attack vectors (rows T11–T20 of `practices/security-baseline/threat-model-agentic.md`) rests on one sentence: "LLMs have no native separation of concerns between the system controls and the data"; alignment is "a probabilistic preference, not a hard constraint". Bhardwaj's sandwich defence and XML-tagging are the *cheapest first layer*; guarantees live outside the model (`10-llm-api-fundamentals.md` §3.1 rule 4). Jarmul (2026-01, `yt-lz0L0rRV7RE…`): "use guardrails but they're not going to save you". Depth is parked for session 14.

**Prompts and policy files as code; confidence-gated approval.** Bhardwaj: the system prompt and a per-domain policy file are **committed, reviewed and gated in CI** with injection and retrieval tests (`practices/structured-outputs/guardrail-fixture.md`); and "if you have a low confidence, have human in the loop… give them like one hour or two hours just to validate… if it is correct, agent will automatically send it out" — rule 2b of `practices/verification/dry-run-and-approval.md`.

### 3.4 Decisions versus generation — calibration, classifiers, system-one models

**Most decisions inside software are classifications, and a generative model is the wrong tool for them.** Pokrass: "we often recommend using log probs with classification tasks… you can just do ABCD and get the log probs… a non-calibrated model might always pick seven". Witten, on a 1–5 grader: "I don't think it's very well calibrated… limit the granularity to maybe five different classes", reasoning *before* the grade; log-probabilities after a chain of thought need prefill and logprobs in one API, which few models offer. The rules: a generated score is a **written token, not a probability**; **at most five classes**; **reasoning field first**; **logprobs over enumerated options** where the API allows; **per-class consistency over at least five runs** (`05-verification-loops.md`; `practices/structured-outputs/decision-vs-generation.md`). Refined 2026-10-01 from the s5 scan: for a **grader** (an eval judge) the default is **binary per failure mode** with an `unknown` out, and the five-class allowance is for a *graded decision* only (Husain and Shankar 2025-09; Yan 2024-08; Anthropic's agents post 2026-01); and **a tool's 0–1 score with a default threshold (DeepEval's `GEval` at 0.5, read 2026-10-01) is uncalibrated until that threshold has been checked against human labels** — a Likert scale in disguise (Lucas, Nova Escola 2026-07) — `14-evals-and-error-analysis.md` §3.2.

**System-one models — a dated trend.** Jev (Type-Safe AI, out of stealth 2026-09; Witteveen's test `yt-X117w2Rark8…`; discussed by Boundary in `yt-35PSMmDDKP8…` — Boundary ships a client, it does not make it) answers **typed questions** (choice, score, yes/no) with real probabilities in **one forward pass**; it cannot generate, reason or call tools, and "cannot hallucinate" means only that it stays inside the option set. The KB records the **pattern** — decisions go to a discriminative or probability-returning model, a tier below the cheapest chat model in `08-model-selection.md` — as new and the **product** as parked: re-evaluate after 2026-12 with a 20-case eval; prices and relayed accuracy figures are not carried (digest §4). Decomposition and thresholds in code: `practices/structured-outputs/decision-vs-generation.md` rules 2–6.

### 3.5 Non-conversational interfaces — generative UI as a structured output

Ruben Casas (Postman; Agent Conf 2026, 2026-09, `yt-DLEPGhA4NJQ…`): "the GUI has not been invented"; Harshil Agrawal (Cloudflare; dotJS 2026, 2026-09, `yt-iymZjaNcwc8…`): a chat agent over an admin dashboard produced unreadable "text blurb". **Three tiers**, named almost identically by CopilotKit (2026-01, `yt-Z4aSGCs_O5A…`) and Casas: **static** — a tool call mapped to a developer-built component (pixel-perfect, but "the codebase is going to grow linearly with your use cases"); **declarative** — a JSON description rendered through a constrained component catalogue: "the structure of the content is non-deterministic but the actual rendering of it is deterministic… probably the best balance" (Casas); **open-ended** — model-written HTML or code in an iframe or isolate: "render anything", at the price of predictability, cost and a security surface. Protocol names and precedents: `practices/structured-outputs/generative-ui-decision.md`. **Position taken (opinion, for Martin's shapes):** declarative by default, static for the well-trodden paths, open-ended only in a sandbox for consume-and-discard visualisations. The shared artifact with **bidirectional typed state** (CopilotKit's AG-UI demonstrations; Casas) extends `12-llm-gateway-layer.md` §3.6: *the UI consumes typed events and typed state, never free text*. UI protocols are parked for session 13.

**Model-written code is untrusted code — Agrawal's three questions.** The model writes a function that fetches through a *typed tool* (never SQL) and returns a **description of the UI**, never HTML or JSX. **What can the code access** — only the tools given, each enforcing its schema; **what can it do while running** — it runs outside the app in a V8 isolate with outbound network `null` or allow-listed and a CPU limit; **what comes back** — schema validation on the server and in the browser, a `switch` over known component types, an unknown type not rendered ("the last defense point"). "Treat it as an untrusted code… run the model-written code outside your app." Decision file: `practices/structured-outputs/generative-ui-decision.md`; sandboxing depth belongs to session 14.

### 3.6 Structured prompts and dynamic templates — confirmed, with four sharpenings

Witten (2024) and the reused *Prompting 101* (2025-05) confirm `10-llm-api-fundamentals.md` §3.3 and sharpen four points: (1) placeholder syntax is tooling, the *static/dynamic boundary* is the rule; (2) tags for sections, and instructions "are more tightly followed the closer they are to the bottom of the prompt"; (3) **examples are the biggest lever** — "picking the perfect document… more important than everything else that I've said combined"; (4) **do it in code** — "when you can offload stuff to code… just do that" — `02-harness-engineering.md`'s "mechanism over prompts" applied to the prompt. From Colvin (2025-02): unit-test a call **with a mock model that returns a typed object**; live-model smoke on every commit to `main` (`05-verification-loops.md`); his view that smarter models need less structure is opinion — structure for *integration* may shrink, structure for *safety* does not (digest §5).

## 4. How to apply it in a repo

The Verify of `practices/structured-outputs/README.md`, in order; the practice is `draft` and **unrouted** until the routing gate of `decisions/0004-day-one-for-blank-and-existing-repos.md` §6.

1. Confirm `llm_calls` (`practices/facts.md`); find every place where code consumes a model output (`json.loads` or a regex over a response is the symptom).
2. Route every such output through one structured module (`structured_call.py`): native schema-constrained mode, a typed object with the five result branches before any other code reads it.
3. Schemas by `schema-design-rules.md`; a code validator per invariant and one re-ask owner with a cap of one (`validation-and-reask.md`); library schema-level retries set to zero.
4. Every output that decides a branch follows `decision-vs-generation.md`: enumerated options with an out, probabilities not written numbers, thresholds in code.
5. Write `guardrail-policy.md` — one row per guardrail, side-effect guards blocking, versioned beside the prompts; in the full part, the fixture from `guardrail-fixture.md` runs in CI.
6. If the model drives an interface, decide the tier per screen with `generative-ui-decision.md`; the renderer is an allow-list; model-written code runs isolated.
7. Version each schema beside its prompt; a schema change goes through the same header, eval and commit as a prompt change and, on Anthropic, breaks the prompt cache (`11-runtime-context-management.md` §3.3).

## 5. Anti-patterns

- `json.loads` (or a regex) on free text, on a path that feeds a system.
- A library re-asking for *schema* violations on a provider that guarantees the schema — paying twice; two layers re-asking at once.
- A numeric, length or `pattern` constraint in the schema relied on as the only check instead of a validator; an open object or optional keys left to the default.
- A 1–10 score read as a probability; a free-text label; a forced choice with no "none/unknown".
- An LLM judge as the only gate on a send, a payment or a publish; a parallel guardrail on a tool with side effects.
- A guardrail in code with no row in the policy file, or a row with no on-fail action.
- `dangerouslySetInnerHTML` of model output; a renderer with a default branch that renders unknown component types; generated code with network access it was not granted.
- Prefill together with native JSON outputs (Anthropic: incompatible); PHI or personal data inside a schema definition.
- A schema edited with no version bump or eval record.
