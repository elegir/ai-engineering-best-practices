# Memory, external context and permissions

## 1. The question this answers

When a product must remember across turns and sessions, read files and the web, and act with tools: what is stored, how it is written, consolidated, forgotten and scoped; what the provider does for you and under which tenancy rules; and how an identity's permissions follow it from the request through retrieval to the tool call and the approval?

## 2. Short answer

**Memory** is a store the application owns, in three types — **semantic** (facts), **episodic** (events), **procedural** (instructions) — and two scopes — **thread state** (the session, principle 11's problem) and **cross-session namespaces** per user or tenant. Writes go **extract → consolidate**: candidate facts from an exchange meet their nearest existing units and a *reasoning* model decides **add / update / forget / noop**, off the response path. Reads are **bounded**, **labelled by type** and **filtered by identity before ranking**. **Forgetting is a status with a trail** (recency × relevance × importance decay or an explicit retraction), plus an **erasure path** where the law requires one. The model's *interface* may be files or file-like commands; the *substrate* behind a multi-user handler is a namespaced store with concurrency and audit. **External context** increasingly comes from provider tools: files by `file_id` with the **workspace as the tenant boundary** (never a `file_id` from a user), **web search** with domain lists, `max_uses` and provider-side filtering, and results **echoed back unchanged**; MCP servers admitted by review. **Permissions** are three mechanisms, not one: an **identity per agent** (and, as this KB's extension, a narrower one per spawned sub-agent) with just-in-time, short-lived credentials; **authorisation at retrieval** (pre-filter or post-filter by hit rate; memory as a namespace the query carries); and **validation and approval next to the tool that creates the side effect** — an approval being a paused run with serialised, resumable state that **fails closed** on timeout.

## 3. Long explanation

### 3.1 Taxonomy — what memory is, and what it is not

LangChain's concepts page (`langchain-memory-concepts.md`, read 2026-10-01) draws the first line: **short-term memory** is thread-scoped — the message history and per-conversation state persisted by a checkpointer — and its problem is `11-runtime-context-management.md`; **long-term memory** is cross-thread, saved under **namespaces** (user, organisation, context) as JSON documents searchable by filter and similarity. The three types come from the CoALA paper via that page: **semantic** (facts about a user), **episodic** (past actions — "often implemented through few-shot example prompting"), **procedural** (the agent's instructions — "more common… to modify their own prompts" by reflection than weights or code). Richmond Alake (`podcast-CDadnSE7Eww…`, 2026-04) maps a fourth onto runtime parts: working memory → the window or a scratchpad; semantic → the knowledge base; episodic → anything timestamped; procedural → "skills… we have skill MDs now".

Two shapes for semantic memory (LangChain): a **profile** — one JSON document regenerated or patched, simple and showable, "error-prone as it grows", kept valid by strict decoding (`13-structured-outputs-and-guardrails.md`) — or a **collection** of small documents, higher recall, but "the model must now delete or update existing items… some models may default to over-inserting and others… to over-updating". Two moments to write: "in the hot path" (immediate, transparent, one more tool and some latency — ChatGPT's `save_memories`) or "in the background" (no latency, but a trigger policy). Michel Tricot (`podcast-tYJmgpIEd-Y…`, s2, reused) is the null hypothesis worth keeping: "memory is a form of context… data that is going to land somewhere in your agent and you have a way to query it, update it" — the taxonomy is a design aid, not a different substance. Decision file: `practices/memory-and-permissions/memory-design.md`.

### 3.2 The write path — extract, consolidate, forget

**Extract, then consolidate (Mem0).** Prateek Chhikara on the 2025-04 paper (`yt-cHQyugatz6M…`, AAIF reading group, 2025-06; abstract `mem0-arxiv-abstract.md`): on each exchange the **extraction** call sees a running summary (generated asynchronously), the last *m* = 10 messages and the new pair, and emits candidate memories; the **update** call retrieves the *s* = 5 most similar existing memories per candidate and asks the model to choose **ADD / UPDATE / DELETE / NOOP**. Three model calls per turn, one off the critical path; `add` can be asynchronous, `search` cannot. Two engineering findings matter more than the benchmark: the update step "requires reasoning between the existing and the new memories" — a small *reasoning* model instead of a small chat model gave "a huge performance improvement"; and extraction prompts are **use-case specific** — the platform asks for a use case, a memory style and **include/exclude lists** so order ids are kept and SSNs are not. The graph variant (triplets, merged duplicate nodes "SF and San Francisco", merged redundant edges "likes" and "loves") "we do not recommend… to all of our users" — social-relationship cases only — and roughly doubles tokens; bulk import uses `infer=false`. The abstract's LOCOMO numbers are the vendor's on ten companion-style conversations; the mechanism is what this KB keeps (digest §4). Reference: `practices/memory-and-permissions/memory_store.py`.

**Stateful agents and sleep-time consolidation (Letta).** Charles Packer (`yt-sgD-sw0RW78…`, 2025-07): agents "don't really have the capability to learn", so they are run once and thrown away; a stateful agent "persist[s] indefinitely". MemGPT's mechanism — the model edits its own memory with tools — is what every chatbot's memory feature now does; the next step is **consolidation**: atomic facts rewritten into one sentence, "memories are more than a sum of their parts", because raw memory is "the most random stuff". It runs **at sleep time** — a background agent, "the subconscious brain of the main agent", that rewrites memory, reads uploaded documents and indexes a codebase while the user is away, removing the synchronous "hold on, I'm going to write to my memory" latency. Kept as **opinion with a kernel the KB accepts**: OpenAI's agent definition (model, instructions, tools, runtime) "doesn't have state", and "the lifetime of the agents are much longer than the lifetime of the models" — state lives in storage you own. Bilt's "over a million agents" is a vendor figure. Manus's explicit memory (`yt-6_BcCthVvb8…`, s2, reused) is the **user-confirmed** variant — "here's what I learned… would you like to accept it or reject it?" — the right shape for procedural memory.

**Forgetting is a status, not a delete (Alake).** "Think memory first": "every piece of information [is] something to be remembered or forgotten", so every **memory unit** carries the attributes that make it recallable *and* forgettable. "You don't delete information in memory engineering. You forget" — human-like, and it serves audit in finance. His one concrete mechanism is the Stanford *Generative Agents* (2023) score — **recency × relevance × importance** — so unreferenced memories decay out of retrieval without being destroyed (verify the paper's exact form before tuning — digest §4); the reference `memory_store.py` reads "importance" as how many later units depend on a unit (raised when it is a neighbour of a new candidate or is superseded), an implementation choice, not Alake's definition. **The erasure caveat (position, opinion):** forgetting with a trail is the default; where `personal_data` or `regulated` holds (`practices/facts.md`), a documented **erasure path** removes the unit and its trail on request — audit and the right to erasure are different duties and a product may owe both. The path has more than one stop (s6): "did the vector index retain anything? Did [caches] retain anything? Did evaluation data sets retain anything? And what about those logs?" — "test deletion like you're testing your recovery" (Gambill, 2026-06, `yt-tkFr-4r906Q…`); `practices/data-ingestion/` Verify 7 and `privacy-compliance-checklist.md` §5.

**Position across the three (opinion, for Martin's shapes).** Mem0's pipeline, Letta's model-edited state and Anthropic's client-side tool (§3.3) disagree on *who triggers the write*; the write path is extract → consolidate regardless. A tool-triggered write suits agents working across sessions on their own tasks; a background pass suits user-facing memory where latency and quiet matter; the application owns scoping, validation and forgetting in both (digest §5).

### 3.3 Storage, retrieval and the provider's memory tool

**Memory engineering vs context engineering.** Alake's boundary is the one this KB adopts: the storage side — retrieval strategy, indexing, data model, "the forget logic" — is **memory engineering**; inside the window — budgeting, just-in-time retrieval, composition — is **context engineering**. A summary put back in the window is context engineering; the original moved to a store with an id and a description for later fetch is memory engineering — Manus's compaction-vs-summarisation split restated (`11` §3.2). **Memory-aware agents** segment the window by type, each prefixed with its purpose, including a *workflow memory* of the steps taken — the labelled block of `memory_store.py`'s `as_prompt_block()`.

**Files vs database.** Alake argues against "files are all you need": a proof of concept may use files, production needs "scalability… ACID transactions… auditability" — followed by "Oracle AI database is all you need", a joke, then meant. The KB's own sources point the other way (Claude Code's files, Manus's sandbox, Anthropic's file-shaped tool over any store). **Resolution (digest §5):** the model's *interface* is files or file-like commands; the *substrate* for a multi-user product is a namespaced store with concurrency and audit; a single-user agent can keep real files. "One database for everything" is the vendor's preference. Row added to `practices/context-management/context-store-decision.md`.

**Anthropic's memory tool** (`anthropic-memory-tool.md`, read 2026-10-01). A **client-side** tool: the model issues file-like commands under `/memories` and **your application executes them against storage you control**; the API adds an instruction that makes the model read its memory directory first and write as it goes, assuming the context may be reset at any moment. Security is the handler's job — path validation against traversal, sensitive-data stripping before writing ("Claude usually refuses… for stronger guarantees, add validation"), size caps, expiry of unused files. Its relation to s2 is stated by the page: pair it with **compaction** — "compaction keeps the active context small without client-side bookkeeping, and memory preserves the information that must survive summarization" — the provider-side form of *offload* (`11` §3.2). For multi-session software work, an initializer session writes a progress log and a feature checklist, each session reads them first and updates them last — the provider-side form of `practices/session-state/`. The commands, the SDK helpers per language and the duties as a checklist: `practices/memory-and-permissions/memory-tool-handler-notes.md`.

**The cross-session eval.** Alake names LongMemEval, LoCoMo and MemBench as the benchmarks a unit's attributes are "evaluated against"; Mem0 reports on LOCOMO. The s2 long-session eval tests turn N+1 *within* a session; memory fails *across* sessions, so `practices/context-management/context-metrics-and-evals.md` §2 gains the case (a fact from session 1 recalled, a contradicted fact updated, in session N; five runs) and `practices/memory-and-permissions/memory-eval.md` holds the four minimum cases, run through `practices/evals/eval_harness.py` (`14-evals-and-error-analysis.md`). A public benchmark is read in full before it is cited (scan log, s5 validation pass).

### 3.4 External context — files, web, MCP

**Files API** (`anthropic-files-api.md`, read 2026-10-01). Upload once, reference by `file_id`. The security paragraph is the finding: "Uploaded files are accessible to your entire workspace, not scoped to an end user, conversation, or session… **Never accept `file_id` values from end users**… create a separate workspace for each tenant. **The workspace is the isolation boundary**". Rule: a `file_id` is a server-side reference the application resolves from its own table; one workspace per tenant; expiry is a lifecycle feature, "not a guaranteed-deletion control". In the threat model this is **T21** (`practices/security-baseline/threat-model-agentic.md`). Limits, prices and the audit feed, dated: `practices/memory-and-permissions/external-context-notes.md` §1.

**Web search tool** (`anthropic-web-search-tool.md`, read 2026-10-01). Server-side; the model decides when to search, steerable by prompt and capped per request; domain allow- or block-lists. **Dynamic filtering is the s2 *reduce* operation done by the provider**: "Claude instead writes and runs code that filters the results first, so only relevant content reaches the context window" (`11` §3.2). Client duties: result blocks are **sent back unchanged** on later turns; citations shown to end users; errors read inside a successful response; results count as input on every later turn. The eval is Anthropic's balanced should-search / should-not set (`14` §3.3). These are **provider server tools** — no transport to run; the controls are request parameters — a row in `practices/agent-patterns/tool-transport-decision-table.md`. Versions, parameter names, error codes and price, dated: `practices/memory-and-permissions/external-context-notes.md` §2.

**MCP as the external-context transport** (Angie Jones, Block, `podcast-O7etCBod2IY…`, 2026-01). Her answer to "fancy function calling": MCP's value is cross-system workflows "that couldn't have happened on your closed machine" — an incident report that pages a human while a GitHub-connected agent opens a PR; an agent in Slack that reads a thread, proposes three fixes and implements the chosen one. This does not contradict Notion's s12 position (CLIs for coding agents, MCP for narrow permissioned agents — `21-agent-design-and-tools.md` §3.5): her examples are all narrow, hosted and permissioned. The Council of Mind demo uses MCP **sampling** — the server borrows the user's model for nine persona calls — the primitive `21` §3.5 lists; depth parked for session 13.

### 3.5 Permissions — identity, retrieval, the tool boundary

**Zero trust restated for agents** (IBM, `yt-d8d9EZHU7fw…`, 2026-02). Kept because the bullet has no conference talk of its own and the vocabulary is standard: **verify, then trust**; **just-in-time, not just-in-case** ("only when they're needed, and not for longer than they're needed"); **pervasive controls**, not "the hard crunchy outside and the soft, chewy center"; **assume breach**. For agents: agents spawn agents and use many **non-human identities** (NHIs), all of which get "the same level of control and visibility that we had for the human users" (IBM's statement); that each spawned sub-agent gets *its own, narrower* identity rather than the parent's is this KB's extension (opinion), not IBM's words; **no static credentials** — a vault issuing dynamic, short-lived ones; a **tool registry**; an **AI gateway** inspecting inputs and outputs; **immutable logs**; a human with a **kill switch**, **throttles** and **canary deployments**. The register gains the columns "identity the tool runs as (NHI) and credential lifetime" (`practices/security-baseline/mcp-trust-register.md`); T9 gains the vault rule. Depth (vault, NHI lifecycle, gateway) parked for session 14.

**What a regulated company did** (Block, Jones). Goose, Block's open-source MCP client, reached about 12,000 employees (her figures; promotional); the controls carried: an **allow-list of MCP servers** — "if it's not on that allow list… the agent will say nope, can't install it" — admitted only after a security review, most built in-house, "only a handful" from vendors; **tool annotations** marking a tool *destructive* and a toggle so the agent runs non-destructive tools freely and "if you run into one that is, you need to ask my permission first, like give me some insight into what this is"; **OAuth against the company identity provider** instead of API keys and scopes; a red team that found **invisible characters** hidden in shareable "recipes" (bundled instructions, prompt and servers — T15/T16). This becomes the permission model of the MCP branch in `21` §3.5.

**Approvals in the SDK** (`openai-agents-guardrails-approvals.md`, read 2026-10-01). The decision table: block disallowed requests → **input guardrails**; validate or redact the final output → **output guardrails**; check arguments or results around a function → **tool guardrails**; "pause before side effects like cancellations, edits, shell commands, or sensitive MCP actions" → **approvals**. An approval is a tool declared as needing approval; the run "records an approval interruption instead of executing the tool", returns the interruptions plus a **resumable state**, the application approves or rejects, and the run resumes *from that state* — "if the review might take time, serialize state, store it, and resume later. That's still the same run"; it holds inside handoffs and nested agent-as-tool calls. The boundary rule, adopted verbatim: "don't rely only on agent-level input or output guardrails. **Put validation next to the tool that creates the side effect.**" The cybersecurity paragraph is the strictest check in the module: compare "the proposed target, action, tool arguments, calling identity, and engagement window against the approved scope", give the reviewer "only the context needed", pause ambiguous actions, and **"fail closed if review times out or becomes unavailable"** — the default `practices/verification/dry-run-and-approval.md` rule 2b already chose; 2b now also carries the serialised-state rule, and `guardrail-policy.md` G4 the note.

**Authorisation at retrieval** (Pinecone, written by AuthZed's Sohan Maheshwar, `pinecone-rag-access-control.md`, 2026-01-08). "If different users have different levels of access to data… your RAG pipeline must enforce those access boundaries"; the constraint is that "embeddings need to retain the permissions from where the data was originally sourced", hence the author's case for **relationship-based access control** (ReBAC — Google Zanzibar, SpiceDB). Two placements: **pre-filter** — `LookupResources` returns the ids the subject may view and the vector query carries `filter: {article_id: {$in: authorized}}`; **post-filter** — the store returns top-k and `CheckPermission` (or `CheckBulkPermissions`) runs per result before the context is built. Choice by **hit rate**: post-filter when most retrieved documents are authorised; pre-filter for a large corpus with a low authorised rate. The mechanism is product-independent; the customer figures are AuthZed's marketing. **The same filter applies to a memory store** — a user's or tenant's memories are a namespace the query must carry — which is why `memory_store.py` scopes every unit by owner and filters before ranking, and why G6 gains the pre/post-filter rule.

**Retrieval protects reads; the tool boundary protects writes.** Pinecone/AuthZed around retrieval, OpenAI "next to the tool that creates the side effect", IBM everywhere — not alternatives (digest §5). **Position:** both, with identity carried from the request through the filter to the tool call, and the trust register recording each tool's identity rung. When the store is Postgres, **RLS is the enforcement point** — "always applied even as new queries and application logic is introduced" (Supabase, `supabase-rag-with-permissions.md`, read 2026-10-01) — and the owner column is written at ingestion by the ingestion identity (`16-data-for-ai-products.md` §3.7; `practices/data-ingestion/` Verify 2, 8); the pre/post-filter above is the mechanism when authorisation lives outside the store. Gambill's "no side door" — a user who cannot open a record cannot have a chatbot summarise it (2026-06, `yt-tkFr-4r906Q…`) — confirms the rule. **Why scope limits are scale limits** (Barry Zhang, `yt-D7_ipDqhtwk…`, s12, reused): "if your errors are going to be high stake and very hard to discover… you can have read only access, you can have more human in the loop, but this will also limit how well you're able to scale your agent"; the survey (`yt-RGe6EjucbzI…`, Amplify 2026-07, self-report) shows the market moving the other way — write-enabled agents tripled, controls "the same toolkit you'd use to manage an intern". Map: `practices/memory-and-permissions/permission-model.md`.

## 4. How to apply it in a repo

This is the Verify of `practices/memory-and-permissions/README.md`, in order; the practice is `draft` and **unrouted** until the routing gate of `decisions/0004-day-one-for-blank-and-existing-repos.md` §6.

1. Confirm `multi_turn` (`practices/facts.md`) and answer `memory-design.md` §0 first: does anything outlive the session? If not, stop — `practices/context-management/` is enough.
2. Fill `memory-design.md`: types, profile vs collection, hot path vs background, the never-written list, retention and forgetting, the erasure path where `personal_data` or `regulated` holds, substrate.
3. Route every write through `memory_store.py`'s `remember()` (extract with include/exclude → consolidate by a reasoning model, off the response path) and every read through `search()` (identity filter before ranking, bounded by k and characters, block labelled by type).
4. Prove isolation with the two-identity test and the four cases of `memory-eval.md` through `practices/evals/eval_harness.py`, k = 5, pass^k 1.0.
5. If the provider's memory tool is used, implement the handler duties of `memory-tool-handler-notes.md` over the same store; pair with compaction (`practices/context-management/compaction-policy.md`).
6. Files and web search: copy the applicable rows of `external-context-notes.md` into the architecture doc — `file_id` as a server-side reference, one workspace per tenant, domain lists and `max_uses`, result blocks echoed back unchanged.
7. Full part: `permission-model.md` — an identity row per agent and sub-agent; the retrieval placement (pre- or post-filter) written down; destructive tools behind an approval that is serialised, resumable state and fails closed (`dry-run-and-approval.md` 2b; `guardrail-policy.md` G4/G6); a register row per tool.

## 5. Anti-patterns

- Appending every extracted fact to a profile; a store with two active, contradictory units for one owner.
- Hot-path writes with a chat model deciding conflicts; a reply that waits for consolidation.
- A memory unit with no owner, timestamp or source pointer; memory text in the prompt with no label or purpose.
- Deleting where audit matters; no erasure path where the law matters.
- A `file_id` taken from a request; one workspace for all tenants; search result blocks edited before being sent back.
- A static key shared by every agent and sub-agent; a credential in a prompt or a tool result.
- An MCP server installed without review; a destructive tool with no approval; an approval that sends on silence.
- Permissions at only one of the two boundaries — a filtered retriever with an unguarded tool, or an approval queue over an unfiltered store.
- The vector index kept after the row was erased.
