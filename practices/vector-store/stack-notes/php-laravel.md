# Stack-notes — PHP / Laravel

Written 2026-10-05 from the contract (`../README.md` Verify); no field report yet, so this is knowledge, not a port (decision 0005 §5). The s7 stack note (`../../embeddings-and-chunking/stack-notes/php-laravel.md`) already fixes the pgvector column by migration and the configuration as a typed class; this note adds the store side.

- **Store manifest as a typed class** (`App\Retrieval\StoreManifest`, `readonly` properties, constructor validation) holding the same fields as the reference — embedding fingerprint computed from the s7 configuration class, spec, quantization, placement, tenant model, benchmark record path, tenant proof — serialised to `retrieval/store-manifest.json`; a `check()` method run from a service provider at boot against the configuration and the s7 manifest, failing the request cycle before the first query if they disagree.
- **Spec and quantization as value objects** (`IndexSpec`, `Quantization`, `Placement` as `final readonly` classes) with the same refusals in their constructors: `m ≥ 2`, `ef_construction ≥ m`, mandatory `flat_until`, a lossy method without rescoring refused, an off-RAM placement without a cold-latency budget refused.
- **The two `SET LOCAL`s in a query scope:** an Eloquent scope (or a repository method) that opens `DB::transaction()`, runs `SET LOCAL hnsw.ef_search` and `SET LOCAL hnsw.iterative_scan` from the manifest's spec, then the `<=>` query with `LIMIT k` — never outside a transaction, because Laravel's pooled PDO connection would keep the setting for the next request. `exact` is `SET LOCAL enable_indexscan = off` in the same scope.
- **The query as a value object:** a `readonly` `Query` class carrying the tagged embedding, `k`, tenant and filters; the repository refuses a missing tenant when `multi_tenant` is configured and raises on fewer than `k` rows unless the strategy is exact — the `UnderFilled` of the contract as a domain exception, never an empty collection.
- **Tenant model as a migration:** `PARTITION BY LIST (tenant_id)` with an HNSW index per partition in the migration that creates the sections table, the RLS policy from `../../data-ingestion/stack-notes/php-laravel.md`, and the tenant set as a session variable (`SET LOCAL app.tenant_id`) in the same transaction as the query.
- **Benchmark as an Artisan command** (`retrieval:benchmark`) run on staging against the production fixture: exact search as ground truth, recall@k, QPS at the configured concurrency (a queue of workers), p99, memory from `pg_relation_size` of the index, build time from the migration log; it writes the `BenchmarkRecord` JSON with the fixture hash, spec hash and quantization hash — the manifest's `check()` re-verifies them.
- **Monitor as a scheduled job:** a `Schedule` entry running the sampled exact comparison with the recorded floor and firing the alert channel the app already uses; the same command with `--check` semantics (exit codes 2 / 1 / 0) in CI on changes under `app/Retrieval/**`, `database/migrations/**` and `docs/stack.md`.
- **Tests:** a Pest suite re-running the demo's refusals against the real database — hand-typed fingerprint, flat manifest over a built HNSW index, typed-in benchmark record, tenantless query, under-filled filtered query, a tenant with fewer than `k` results on a shared index, bq1 without rescoring, capacity overflow.
- **Pitfall:** a request-scoped runtime cannot build an HNSW index inline; the build is a queued job or a migration run by the deploy, with `maintenance_work_mem` raised for that session only.
- **Pitfall:** an object-storage-native store's write latency (hundreds of milliseconds) belongs in a queued job, never in the request; the manifest's cold-latency budget is the number the product's p99 must absorb.
