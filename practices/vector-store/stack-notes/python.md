# Stack-notes — Python (the reference stack)

Written 2026-10-05 from the contract; no field report yet. The reference `vector_store.py` needs only the standard library and the s7 module; the real store is wired behind the `Backend` protocol at `<<STORE_BACKEND>>`. Check current versions and licences at adoption.

- **Default store:** pgvector (https://github.com/pgvector/pgvector) in the repo's PostgreSQL, over the same connection the product uses (psycopg or SQLAlchemy); the `vector(d)` column, `d` being the configured dimension, is already fixed by the s7 migration (`../../embeddings-and-chunking/stack-notes/python.md`). Day zero has no index: `ExactBackend` is the `ORDER BY embedding <=> $1 LIMIT k` query.
- **The approximate backend:** `CREATE INDEX … USING hnsw (embedding vector_cosine_ops) WITH (m = …, ef_construction = …)` after the load, as a maintenance job with `maintenance_work_mem` raised for the session; `index_type()` reads `pg_indexes` for the table so the manifest cannot claim `flat` over a built graph.
- **Per-query settings are per transaction:** `SET LOCAL hnsw.ef_search` and `SET LOCAL hnsw.iterative_scan` inside the same transaction as the query; on a pooled connection (pgbouncer in transaction mode) anything else leaks the setting to the next request. `exact=True` is `SET LOCAL enable_indexscan = off` in that transaction.
- **Tenant model on Postgres:** RLS policy from `../../data-ingestion/privacy-compliance-checklist.md` §4 plus `PARTITION BY LIST (tenant_id)` with an index per partition (`rls_with_partition`), or a partial index per tenant when tenants are few, or the iterative scan on a shared index; the `Query.tenant` value sets the session variable the policy reads.
- **Dedicated engines:** the Qdrant client (payload index on the tenant field with `is_tenant`, `hnsw_ef`, quantization with `rescore` and `oversampling`) or the Weaviate client (per-tenant collections, `ef`, `rescoreLimit`) behind the same `Backend`; `index_type()` reads the collection's configuration. turbopuffer's namespace per tenant maps to `tenant_model="namespace"`.
- **The manifest:** `StoreManifest.to_json()` beside the s7 manifest under `retrieval/` (or a row in the same `index_manifests` table); `check()` runs at application start with the configuration and the s7 manifest, so a drift between the three fails before the first query.
- **Benchmark and monitor:** `run_benchmark()` against the real backend from a one-off script on staging with the production fixture; `sampled_recall()` as a scheduled job (sessions 13/15) writing the number where the alerting reads it; `--check --manifest … --fixture …` as the CI gate on paths `src/<package>/retrieval/**`, `evals/retrieval/**`, the migration folder and the stack document.
- **Tests:** `tests/test_vector_store.py` re-runs the demo's refusals against the real backend: hand-typed fingerprint, flat manifest over a built HNSW, typed-in benchmark record, tenantless query, under-filled filtered query, bq1 without rescoring, capacity overflow.
- **Pitfall:** `EXPLAIN (ANALYZE, BUFFERS)` is the way to see whether the planner used the HNSW index, a B-tree on the filter column, or a sequential scan — the README's own advice; a recall drop after a data load is often a planner change, not an index change.
- **Pitfall:** `REINDEX INDEX CONCURRENTLY` then `VACUUM` after bulk deletes; a deleted vector is hidden before it is gone, so the erasure test queries the index, it does not count rows.
