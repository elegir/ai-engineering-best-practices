# Vector store

## Solves
The product retrieves by similarity and one of these symptoms appears: an HNSW index over a corpus that exact search was serving in milliseconds, with nobody able to say what it bought; index parameters copied from a vendor's page and never measured on the repo's own data; a tenant who gets three results because the shared graph is two per cent theirs — a recall loss that looks like an empty corpus; a filtered or permissioned query that silently returns fewer than *k* results; a binary index with no rescoring step and no recall number beside it; an irreversible quantization switched on without a before/after; a store chosen from a ranking or a vendor's own comparison; an out-of-memory error at the first index build because nobody multiplied vectors by dimensions by bytes; "the vector database is slow" when the embedding call is what takes 300 milliseconds; two configurations compared at different recall and the faster one declared better.

## Applies when
- The fact `retrieval` holds (`../facts.md`) and the corpus, the latency or the bill asks for an approximate index. This folder sits **after** `../embeddings-and-chunking/` in the `../facts.md` ordering because it reads that folder's `EmbeddingConfig` (the fingerprint it binds to), `Embedded` (the tagged vectors it stores and queries with) and `IndexManifest` (whose `index` block says `flat` on day zero).
- **First-user**, not day-0, by design (`when: first-user`): index type, parameters, quantization, placement and benchmark are decisions a walking skeleton does not need. Day zero is pgvector in the same PostgreSQL with **exact search** (`flat_until` unreached), already recorded by the s7 manifest's `index: flat` default (`../embeddings-and-chunking/` Verify 1); when `multi_tenant` holds, tenant isolation at the index with the *k*-results proof is `../data-ingestion/` Verify 8. Those two day-0 obligations live in the day-0 practices this folder refines; `tenant-isolation-in-the-store.md` is the long form both point at.
- The full part (`full-when: retrieval and multi_tenant`): `tenant-isolation-in-the-store.md` and Verify 4 — the tenant model named in the manifest, a tenantless query refused, the two-tenant proof with the production index and parameters.

## Does not apply when
- The knowledge is **in the window** (`../context-management/context-store-decision.md`) or the corpus is **code or documentation for a coding agent** (agentic search over files — `../agent-patterns/`); nothing is embedded, so nothing is indexed.
- The corpus is **below the exact-search threshold** and will stay there: exact search in the database the repo has, recorded by the s7 manifest, is the whole answer. Install this folder when a measurement — the corpus count against `flat_until`, the query latency, the bill — says otherwise, not when a tutorial does.
- **Hybrid search, BM25 inside the store, reranking, phased ranking, facets** are session 10; **operations** of the store (metrics, indexing queues, shard sizing, the sampled-recall monitor as a scheduled job) are sessions 13 and 15; **the store as an attack surface** is session 14 (`../security-baseline/threat-model-agentic.md` T20 is the entry point). This folder states the boundary and stops.
- Embedding configuration, chunking and the retrieval eval set are `../embeddings-and-chunking/`; parsing, the envelope, the PII scrub and the RLS policy itself are `../data-ingestion/`. This folder assumes tagged vectors and an owner/tenant column already exist.

## Reference implementation

`vector_store.py`: one module, standard library only, implementing assertions 1, 2, 3, 4, 5, 6 (the record), 7 and 9 for Python with two in-memory backends — an **exact** one (the ground truth and the day-0 store) and a **stub approximate** one that imitates the one property of a shared graph this folder cares about: a bounded candidate list (`ef_search`) drawn over the whole collection *before* the tenant and filter predicates apply, so a small tenant or a selective filter gets fewer than *k* results. It is a stand-in, not an index; the real backend (pgvector, Qdrant, Weaviate, turbopuffer) is wired at `<<STORE_BACKEND>>`. The vectors it stores and queries with are s7's tagged `Embedded` objects — the fingerprint is read from the tag, never from a caller argument — and the manifest's `embedding_fingerprint` is computed from the `EmbeddingConfig` by `StoreManifest.for_config()`, so a fingerprint typed by hand is caught by `check()` the first time the configuration is at hand. **Provenance travels inside objects**: the spec is validated at construction and hashed; a benchmark record is bound to the fixture file's hash, the spec hash and the quantization hash and is re-read from disk and re-verified every time the manifest is checked; a quantization's before/after recall is copied from two such records, never typed; a `Query` is frozen and signed, so an accidental mutation after construction is caught — a guard, not a security control: the control is the store's own tenant predicate (RLS, partition, namespace), which the query only carries a value to; the capacity estimate is recomputed from the manifest's counts, not read from a field. **What hash-binding does and does not do:** a record bound to the fixture hash, the spec hash and the quantization hash catches a *stale or careless* record — another fixture, an older parameter set, a typed-in file — and nothing more; a forger who rewrites the hashes passes `check()` (the demo shows it). The control against forgery is `--check` **re-running** the two-tenant proof and the sampled recall from the fixture itself, every time, and never reading the stored result. `--check` returns a non-zero exit code when the manifest is missing or malformed, an approximate spec has no valid benchmark, the s7 manifest's `index` block disagrees, the two-tenant proof re-run from the fixture under-fills or crosses tenants, the resident estimate exceeds the recorded memory, or the smallest per-tenant sampled recall on the fixture is below the floor.

## Stack-sensitive points

- **Where the store lives decides who enforces the tenant predicate and which file the proof runs through**: in Postgres the predicate is an RLS policy (`../data-ingestion/privacy-compliance-checklist.md` §4) and the recall companion is a partition, a partial index or `hnsw.iterative_scan`; in Qdrant it is the tenant payload index; in Weaviate the per-tenant flat or dynamic index; in turbopuffer the namespace. The `Query.tenant` field is the same in all of them; what it binds to differs.
- **`SET LOCAL` is per transaction in Postgres**: `hnsw.ef_search` and `hnsw.iterative_scan` set on a pooled connection without a transaction leak into the next request. Request-scoped runtimes (PHP-FPM, serverless) must wrap the two settings and the query in one transaction.
- **A pgvector dimension is fixed at the column**, and `vector` index pages stop at a dimension limit (`halfvec` at twice it — numbers in `tuning-and-capacity.md` §1, read 2026-10-05): the dtype step from `float32` to `halfvec` is a column change and a re-index, not a flag.
- **The build runs where the data is**: an HNSW build is CPU-bound for minutes to hours and holds `maintenance_work_mem`; it is a maintenance job on the database host or a background indexer in a dedicated store, never a request handler.
- **Object-storage stores make write latency a queue concern**: a write acknowledged after an S3 commit takes a hundred milliseconds or more (Eskildsen, CMU 2026-03-10; figures per talk in `store-selection.md` §2–3), so request-scoped runtimes enqueue upserts; the manifest's `Placement.cold_latency_budget_ms` is the number the product's latency budget must absorb.
- **The benchmark runs against the real backend**; the reference's stub backends test the contract and the record format, not your index.

## Verify

Each numbered line is a stack-neutral assertion — the contract (decision 0005 §2). `observer` says who judges it: `script` (a command's exit code), `agent` (observed in a session), `Martin` (a human reads it). `negative` is what must make it fail. `framework: beats` means the assertion wins over the repo's library; `bends` means the library's convention may stand. Stack-specific commands live only under *Example commands (Python)*.

1. Every index has a store manifest binding the embedding configuration's fingerprint to index type and parameters, store quantization, placement and tenant model; a search or upsert against a store whose manifest disagrees with the embedding configuration, the embedding manifest or the index the backend actually built is refused — observer: script — negative: a store manifest with another fingerprint, or an HNSW index whose manifest says `flat`
2. Below the recorded `flat_until` vector count the index is exact; an approximate index is built only above it — observer: script — negative: an approximate spec at a count under the threshold, or a manifest with no threshold
3. Index parameters are validated (`m`, `ef_construction`, `ef_search ≥ k`, `lists`, `probes`) and a change of type or parameter takes effect only with a benchmark record on the repo's own fixture (recall@k vs exact, QPS at a stated concurrency, p99, memory, build time, date) for that exact specification — observer: script — negative: `ef_search` or `m` changed with no record, a record whose fixture hash differs from the fixture, or a record typed in with no fixture file
4. When `multi_tenant` holds, every query carries a tenant predicate enforced by the store and the manifest names the isolation model; a query without a tenant is refused; the two-tenant proof runs with the production index and parameters and returns *k* results per tenant with zero cross-tenant hits — observer: script — negative: a tenantless query, a cross-tenant hit, or a tenant with fewer than *k* results on a shared approximate index — framework: beats
5. Filters declared selective are not post-filtered over a fixed candidate list: the strategy per filter class is recorded with a selectivity **measured** by the benchmark on the fixture (never typed), post-filtering at or under the selectivity threshold is refused, and a filtered query returning fewer than *k* fails loudly; filtered recall is measured against filtered exact search — observer: script — negative: a silently under-filled result set, a selective filter with strategy `post`, or a filter class whose selectivity was typed rather than measured
6. Store quantization is recorded with method, oversampling, rescoring flag, originals' placement and recall before and after on the fixture, the two recall values copied from benchmark records; a lossy quantization without rescoring, or without the two records, is refused — observer: script — negative: a binary index with `rescore=False`, or a quantization whose before/after were typed in
7. A capacity estimate (vectors × dimensions × dtype bytes, graph overhead by `m`, quantized copies, replicas) is recomputed from the manifest's counts before the build and compared with the placement's available memory — observer: script — negative: an in-RAM index whose estimate exceeds the recorded memory with `placement` unset
8. The store was chosen against the facts in `store-selection.md`, Postgres with pgvector being the default; the record names a vendor's benchmark page only as the shortlist — observer: Martin — negative: a store picked from a ranking or a vendor's own comparison — framework: bends
9. Recall is monitored in production by a sampled comparison of the approximate index against exact search over the same vectors, with a recorded floor and an alert, on a schedule and after every spec, quantization, placement or corpus-size-band change — observer: script — negative: no sampled exact comparison, or a drift below the floor without an alert
10. Before and after every quantization, placement or index change Martin reads one row — the before/after recall, the cost line and the reversibility of the choice — beside the decision — observer: Martin — negative: an irreversible quantization with no row beside it

**Example commands (Python):** `python3 vector_store.py --demo` (offline; exit 0 when every step passes and every negative is refused); `python3 vector_store.py --check --manifest retrieval/store-manifest.json --fixture evals/retrieval/fixture.json --k 10 --floor 0.95` (exit 2 when the manifest is missing or malformed, an approximate spec has no valid benchmark record, a `multi_tenant` manifest has no tenant proof at the current spec, or the estimate exceeds the recorded memory with no placement; exit 1 when sampled recall is below the floor; exit 0 otherwise — the gate of assertion 9; the reference runs with the s7 `DEMO_CONFIG`, the stub embedder and the stub backends until Adapt points it at the real store); `pytest tests/test_vector_store.py` (the repo's tests re-running the demo's refusals against the real backend).
