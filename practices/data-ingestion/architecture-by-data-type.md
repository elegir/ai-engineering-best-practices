## 0. The rule

Every input becomes **one element-typed document with provenance** — Docling's `DoclingDocument` ("element types, headings, and per-element metadata"), Unstructured's partitioned elements (`Table` with `text_as_html`, `page_number`, `filename`), LlamaIndex's `Document` → `Node`s — and **views are derived from it per consumer**: Markdown for the reasoning model on text, HTML or lossless JSON for a complex table, a natural-language rendering for the embedding model, the element tree for an agent that navigates. The reference type is `Element` in `ingestion_pipeline.py` (six types, `page`, `bbox`, `confidence`, three `to_*()` views). The stages are the three every source names: **load → transform → index/store**.

## 1. The table

| Data type | Parse path | View for the reasoning model | View for the embedding model | Provenance kept | Chunks or tree | Notes (dated 2026-10-01) |
|---|---|---|---|---|---|---|
| **PDF, born-digital** | layout detection (small models, CPU) → per-region models → element document; heuristic text extraction only as the model-free *first pass* | Markdown; HTML for complex tables | element text; table sentences | page, bbox, confidence, parser version | page-level is "a pretty strong baseline" (Liu 2024); chunk parameters are session 7 | a PDF is "machine instructions… for display purposes": reading order and tables are reconstructed, never read (Liu 2026) |
| **Scan / image of a document** | OCR model per region after layout; agentic OCR = token-level verification, never an LLM rewriting the page | Markdown with low-confidence spans marked | element text | page, bbox, **confidence per element** | as PDF | "a period versus a comma, a zero versus an O" (Abraham); a frontier VLM is a tool on the hard page, not the OCR of the corpus |
| **Table** (inside any document) | table-structure model (TableFormer in Docling) → rows and cells; keep it as a `table` element, never merged with text (Unstructured) | **simple:** Markdown; **complex (merged cells, nested headers):** HTML or lossless JSON — "you may want to use something like HTML" (Abraham) | **a natural-language rendering** ("Table with columns …; Plan is Pro; Refund window is 30 days") — "embedding models really struggle to correlate… this messy blob of HTML tags and numbers" | page, bbox, the table's own id so both views link to one element | one element per table; a very long table splits by row groups with the header repeated (session 7) | simple-vs-complex routing was user-controlled in 2026-01 and "a dynamic problem" by 2026-09 (Reducto) |
| **Spreadsheet** (xlsx, csv) | sheet → table elements per sheet or per logical block; Docling and LlamaParse read xlsx | HTML or JSON per block | sentences per row group | sheet name, row range | by block | no source says more; treat as tables |
| **Word / PowerPoint** | the parser's own reader ("custom bespoke XML format… a ton of fluff" — Liu, 2026-09, `../../sources/raw/2026-09-27-market-scan-s02-context-caching/yt-RQi7x-navxU-ai-engineer-jerry-liu-document-context-layer.md`, s2 reused) → headings, paragraphs, tables, slide notes | Markdown with headings | element text | page or slide number | by heading (tree) | notes and comments are elements too, with their own sensitivity |
| **HTML page / website** | HTML parsed directly ("essentially just looks at the HTML and parses it" — Docling); a `sitemap.xml` walk for a whole site (Ebbelaar); strip navigation and boilerplate before indexing | Markdown | element text | URL, fetch timestamp (EDPB: "recording the timestamp"), section anchor | by heading | scraping duties in `privacy-compliance-checklist.md` §3 |
| **Image / figure / chart** | caption and alt text kept; Docling can "enrich figures with text descriptions so that they're retrievable alongside text" and convert bar, pie and line charts into tables or code | the description, or the recovered table | the description | page, bbox, the source image id | one element | the description is model-generated: mark it so and keep the image for a VLM tool |
| **Database / structured records** | two shapes: **rows as documents** (`DatabaseReader` "returns every row of the results as a Document" — LlamaIndex) for retrieval, or **text-to-SQL** at query time with "an intermediate step to predict what tables to use" when the schema is large (Huyen) | a row rendered as `field: value` lines, or the SQL result | a sentence per row | table, primary key, snapshot time | one element per row or per entity | `../context-management/context-store-decision.md` question 7; RLS applies to both shapes |
| **Audio / video** | ASR to a transcript (Docling supports it); the transcript is then text | Markdown with timestamps | transcript segments | media id, timestamp range | by segment | noted in the scan, not digested; speaker PII in transcripts is a scrub class |
| **Long, organised documents** (manuals, contracts, standards) | parse to the **tree** and keep it; give the agent an outline "where each section comes with a short summary" and tools to open a section (IBM 2026-08) | the section opened | section summaries for the find-the-document step | section path, page | **tree navigation inside the document**, similarity search to find the document | costs: "you need a good tree before any of it works… more latency and more calls" |

## 2. Chunks or tree — the decision for `<<corpus>>`

"Similarity search to find the right document, structure to navigate inside of it" (IBM 2026-08). Answer `../context-management/context-store-decision.md` question 8 — *a few long structured documents, or many short ones?* — and record: **<<chunks / tree / both: similarity to the document, tree inside>>**, because <<…>>. Tree navigation needs the parser to produce a good hierarchy (Verify 3 on tables; headings as `title` elements); "parsing real world documents into clean structure is a hard problem. That's most of the engineering".
