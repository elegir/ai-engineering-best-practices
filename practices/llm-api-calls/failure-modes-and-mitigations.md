# What the model is structurally bad at — and what covers it

Read once; copy the rows that apply into the feature spec, naming the concrete tool, retrieval or check in *this* repo. Each row is a *mechanism* (why it fails), not a bug that the next model release fixes; the mitigation is therefore never "a better prompt". Sources: Karpathy (2025-02), Klein (2026-04), Ng (2026-05), Anthropic roundtable (2024-09) — digest `../../sources/2026-09-27-s01-llm-setup-digest.md` §3.1, §3.3. Principle: `../../principles/10-llm-api-fundamentals.md` §3.1.

| # | The model reliably fails at | Why (mechanism) | What covers it |
|---|---|---|---|
| 1 | Facts, numbers, identifiers, dates, prices, policies "from memory" | Parameters are a lossy compression of training text — "a vague recollection"; the model cannot tell recall from confabulation, and fluency hides it ("looks right and is right are not the same") | Put the source in the context (retrieval, attached document, tool result) and instruct "answer only from it"; validate any id/number against the system of record in code |
| 2 | The inverse of a fact it knows (A's mother is B, but "whose son is A?") | Knowledge is one-directional in the weights ("reversal curse") | Same as 1: state the fact explicitly in context; never rely on recall for lookups in either direction |
| 3 | Counting letters, exact substrings, character positions, precise spelling | It sees tokens (multi-character chunks), never characters | A code-execution tool or plain code on your side; never prompt around it |
| 4 | Arithmetic and multi-step calculation answered "in one token" | Fixed compute per output token; the work must be spread over tokens | A calculator/code tool for the arithmetic; for reasoning, a thinking budget (reasoning model) or "show your work before the answer" (other models); never "reply with just the number" |
| 5 | Comparing numbers, units, dates that "look" like something else (9.11 vs 9.9) | Capability is "Swiss cheese": adjacent easy cases fail for reasons unrelated to difficulty | Do comparisons in code; test the specific cases your feature meets instead of assuming "easier, so fine" |
| 6 | Anything after its training cutoff; anything niche or local | Nothing in the weights; the model may still answer fluently | A search/retrieval tool with the current date and the cutoff stated in the system prompt so the model knows when to call it |
| 7 | Saying "I don't know" / "none of these apply" | Trained to be helpful; forced-choice prompts produce forced answers | Give an explicit **out** in the rules and in the output schema (`"none"`, `null`); check the out is actually used on edge inputs |
| 8 | Disagreeing with the user's premise | Sycophancy is trained in by preference optimisation | Neutral framing in prompts; a rule to check premises; an A/B test of leading vs neutral phrasing in the eval |
| 9 | Knowing what it is, its version, cutoff, what it can and cannot access | No self-model; the answer is hallucinated unless supplied | State identity, cutoff and limits in the system prompt |
| 10 | Guaranteeing a behaviour because the prompt says so | Prompting is "not a control surface with precise semantics" | Guarantees in code: schema validation on output, allow-lists on tools, business rules, human approval on irreversible actions (`acts_on_world` in `../facts.md`) |
| 11 | Catching its own or another model's errors | Failures are **correlated**: an LLM judge shares the generator's blind spots; "80 % checking 80 %" is ~82 %, not 96 %; multi-turn compounds per-turn error | Use an LLM judge as one signal next to deterministic checks; never as the sole gate; measure the judge's miss rate on your hard cases |
| 12 | Being right *every* time on a scenario it usually gets right | Sampling is stochastic; an aggregate pass rate hides scenario-level flakiness | Run each eval scenario N times (≥5) and report the worst case; ship on consistency, not on the mean |
| 13 | Following instructions buried in the middle of a long context | "Lost in the middle": recall is best at the start and end | Key rules at the start and repeated at the end; keep the context short; new thread on topic change |
| 14 | Reading fetched web pages, emails or documents as *data* rather than as instructions | Prompt injection: instructions hidden in content are read like any other tokens (parked for session 14) | Trust boundary in code: fetched content is data; restrict what tools can be called on its basis; a moderation/classification layer independent of the generator |
| 15 | Fine-grained visual discrimination, handwriting, meter readings | Coarse scene understanding is good; fine detail is not (outside this module) | A verification step or human check for anything high-stakes read from an image |

## How to use this in a spec

For the feature, list the rows that apply and write one line each: *row → what in this repo covers it* (e.g. "row 1 → `get_order` tool returns the order page; rule 2 in `prompts/support/system.md`"; "row 12 → `evals/support.py` runs 5× per case, CI fails on any scenario < 5/5"). A row that applies with nothing covering it is a known gap; write it down as such rather than hoping the prompt holds.
