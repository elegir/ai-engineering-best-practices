# Stack-notes — PHP / Laravel

Written 2026-10-04 from the contract; no field report yet. The mechanism is a typed configuration validated at construction and compared with a record and a manifest, one embedding service with a mandatory side, a queued chunk-and-embed job that counts in the model's tokens, a pgvector column whose dimension the migration fixes, an eval fixture under version control and an Artisan command whose exit code gates the merge. Check package versions at adoption.

- **Configuration as a typed class:** a final readonly value object built from `config/embeddings.php` (model, version, dimensions, supported dimensions, dtype, metric, max input tokens, query and document conventions, tokenizer name) whose constructor throws on an empty version, an undeclared dimension or an unsupported dtype or metric, and whose `fingerprint()` is a hash of those fields; a boot-time check compares it with the `docs/stack.md` record and the manifest row (assertion 1).
- **One embedding service:** a class with `embed(array $texts, string $side)` that throws unless `$side` is `query` or `document`, applies the provider's `input_type` or prefix itself and calls the provider over HTTP through the repo's one LLM client; controllers and jobs never call the provider directly (assertion 2).
- **Tokenizer:** no native tokenizer for most providers in PHP — call a small tokenizer sidecar (the Python reference's tokenizer behind HTTP) or a PHP port such as `yethee/tiktoken` on Packagist (https://packagist.org/packages/yethee/tiktoken) for OpenAI's encodings; record the tokenizer's name in the configuration and a safety margin in the manifest when the count is approximate (assertion 3).
- **Chunk-and-embed as a queued job:** one `ShouldQueue` job per document reading the element rows written by the ingestion job (`../../data-ingestion/stack-notes/php-laravel.md`), applying the structure rules (table standalone or row groups with the header, title attached to its paragraph, metadata prefix) and refusing an oversize chunk before any provider call; the job carries the configuration fingerprint and writes only into the table whose manifest matches (assertions 3, 4, 7).
- **Store:** `pgvector/pgvector` on Packagist (https://packagist.org/packages/pgvector/pgvector) with a migration per index declaring `vector(<<DIMENSIONS>>)` — an insert of another dimension fails at the database — and a table name carrying the fingerprint; a `index_manifests` table with the chunker record and the eval record; RLS from the ingestion practice applies unchanged.
- **Eval fixture and harness:** the fixture under `evals/retrieval/` in version control; an Artisan command `retrieval:check` that loads it, chunks the corpus with the configured chunker, embeds with a deterministic stub in CI (and the real service on demand), computes token-level recall, precision, Precision_Ω and IoU, and exits 2 when the fixture is missing or has fewer than fifty questions, 1 below the floor, 0 otherwise (assertions 5, 9).
- **Build gate:** the command that creates a new index table refuses to run when the manifest has no eval record comparing at least two chunkers (assertion 5).
- **Re-embed:** a new migration and table per fingerprint, the shadow comparison run by `retrieval:check` against both tables, the cut-over as a config change, the old table dropped after the bake period (`embedding-config-and-versioning.md` §6).
- **Pitfall:** a queued job started before a config deploy finishing after it — the job's fingerprint check against the manifest is what catches the mixed index.
- **Pitfall:** `config:cache` serving a stale embeddings configuration — the boot-time comparison with the manifest row makes the mismatch fail loudly.
