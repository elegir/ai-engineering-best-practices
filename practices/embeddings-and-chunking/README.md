# Embeddings and chunking

## Solves
The product retrieves by similarity and one of these symptoms appears: an answer whose source chunk exists in the corpus and was never returned, and nobody can say whether the chunker or the model lost it; a date, an invoice number or a negation answered from a passage that is merely *about* the same topic; a table answered from half its rows because the splitter cut it mid-row, or a heading indexed alone and its paragraph indexed without it; two embedding models' vectors (or two dimension settings of one model) compared in one index after a quiet upgrade, with similarity scores that mean nothing; a chunk size copied from a tutorial or left at a framework default and never measured; queries embedded with the document instruction (or with no instruction) on a provider whose model expects one per side; a "contextual" or "late" chunking feature adopted with no before/after number beside it; a retrieval change merged because an LLM judge liked the answers.

## Applies when
- The fact `retrieval` holds (`../facts.md`): the product fetches documents or rows into the window by similarity or search. This folder decides how text becomes vectors and into which units, and it sits **after** `../data-ingestion/` in the `facts.md` ordering because it reads the typed elements and the envelope that folder writes (`Element` with `type`, `text`, `page`, `rows`, `to_embedding_text()`; `Envelope` with filename, title, page, owner, tenant, ingested-at).
- Day-0 part: the embedding configuration (`EmbeddingConfig`), the chunker record in the index manifest, and a retrieval eval set with token-level metrics computed before the first index is built. These cannot change later without re-embedding everything.
- First-user or at-scale parts, marked so in `chunking-decision-table.md`: contextual prefixes, late chunking, quantization below bfloat16, hierarchical or multi-representation indexing, fine-tuning. Each is adopted only with a before/after on the eval set (Verify 8).

## Does not apply when
- The knowledge is **in the window** — a bounded, stable corpus kept in the cached prefix (`../context-management/context-store-decision.md`). Nothing is embedded; Anthropic's 2024-09-19 rule of thumb — a knowledge base "smaller than 200,000 tokens (about 500 pages of material)" can go in the prompt — is quoted in the principle, not as a vendor limit.
- The corpus is **code or documentation for a coding agent**: agentic search over files that already have names and structure (`../agent-patterns/agentic-rag-skeleton.py`); no chunker, no embedding model.
- **Exact identifiers, dates, ranges and negations** — these are lexical and structural problems; hybrid search (BM25), metadata filters, reranking and query rewriting are session 10 and are not in this folder. The folder states the boundary (principle §3.1) and stops there.
- **Vector-store internals** — index types, quantization inside the index, placement, tenant isolation at the index, multi-vector storage at scale — are `../vector-store/` (first-user, s8). This folder records `dtype` and `dimensions` as part of the configuration and, since 2026-10-05, an `index` block in the manifest that says `flat` (exact search) on day zero; `../vector-store/vector_store.py`'s `StoreManifest.check()` refuses a store manifest that disagrees with it.
- Parsing, the audit report, PII scrubbing and tenant isolation are `../data-ingestion/`; this folder assumes typed elements and an envelope already exist.

## Reference implementation

`embedding_config_and_chunker.py`: one module, standard library only, implementing assertions 1, 2, 3, 4, 5, 7 and 9 for Python with an in-memory index and a **deterministic stub embedder** (a hashed bag of tokens, normalised) standing in for the provider call, so the demo and the harness run offline and CI never pays for embeddings to test a chunker. The tokenizer behind the `Tokenizer` protocol is a declared **approximation** (`ApproxTokenizer`: whitespace and punctuation pieces with character offsets); the real one (`tiktoken`'s `cl100k_base` for OpenAI's third-generation models — OpenAI's guide, read 2026-10-04 — or the provider's tokenizer) is wired at `<<TOKENIZER>>`. The mechanism it fixes is a chain of refusals around one path, none of which trusts the caller: a configuration is pinned (`EmbeddingConfig`) and compared with the record in `docs/stack.md` and with the index manifest; every embedding call declares its side, the provider's convention is applied by the code, and the result is a **tagged** `Embedded` carrying the configuration fingerprint, the side and the model — the index reads those fields, so a caller cannot pass a string to get a foreign or wrongly-sided vector in; chunks are produced by a declared chunker that counts prefix + body in the model's tokens and refuses a chunk over the limit; the structure-aware chunker reads the element tree, carries headings forward and renders the envelope's metadata prefix; an index cannot be built without an eval record whose question count is re-counted from the fixture file and whose at-least-two compared chunkers each carry the four metrics; `--check` returns a non-zero exit code when the eval set is missing, malformed, too small (the floor of fifty cannot be lowered by a flag), the chunker arguments are invalid, or recall is below the recorded floor. The reference `--check` runs with `DEMO_CONFIG` and the stub embedder — it tests the chunker; in a repo it is pointed at the manifest's configuration (Adapt).

## Stack-sensitive points

- **Where the tokenizer runs decides how the limit is enforced**: in Python the model's tokenizer is a library call at chunk time; in a request-scoped runtime without a native tokenizer the count comes from a sidecar or a calibrated approximation, and the limit is enforced with a safety margin recorded in the manifest.
- **A pgvector column's dimension is fixed at migration** — a guard for free (an insert of another dimension fails at the database) and a migration per re-embed; the manifest's `dimensions` and the column's must agree, and the re-embed protocol creates a new table or column rather than altering the old one.
- **Rate limits make batch embedding a queued job** in request-scoped runtimes (PHP-FPM, serverless): the job carries the configuration fingerprint and refuses to write into an index whose manifest differs.
- **`input_type` is a parameter on Voyage and Cohere and absent on OpenAI's guide** (all three read 2026-10-04, `embedding-config-and-versioning.md` §7): the adapter hides the difference, the configuration records the convention actually applied, and the caller only ever passes `side`.
- **The harness must run offline** — a stub embedder and a saved fixture — so CI tests the chunker on every change without an API key; the same harness with the real embedder is the model comparison of `embedding-model-selection.md` and runs on demand, not on every push.

## Verify

Each numbered line is a stack-neutral assertion — the contract (decision 0005 §2). `observer` says who judges it: `script` (a command's exit code), `agent` (observed in a session), `Martin` (a human reads it). `negative` is what must make it fail. `framework: beats` means the assertion wins over the repo's library; `bends` means the library's convention may stand. Stack-specific commands live only under *Example commands (Python)*.

1. One embedding configuration per index pins model id, version, dimensions, dtype, metric and the provider's query and document conventions, recorded identically in the stack document and the index manifest, whose `index` block states the index (`flat` on day zero — type, params, quantization, placement; an approximate type with no params or a flat type with params is refused) — observer: script — negative: an embedding configuration with no version, an undeclared dimension or an unsupported dtype, or a stack record or manifest that disagrees with the configuration, or an index block naming hnsw without parameters
2. Every query is embedded as a query and every document as a document, by the same model, through one code path that applies the provider's convention — observer: script — negative: an embed call without a side, a query embedded as a document, or a search whose query model differs from the index model
3. Chunks come from a declared chunker (strategy, size and overlap in tokens of the model's tokenizer) recorded in the manifest, and no chunk exceeds the model's maximum input — observer: script — negative: a chunk over the limit, or an index whose manifest has no chunker record
4. Chunks follow the element tree: a table is one chunk (or row groups with the header repeated) rendered with its embedding-text view, a heading never stands alone or apart from its first paragraph, and each chunk starts with the envelope's metadata prefix — observer: script — negative: a table row split across chunks or a table merged with prose, a lone-heading chunk, or a chunk without its prefix
5. A retrieval eval set exists for the corpus (at least fifty questions with verbatim excerpts, generated and filtered or real) and token-level recall, precision and IoU were computed for the chosen chunker and at least one alternative before the index was built — observer: script — negative: an index built with no eval record, or a chunker recorded with no comparison
6. The embedding model was chosen from at least two candidates filtered by task, language, max input, knowledge cutoff and cost and compared on the corpus eval set; the record names the leaderboard only as the shortlist — observer: Martin — negative: a model picked from a rank or from the provider already in use without a comparison — framework: bends
7. A model, version, dimension or dtype change re-embeds the whole corpus behind a new index; no index holds vectors from two configurations — observer: script — negative: an upsert whose fingerprint or dimension differs from the index manifest's
8. Context prefixes, late chunking, quantization below bfloat16, hierarchical or multi-representation indexing and fine-tuning are adopted only with a before/after on the eval set and a recorded cost — observer: Martin — negative: a context prefix or a binary index with no measurement beside it
9. The retrieval eval runs deterministically, with no judge, on every change to the chunker, the configuration or the index, and blocks the merge when the set is missing or recall is below the recorded floor — observer: script — negative: a chunker or configuration change merged without the run, or a run that passes with the eval set absent

**Example commands (Python):** `python3 embedding_config_and_chunker.py --demo` (offline; exit 0 when every step passes and every negative is refused); `python3 embedding_config_and_chunker.py --check --fixture evals/retrieval/fixture.json --chunker recursive --size 200 --overlap 0 --k 5 --floor 0.85` (exit 2 when the fixture is missing, malformed, has fewer than fifty questions — `--min-questions` can raise that floor, never lower it — or `--overlap >= --size`; exit 1 below the floor; exit 0 otherwise — the CI gate of assertion 9; the reference runs with `DEMO_CONFIG` and the stub embedder until Adapt points it at the manifest); `pytest tests/test_retrieval_config.py` (the repo's tests re-running the demo's refusals against the real tokenizer and store).
