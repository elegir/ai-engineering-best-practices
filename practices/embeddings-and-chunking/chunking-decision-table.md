## 0. Two questions before any strategy

**Does this data need chunking at all?** Weaviate (2025-09-04): "FAQs, product descriptions, or social media posts, you usually do not need to chunk them. Chunking can even cause problems." A unit that already fits the embedding model's maximum input and makes sense alone to a human is embedded whole — the human test two vendors state identically: "if the chunk of text makes sense without the surrounding context to a human, it will make sense to the language model as well" (Pinecone 2025-06-28; Weaviate 2025-09-04).

**Which unit does the generator need?** Kamradt (2024-01): "rather than starting with hey how should I chunk my data your question should really be what's the optimal way for me to pass the data that my language model needs for my task". Martin (2024-04): "just get me the right document. It's an easier problem than get me the right chunk". Record: **`<<UNIT>>`** — a passage (the chunk itself is handed to the generator), a page (the chunk finds the page), or a document (the chunk or a summary finds the document; the generator reads it whole). The unit retrieved and the unit embedded may differ — that is what the hierarchical and multi-representation rows are for.

## 1. The table

`When` is the point in the product's life at which the row is allowed (decision 0004 §5): **day-0** (before the first index), **first-user** (once real queries exist and the eval set has them), **at-scale** (once cost or latency is measured as a problem). Every row below the baseline enters only with a before/after on the eval set (`chunk-eval-harness.md`; README Verify 8).

| Strategy | What it is | What it fixes | What it costs | When | Dated evidence (directions, not decimals) |
|---|---|---|---|---|---|
| **Fixed-size (tokens)** | A window of N tokens, optional overlap | Nothing but the model's limit | Cuts mid-sentence and mid-row; "extremely simple… very rigid… I don't know anybody that does this in production" (Kamradt 2024-01) | day-0 as the *alternative* in the eval, not as the baseline | Chroma 2024-07: a 250-token fixed chunker on the small `all-MiniLM-L6-v2` lost recall when overlap was removed (82.4 → 77.1) — "for smaller context, overlapping chunks are necessary"; on `text-embedding-3-large` fixed and recursive were close; **fixed 800/400** (the OpenAI Assistants default, "assuming the TokenTextSplitter method is employed") "results in slightly below-average recall and the lowest scores across all other metrics" (snapshot `chroma-evaluating-chunking.md`) |
| **Recursive (separator list)** | Split on the first separator that works — paragraphs, lines, sentences, words, characters — merge pieces up to N tokens | Respects the author's boundaries where they exist; cheap; deterministic | Separators must fit the text; LangChain's default list `["\n\n", "\n", " ", ""]` "would commonly result in very short chunks, which performed poorly" until Chroma added `".", "?", "!"` | **day-0 baseline**: 200–400 tokens of the model's tokenizer, no overlap | Chroma 2024-07 (5 corpora, 472 questions, k = 5, deviations ± 25–35 points): recursive 800/400 recall 85.4, precision 1.5, IoU 1.5; recursive 400/0 recall 89.5, precision 3.6, IoU 3.6; **recursive 200/0 recall 88.1, precision 7.0, Precision_Ω 29.9, IoU 6.9 — "consistently high performing across all evaluation metrics"**; "reducing chunk overlap improves IoU scores" (the Assistants-default finding is on the Fixed-size row: Chroma measured it as `TokenTextSplitter` 800/400). Kamradt: "if I'm starting a project this is my go-to splitter"; Weaviate: "usually a solid default choice"; Pinecone: "a great middle ground" |
| **Document-aware** | The same splitter with the format's structure as separators: Markdown headers, code by class and function, HTML by tag, LaTeX by section | Keeps a heading with its section, a function whole | Only as good as the format's markup | day-0 when the source has markup | Kamradt 2024-01; Weaviate 2025-09; Pinecone 2025-06 — all three name the same four formats |
| **Element / page (structure-aware)** | Recombine the parser's typed elements: text elements merged up to N tokens, a table standalone (or row groups with the header repeated), a title attached to its first paragraph, no chunk across a section or page boundary | A table never split mid-row or merged with prose; a heading never alone; page provenance kept | Needs a parser that produces elements (`../data-ingestion/`); long tables still split by rows | **day-0 baseline when the parser gives elements**; page boundary when the documents are paged | Unstructured (read 2026-10-01): "Table elements are always treated as standalone chunks. If a table is too large, the table is chunked by rows"; by-title: "A single chunk should not contain text that occurred in two different sections"; Jerry Liu 2024-07: "page level chunking… is honestly a pretty strong baseline… Stop worrying about tuning your chunk size of like 512 or 1024"; Reimers 2025-05: "humans… spend a lot of time to create like a nice PDF to adhere to page boundaries"; Ebbelaar 2025-02 on Docling's hybrid chunker: "split chunks that are too large… stitch together chunks that are too small… and it works with your specific tokenizer" |
| **Metadata prefix** | Render filename, title, page, date (never owner or tenant) as text at the head of every chunk | Questions that name a document, a date or an author; "Modified by" alone served "10 % of our question base" at one client (Liu, TWIML 2024-11) | A few tokens per chunk; the prefix must be excluded from the eval's token counts | day-0 (part of the structure-aware chunker) | Jason Liu, *Low-hanging fruit* 2024-05-11: "include file and document metadata as additional text in each chunk… File path, Document title, Author, Creation date, Tags" |
| **Semantic (embedding breakpoints)** | Embed neighbouring sentence groups, cut where the distance to the next group is in the top percentile (Kamradt's 95th) | Topic shifts inside a long section | One embedding call per sentence group; "experimental", "more expensive… slower" (Kamradt); the percentile "is a relative metric and can lead to larger chunks in bigger corpora" and the splitter "is greedy" (Chroma) | first-user, eval-gated | Chroma's **KamradtModifiedChunker** adds "a binary search over discontinuity thresholds such that the largest chunk is shorter than the specified length"; its **ClusterSemanticChunker** (50-token pieces, dynamic programming to maximise pairwise cosine within a chunk) scored **recall 91.3 at 400 tokens** and **precision 8.0, Precision_Ω 34.0, IoU 8.0 at 200 tokens** (the highest) — at the cost of "requiring chunks to be re-computed as data is added" |
| **LLM / agentic chunking** | An LLM decides the boundaries: Kamradt's propositions ("Greg went to the park. Greg likes walking") grouped by an agent-like loop with a running title and summary; Chroma's `split_after: 3, 5` over tagged 50-token pieces; Weaviate's agent picking a strategy per document | Boundaries a splitter cannot see; self-contained propositions | "slow and… expensive" (Kamradt); "tens of minutes" per corpus (Chroma); rewriting the corpus "was costly, slow, and suffered from hallucinations" (Chroma); "a lot of computing power" (Weaviate) | first-user, eval-gated; **agentic chunking skipped by default** (digest row 10) | Chroma's LLMSemanticChunker: **recall 91.9**, average efficiency; next-token entropy as a boundary signal: "we did not extract a clear signal for semantic boundaries"; attention values: "we also did not find that there was any clear structure in the attention values which could be used for chunking" (Chroma 2024-07) |
| **Hierarchical / parent-document / chunk expansion** | Embed small units, return the parent (LlamaIndex `HierarchicalNodeParser` 2048/512/128 in Kamradt's demo; LangChain `ParentDocumentRetriever`); or expand a hit to its neighbours, paragraph, page or document (Pinecone) | Precision of a small embedding with the context of a large unit | A document store beside the index; expansion is a retrieval-time step (session 10) | first-user | Kamradt 2024-01; Martin 2024-04 ("decoupling raw documents and the unit you use for retrieval"); Pinecone 2025-06-28: "retrieving neighboring chunks within a window… expanded to paragraphs, pages, or even whole documents" |
| **Contextual prefix (contextual retrieval)** | An LLM writes 50–100 tokens situating the chunk in its document; the text is prepended before embedding and before BM25 indexing | The chunk that "doesn't specify which company it's referring to or the relevant time period" (Anthropic's SEC example) | One LLM call per chunk: "$1.02 per million document tokens" with prompt caching, "assuming 800 token chunks, 8k token documents, 50 token context instructions, and 100 tokens of context per chunk" (Anthropic 2024-09-19); Reimers 2025-05: fine for "a thousand PDFs", "very slow, expensive" for a billion | first-user, eval-gated (the before/after is the point) | Anthropic 2024-09-19, own evaluation, measured as 1 − recall@20: contextual embeddings cut the failure rate "by 35 % (5.7 % → 3.7 %)"; with contextual BM25 "by 49 % (5.7 % → 2.9 %)"; with reranking "by 67 % (5.7 % → 1.9 %)" — BM25 and reranking are session 10. **What did not work**, same page: "adding generic document summaries to chunks (we experimented and saw very limited gains), hypothetical document embedding, and summary-based indexing (we evaluated and saw low performance)". The chunker stays: "the choice of chunk size, chunk boundary, and chunk overlap can affect retrieval performance" |
| **Late chunking** | Embed the whole document through a long-context, mean-pooling model; pool per chunk *after* the transformer | Pronouns and references resolved by the document ("Berlin… mentioned only in the first sentence" — Jina) at the storage of naive chunking | A long-context model with mean pooling is "a requirement" (Weaviate); documents must fit the window (8,192 tokens, "roughly ten standard pages", for `jina-embeddings-v2-base-en`); "limited data available on its performance in benchmarks" (Weaviate); "we will probably need a lot more validation from independent sources" (Prompt Engineering, 2024-10-11, `yt-Hj7PuK1bMZU-…`) | first-user, eval-gated, only on a model that allows it | Jina README (BeIR nDCG@10, 256-token chunks, `jina-embeddings-v2-small-en`): from no change on Quora (62-character documents) to NFCorpus 23.46 → 29.98 — "in all cases, late chunking improved the score… the average length of the documents correlates with greater improvement"; two datasets where "no chunking performs best". Weaviate's storage table (8,000 tokens × 768 float32 × 100,000 documents): late interaction "~2.46 TB", naive and late chunking "~4.9 GB" |
| **Multi-representation (summary, questions, sentences → parent)** | Embed a summary, hypothetical questions or sentences; return the page, table or document they point at (LangChain `MultiVectorRetriever`) | Tables (embed the natural-language view and the caption, link to the HTML), images (embed the description), whole-document return | More vectors per unit and a document store; a summary on every chunk is not this | first-user | Kamradt 2024-01; Martin 2024-04; Jerry Liu 2024-07 ("embed… an extracted summary, or embed the caption, or all three… link all of them to the same underlying data"). **Contested** (digest §5): Anthropic saw "low performance" for summary-based indexing — the units differ (a summary standing for a document vs a shared summary on every chunk). Position: summaries find the document; chunk-level context must be chunk-specific |
| **RAPTOR** | Cluster chunk embeddings, summarise each cluster, recurse; index leaves and summaries together | Questions that span many chunks ("better semantic coverage across the abstraction hierarchy" — Martin) | LLM summaries at every level; re-clustering as data changes | at-scale, eval-gated | Martin 2024-04; no independent measurement in the scan |
| **Adaptive / post-chunking at query time** | An agent picks the strategy per document (Weaviate); chunking after retrieval of whole documents (Weaviate's Elysia) | Named, not measured | Vendor features | not adopted; re-read at the s7 validation pass | Weaviate 2025-09-04 — no numbers |

## 2. The four starting points the sources disagree on

| Source | Starting point | Comment |
|---|---|---|
| Chroma 2024-07-03 | recursive **200–400 tokens, no overlap** | The only token-level measurement in the scan; two chunkers of Chroma's own among the winners |
| Unstructured (2024-07-17 blog, s6 snapshot) | "about 250 tokens" | A vendor default |
| Weaviate 2025-09-04 | "A good place to start is a chunk size of 512 tokens and a chunk overlap of 50-100 tokens. This gives you a solid baseline" | A starting point for comparison, not a default; "between 10 % and 20 %" overlap |
| Pinecone 2025-06-28 | Fixed-size chunking: "we recommend starting here and iterating only after determining it insufficient"; the size is "usually… the max context window size of the embedding model" — what the page says people usually do, not a recommendation of its own | Contradicted by Chroma's measurement; a vendor opinion |

**This KB's position** (digest §5): start at recursive 200–400 tokens of the model's tokenizer with no overlap, or at the element or page boundary when the parser gives one; overlap only where the eval shows recall needs it (the small-model case above); the token-level eval on your corpus moves it. Kamradt's 2024 go-to of 2,000–6,000 *characters* is dated opinion.
