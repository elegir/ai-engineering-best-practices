## 1. The configuration — fields and the record block

A vector is a coordinate in one model's space (this KB's reading of Voyage's "All embeddings created with the 4 series are compatible with each other" — stated as a feature because compatibility is not the norm). Everything that makes two vectors comparable is pinned in one object (`EmbeddingConfig` in `embedding_config_and_chunker.py`) and written identically in `docs/stack.md` and the index manifest; `fingerprint()` is the hash of the pinned fields and is generated, never typed.

```yaml
embeddings:                       # docs/stack.md §embeddings — generated by EmbeddingConfig.stack_record()
  model: <<MODEL_ID>>
  version: <<MODEL_VERSION>>      # the provider's dated version or snapshot id; never "latest"
  dimensions: <<DIMENSIONS>>
  supported_dimensions: <<SUPPORTED_DIMENSIONS>>   # the Matryoshka set the provider declares, or (native,)
  dtype: <<DTYPE>>                # float32 | bfloat16 | float16 | int8 | uint8 | binary | ubinary
  metric: <<METRIC>>              # cosine | dot | euclidean
  max_input_tokens: <<MAX_INPUT_TOKENS>>
  query_input_type: <<INPUT_TYPE>>      # the provider's query convention, or null
  document_input_type: <<INPUT_TYPE>>   # the provider's document convention, or null
  tokenizer_name: <<TOKENIZER>>      # the exact name the Tokenizer implementation reports; the manifest check compares it
  fingerprint: (generated by EmbeddingConfig.fingerprint(); never typed)
  decided: <<WINNER_DATE>>        # embedding-model-selection.md §4
```

`matches_stack_record()` refuses a record that disagrees with the configuration field by field; `IndexManifest.check()` refuses a manifest whose fingerprint differs (README Verify 1).

## 2. Query vs document — the convention lives in the code path

"Questions and documents are very different text objects" (Lance Martin, 2024-04-17). The vendors fix it at embedding time, each differently (read 2026-10-04): **Voyage** — `input_type` is `None`, `query` or `document`; "Voyage automatically prepends a prompt to your inputs before vectorizing them"; "Embeddings generated with and without the `input_type` argument are compatible". **Cohere** — `input_type="search_query"` for the query, `"search_document"` for "the text passages that are being searched over"; `classification` and `clustering` for those tasks. **OpenAI's guide** exposes no such parameter: one string for both sides. The research behind one model for both sides is Reimers' 2022-12 account: DPR used two encoders, TAS-B one, and "the same model… work[s] totally better especially like for the out of domain setting". Rule: callers pass `side` (`query` | `document`); `Embedder.embed()` applies whatever the configuration names and refuses a call without a side (Verify 2). The configuration records the convention so a later reader knows which prefix the stored vectors carry.

## 3. Dimensions — the Matryoshka rule

More dimensions mean "more space with which to get accuracy… at the cost of larger storage size", and traditionally "you have to re-embed your entire corpus… every time you want to try a different number" (Johnson, MongoDB, 2026-01-29). Models trained with **Matryoshka representation learning** order the dimensions so "you can basically cut the… vector" (Radu); "I just chop off the last 512" (Johnson). Values as read on 2026-10-04:

| Provider | Default dimensions | Declared Matryoshka set | Statement |
|---|---|---|---|
| OpenAI | 1536 (`text-embedding-3-small`), 3072 (`text-embedding-3-large`) | any value via the `dimensions` parameter on the v3 models | "a `text-embedding-3-large` embedding can be shortened to a size of 256 while still outperforming an unshortened `text-embedding-ada-002` embedding with a size of 1536" on MTEB; when truncating after the fact "you need to be sure to normalize" |
| Voyage | 1024 | 2048, 1024, 512, 256 on `voyage-4-large`, `voyage-4`, `voyage-4-lite`, `voyage-3-large`, `voyage-3.5`, `voyage-3.5-lite`, `voyage-code-3`; `voyage-3`, `voyage-finance-2`, `voyage-law-2` list one dimension | "Most models only support a single default dimension" |
| Cohere | 1024 in the examples | `[256, 512, 768, 1024, 1536, 2048]` on `embed-v5.0-pro` via `output_dimension` | "Matryoshka learning creates embeddings with coarse-to-fine representation within a single vector" |

**Rules.** (1) `dimensions` must be in the model's declared set — the configuration refuses anything else (`UnpinnedConfig`); a model that declares no set has exactly one. (2) Truncation happens in the one embed path and is followed by normalisation when the metric is cosine or dot. (3) Fewer dimensions is a measurement, not a default: Radu saw 512 dimensions beat the full vector on one model and lose "a little bit" on another — "test on your data" (the eval set of `chunk-eval-harness.md`). (4) A different dimension is a different configuration: new fingerprint, new index (§5).

## 4. dtype — the quantization ladder, each step measured

Two quantizations, not one (Radu, 2026-08-31). **The model's weights**: "int8 is a good quantization to pick" on CPU; on GPU an int8 model "is actually going to be a whole lot slower, but you can run… an FP16 variant". **The vectors**: "if you go to bfloat16, you're probably not going to lose any. So that's basically a no-brainer… all the way down to bit vectors, but then you're going to lose something. Whether that something is worth it or not, that's up to you"; under hybrid search the float-to-bit gap "shrinks a little bit"; at scale, binary with Hamming distance as the first phase and "something more expensive to re-rank" (session 10). Provider dtypes as read on 2026-10-04: Voyage `output_dtype` ∈ `float`, `int8`, `uint8`, `binary`, `ubinary` — a binary list is "1/8 of `output_dimension`"; Cohere `embedding_types` with the same five — "1024 binary embeddings… will become 1024/8 => 128 bytes", with `np.unpackbits` code on the page; MongoDB quantizes inside the index (session 8).

The ladder: **float32 → bfloat16 → int8 → binary**. Each step down is adopted only with a before/after on the eval set and a recorded storage and latency gain (README Verify 8: "a binary index with no measurement beside it" is the negative). bfloat16 is the default when the store supports it; below it, measure.

**The store's side (added 2026-10-05, s8).** Quantization *inside the index* — scalar, binary, product or rotational, with oversampling and rescoring against the originals — is a second quantization and is recorded in the **store manifest** (`../vector-store/vector_store.py`, `StoreManifest.set_quantization()`), not in `EmbeddingConfig`: the configuration's `dtype` says what the embedder produces, the store manifest says how the index holds it, and the two are checked together. Vendors' methods, factors and the originals' placement: `../vector-store/tuning-and-capacity.md` §5.

## 5. Metric

OpenAI's guide (read 2026-10-04): OpenAI embeddings "are normalized to length 1", so cosine "can be computed slightly faster using just a dot product" and cosine and Euclidean "will result in the identical rankings"; "the choice of distance function typically doesn't matter much". Radu: dot product on normalised vectors, Hamming on bit vectors. The configuration records the metric because the store's index is built for one, and a metric change is a configuration change.

## 6. Versioning and the re-embed protocol (README Verify 7; the record Martin reads for Verify 8)

Glean (2025-03-05) on why: "if your model does change… you have no way around it or else the quality of your embedding search is going to become a lot worse over time if you don't reindex everything". Any change to model, version, dimensions, dtype, metric or convention is a new fingerprint and runs this protocol:

0. **Not every change is a re-embed (added 2026-10-05, s8).** An index type, parameter, placement or store-quantization change is **not** a re-embed: rebuild the index from the stored vectors under a new store manifest (`../vector-store/`), run the same shadow comparison of step 2, keep the fingerprint. Only a change to the fields of `EmbeddingConfig` runs steps 1–4.
1. **New index, new manifest.** Build `index-<fingerprint>` with its own manifest (config fingerprint, dimensions, chunker record, corpus hash, eval record). The old index is not touched. `Index.upsert()` refuses a vector whose fingerprint or dimension differs from its manifest's, so a job that writes into the wrong index fails at the first row.
2. **Shadow comparison.** Run the retrieval eval (`chunk-eval-harness.md`) against both indexes with the same questions; record both rows in `docs/eval-policy.md` §retrieval with the date. The new index must meet the recorded floor; a context prefix, a dtype step or a dimension cut introduced at the same time gets its own before/after row — that row is Verify 8's record.
3. **Cut-over.** Point the query path at the new index in one change (configuration, not code); the query embedder is the new configuration — `Index.search()` refuses an embedder of another fingerprint, so a half-switched deployment fails loudly.
4. **Tombstone the old index** after the bake period `<<BAKE_DAYS>>`; keep its manifest in `docs/stack.md` history with the date it was retired.

Vendor compatibility statements (read 2026-10-04) do not shortcut the protocol: Voyage's "All embeddings created with the 4 series are compatible with each other" and "Embeddings generated with and without the `input_type` argument are compatible" are the vendor's claims about its own space; this KB still treats a model or convention change as a new fingerprint and asks for the shadow comparison, because the cost of being wrong is a silently degraded index and the cost of being right is one eval run.
